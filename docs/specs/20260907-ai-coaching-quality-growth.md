# AI 코칭 판단·설명 품질과 모델 개선 설계 초안

작성일: 2026-09-07. 2026-09-08 상태: 설계 승인 후 첫 판단 보강 구현·검증 완료. 모델 교체와 운영 배포는 하지 않음. 아래 현재 구조 표는 구현 전 조사 기준이다.

## 목표와 담당 경계

사용자가 자신의 경기에서 확인되는 강점과 개선점을 이해하고, 다음 경기에서 시도할 행동 하나를 선택할 수 있게 한다. 단기 목표는 잘못된 판단을 줄이는 것이며, 장기 목표는 경기 근거 확인 → 행동 연습 → 다음 기록 확인으로 이어지는 코칭 경험이다. 기록 변화만으로 코칭의 효과나 인과관계를 단정하지 않는다.

부모 에이전트가 코칭 판단·설명·평가 체계를 담당한다. 별도 담당이 계산 갱신과 검색 상태/자동 복구를 구현한다. 원본 복구 실패를 모델 성능 문제로 취급하거나 AI 재호출로 해결하지 않는다. 관리자 회원 증감 기능은 독립 작업이다.

## 현재 코드에서 확인한 기반과 한계

| 영역 | 확인된 기반 | 다음 점검 대상 |
| --- | --- | --- |
| 최근 요약 | `aiSummaryCards.ts`의 서버 소유 topicId/metricId/evidenceIds, 관측·비교 상태, 중립 의견 승패 제거 | 지표 ID를 참조했다는 사실과 문장의 실제 주장을 분리해서 검증 |
| 기회 없는 비율 | `aiSummaryCardEvidence.ts`는 분모 0을 0%로 표시하지 않고 관측 기회 없음 사유 제공 | 개인/요약/팀의 관측 범위와 기회 정의가 끝까지 유지되는지 확인 |
| 단일 경기 | `matchAiEvidence.ts`에 투척 수치, 비교 누락, 위치·의도 단정 회귀 방어 | 특정 표현 중심의 방어를 넘는 주장 종류별 허용 기준 |
| 스쿼드 | `squadAiEvidence.ts`에 미측정 지표·등급 보류, 개인 기여도 수치 정합성 검사 | 팀 수치를 개인 행동으로 확대 해석하지 않는지 확인 |
| 표현 정제 | `aiCoachingQuality.ts`에 비난·의도 표현 탐지와 치환 | `방관 → 후속 복구 부족`처럼 근거 없는 판단을 순한 표현으로 남길 가능성 |
| 토론 | 공급자 출력은 kind/spicy 승자를 요구하며 서버가 무효 카드의 승자를 제거 | 관측 가능한 정상 카드에서도 균형·판단 보류 결론을 표현할 계약 |
| 평가 | 실제 Gemini 감사 도구, 원본/최종 응답 검사, 수치 맥락 검사 존재 | 실제 서비스 계약과 감사 프롬프트 차이 점검, 미공개 평가 세트와 모델 간 비교 |
| 비용 | `aiUsageTracker.ts`가 모델명·토큰·응답 시간을 기록 | 비용은 현재 공통 고정 단가, 실패 비용 0 처리. 실제 공급자 청구와 동일하다고 볼 수 없음 |

이는 정적 코드 조사 결과다. 알려지지 않은 표현의 운영 발생률이나 새로운 재현 성공을 의미하지 않는다.

## 접근 방식 비교

1. 프롬프트·금칙어만 보강: 변경은 작지만 표현 변형과 의미 오류 방어가 제한적이다. 기존 회귀 방어 용도로 유지한다.
2. 서버의 근거·판단 범위와 AI의 설명을 연결: 기존 ID 카드 구조를 확장할 수 있고, 모델이 바뀌어도 사실 검증 기준을 유지할 수 있다. 권장한다.
3. 모델 교체나 추가 검수 모델부터 도입: 비용·지연이 늘 수 있으며 누락된 원본이나 잘못된 분모를 해결하지 못한다. 평가 체계 구축 후 후보 실험으로 다룬다.

## 제안하는 코칭 계약

기존 근거 카탈로그를 재사용한다. 새 범용 규칙 엔진을 만들지 않고 유틸리티·복구 지표부터 작은 정책 함수로 적용한다.

- 관측 사실: 수치, 단위, 분자·분모, 관측 경기 수, 개인/팀 범위, 계산 버전을 서버에서 확정한다.
- 관측 상태: 값 있음, 기회 없음, 기록 누락, 미구현을 구별한다. 비교 가능 여부는 별도 축이다.
- 비교: 지표별 비교 표본 수, 모드·매치 유형·티어·계산 버전 조건을 유지한다. 표본 최소 조건을 만족해도 통계적으로 유의한 차이라고 자동 선언하지 않는다.
- 판단: 관측 사실 설명, 비교 설명, 원인 추정, 일반 연습 제안을 구분한다. 원인 추정은 사건·시간·위치 등 필요한 근거가 있을 때만 제한적으로 허용한다.
- 행동 제안: 관련 evidenceIds를 연결하되 사실 주장과 연습 목표를 구별한다. “다음 경기에서 2회 연습”은 기록 수치가 아니다. 기회가 없는 상황에 행동 횟수를 억지로 요구하지 않는다.
- 결론: 강점/개선점/혼합/판단 보류를 먼저 결정한다. 매운맛과 착한맛은 동일한 사실을 다른 어조로 설명한다. 강제로 반대 의견이나 승자를 만들지 않는다.

자연어의 모든 의미를 코드로 완벽하게 검증할 수 있다고 가정하지 않는다. 숫자는 가능하면 서버가 표시하고, 해석은 제한된 주장 종류와 근거 연결, 회귀 검사, 사람 평가를 함께 사용한다. 문제가 있는 문장을 순화해 살리는 대신 해당 해석만 보류하거나 검증된 사실 설명으로 대체한다. 올바른 사실과 다른 카드는 유지한다.

## 대표 사용자 경험

1. 한줄 요약: 이번 기록의 핵심 한 가지. 특정 미측정 지표가 전체 평가를 지배하지 않는다.
2. 두 코치: 유지할 행동과 개선할 행동. 비난의 대상은 사람의 성격·의도가 아니다.
3. 근거 보기: 내 기록, 분석 범위, 비교 가능 여부를 함께 설명한다. 기술적인 표본 출처는 펼쳐 볼 수 있게 한다.
4. 다음 경기 목표: 근거와 관련 있는 실천 한 가지. 근거가 부족하면 판정 대신 관찰할 상황을 제안한다.
5. 후속 단계: 실제 장면 근거가 있는 조언에만 리플레이 시점을 연결한다. 과거·최근 기록 비교는 동일 조건/정의와 기회 수가 확보될 때 도입한다.

경기별 분석은 특정 경기의 행동, 최근 요약은 반복해서 관측된 경향, 스쿼드는 팀 단위 결과를 설명한다. 원인 장면은 단정의 증명이 아니라 사용자가 상황을 확인하는 근거다. 티어/점수 산식 변경은 별도 검토이며, 미측정 종합 등급 보류는 유지한다.

## 모델 성능 개선을 위한 평가 체계

모델 자체의 학습 능력과 BGMS가 제공하는 코칭 품질을 구분한다. 사용자 피드백이 쌓인다고 모델이 자동으로 학습되는 것은 아니다.

### 평가 자료

- 기존 실제 텔레메트리 회귀 사례와 합성 경계 사례를 재사용한다. 정답은 문장 한 개 대신 필수 사실·허용 해석·금지 주장·허용 행동 범위로 정의한다.
- 모드, 개인/팀, 관측 0, 분모 0, 누락, 비교 없음, 작은 표본, 같은 비교값, 큰 값, 소생 성공과 긴 백업 시간, 재투입·중복 이벤트, 일부 경기 제외를 포함한다.
- 동일 경기의 여러 플레이어와 표현 변형은 같은 자료 그룹에 넣어 개발용/최종 평가용 세트 사이에 새지 않도록 한다. 새 실제 사례를 별도로 남긴다.
- 전체 원본 텔레메트리를 모델 평가에 반복 전송하지 않는다. 검증된 최소 근거와 필요한 장면만 사용하고 식별자는 가능한 한 가명화한다.

### 측정과 출시 기준

| 검사 | 방식 | 사용 목적 |
| --- | --- | --- |
| 사실·범위·분모·ID·단위 | 결정적 검사 및 경계 사례 | 고정 필수 사례의 중대 오류는 출시 차단 |
| 근거 없는 원인/비난 | 기존 회귀 검사 + 사람이 검토한 사례 | 단순 금칙어 통과를 의미적 정답으로 간주하지 않음 |
| 구체성·이해도·실천 가능성 | 모델명을 가린 A/B 사람 평가, 필요하면 검수 모델 보조 | 기존 응답보다 유용한지 비교 |
| 정제와 보류 | 원본 오류, 최종 오류, 교체/보류 비율을 별도 기록 | 모두 보류해서 오류율만 낮추는 퇴행 방지 |
| 성능·비용 | 시도별 토큰·지연·실패·재시도·캐시 여부 | 품질을 만족한 후보 중 운영 효율 비교 |

모델 검수도 사람 판단과 일치하는지 표본 확인한다. 모델이 자기 응답을 채점한 점수만으로 출시하지 않는다. 소수 사례의 오류 0건을 운영 전체 정확도 100%라고 표현하지 않는다.

### 개선 순서

1. 현재 모델과 실제 서비스 프롬프트/후처리를 기준선으로 고정한다. 별도 감사 프롬프트만 좋아지는 상황을 방지한다.
2. 입력 근거·구조·프롬프트를 개선하고 동일 세트로 비교한다.
3. 후보 모델은 공급자 지원과 조건을 확인한 후 동일 입력·출력 제한·반복 횟수로 비교한다. 소수 사례에서 시험하고 비용 상한 안에서 확대한다.
4. 검증된 필요가 있을 때만 복잡한 사례를 다른 모델에 보내는 분기를 도입한다. 모든 요청의 이중 호출은 기본으로 하지 않는다.
5. 사람이 교정한 충분한 사례가 쌓이고 반복 오류가 남을 때 파인튜닝 적합성·지원 여부·자료 이용 조건을 별도 검토한다. 미리 학습 파이프라인을 구축하지 않는다.

## 비용과 운영

모델별·적용일별 가격 근거와 토큰 종류를 기록하고, 가격을 확인하지 못한 모델 비용은 미확인으로 둔다. 실패했다고 이미 소비한 토큰을 무료로 간주하지 않는다. 캐시를 포함한 사용자 요청당 비용과 실제 모델 호출당 비용을 분리한다.

현재 플랫폼/플레이어/프롬프트와 계산 버전 보호를 유지하면서 코칭 정책 버전 변경에 따른 캐시 호환 여부를 명시한다. 전체 기존 AI 캐시를 한꺼번에 재생성하지 않는다. 새 품질 로그에는 식별 가능한 전체 프롬프트를 기본 저장하지 않고 정책 버전, 실패 분류, 근거 ID 등 최소 정보를 우선한다.

Supabase에는 필요가 확인된 평가 메타데이터만 추가하고, R2 원본 복제나 전 경기 Gemini 재평가는 하지 않는다. 지표 부재를 해결하기 위한 모델 업그레이드는 하지 않는다.

## 첫 구현 단위와 후속 순서

첫 단위는 **기존 유틸리티·복구 근거로 허용할 판단을 정의하고, 사실 없이 순화된 비판이 남는지 회귀 검사하는 것**이다. 기존 0/기회 없음 처리를 새로 만들지 않고 개인·요약·팀 경계까지 이어지는지 검증한다.

1. 기존 실제 사례의 사실/금지 주장 목록과 현재 응답 기준선을 작성한다.
2. 근거 없는 비판의 단순 치환을 사실 설명 또는 해석 보류로 대체하는 최소 정책을 구현한다. 정상적인 조언이 과도하게 사라지지 않는 사례도 함께 검사한다.
3. 전체 카드 재작성보다 토론의 혼합/보류 결론 계약을 먼저 검토하고, 프롬프트·파서·캐시·화면을 함께 변경한다.
4. 같은 검증 정책을 한줄 요약과 행동 제안에 적용한다. 서로 다른 영역의 결과가 모순되지 않는지 확인한다.
5. 기준선이 갖춰지면 모델 후보 비교, 이후 장면 근거 연결과 목표 추적을 진행한다.

이 문서는 방향성 초안이며 모델 교체·운영 적용·배포 완료를 의미하지 않는다. 구체적인 통과율·비용 예산은 첫 기준선 측정 결과를 보고 정한다.

- [Google Cloud 평가 모델 검증](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/models/evaluate-judge-model): 사람의 평점/선호와 모델 평가를 비교하는 기준을 참고한다. Vertex 도입을 전제로 하지 않는다.


## 2026-09-08 첫 구현 결과

- 근거 없는 비난을 다른 부족 판정으로 순화하던 동작을 문장 단위 판단 보류로 변경했다. 정상 문장과 조건부 연습 조언, JSON 구조, 닉네임과 근거 ID는 보존한다.
