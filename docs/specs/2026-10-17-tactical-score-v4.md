# 전술 안정도 계산 4 설계

상태: 설계 검토 중(구현 전). 근거 데이터는 2026-10-17 운영 DB 읽기 전용 조회 결과다.

## 1. 목적

측정할 기회가 없었던 지표에 관측 평균보다 높은 대체값을 넣어, 기회가 없던 경기가 기회가 있었는데 실패한 경기보다 높게 평가되는 문제를 고친다. 기본 점수와 티어가 바뀌므로 `ANALYSIS_CALCULATION_VERSION`을 4로 올린다.

같은 시기에 모드가 섞여 티어가 부풀려지는 문제(솔로)는 계산식을 바꾸지 않고 화면·집계에서 모드를 분리해 먼저 막는다(8절).

## 2. 근거 데이터

대상: `global_benchmarks`의 계산 2·3, `score > 0` 경기(팀 12,927건, 솔로 295건). 표본은 검색된 플레이어 경기라 상위권에 치우쳐 있다(스쿼드 평균 순위 7위). 전체 티어 비율의 적정성이 아니라 같은 조건끼리의 상대 비교에만 쓴다.

### 2.1 대체값과 관측 평균

| 지표 | 현재 대체값(기회 없음) | 관측 평균(팀) | 관측 평균(솔로) |
| --- | --- | --- | --- |
| 소생률 `reviveRate` | 정상 탈락 100%, 조기 탈락 30% | 14.5% | 해당 없음 |
| 트레이드율 `tradeRate` | 100% / 30% | 8.1% | 해당 없음 |
| 연막 구출률 `smokeRate` | 100% / 30% | 5.7% | 해당 없음 |
| 지원사격률 `suppRate` | 100% / 30% | 9.7%(팀 경기의 24%가 기회 없음) | 해당 없음 |
| 역전 승률 `reversalRate` | 조기 10%, 무사망 1200초 이상 100%, 그 외 50% | 13.2% | 33.0% |
| 반격 속도 점수 | 측정 불가 5점 | 3.28점 | 3.76점 |
| 선제공격률 `initiativeRate` | 45% | 43.1% | 68.4% |

지원사격률은 `global_benchmarks`에 없어 `processed_match_telemetry.data.fullResult.tradeStats.suppRate`(계산 2·3, 팀 16,861건)에서 구했다.

### 2.2 같은 순위대 비교(팀)

| 순위 | 기회 없음 | 기회 있었으나 실패 | 일부 성공 |
| --- | --- | --- | --- |
| 1~3위 | 67.0점(평균 딜 466) | 59.1점(479) | 66.6점(618) |
| 4~10위 | 45.8점(189) | 42.4점(259) | 52.7점(385) |
| 11위 이하 | 33.9점(129) | 30.2점(156) | 41.8점(247) |

기회 없음이 실패보다 3~8점 높고, 1~3위에서는 일부 성공보다도 높다.

## 3. 계산 4 산식 변경

원칙: 기회가 없어 측정되지 않은 비율 지표는 해당 모드의 관측 평균으로 채운다. 평균은 고정 상수로 두고 계산 버전에 묶는다(시간에 따라 같은 경기의 점수가 바뀌지 않게 한다). 조기 탈락 여부에 따른 대체값 분기는 없앤다. 조기 탈락은 생존 점수와 사망 시점에서 이미 반영된다.

| 지표 | 계산 4 대체값 |
| --- | --- |
| 소생률 | 14.5 |
| 트레이드율 | 8.1 |
| 연막 구출률 | 5.7 |
| 지원사격률 | 9.7 |
| 역전 승률 | 팀 13.2, 솔로 33.0 |
| 반격 속도 점수 | 팀 3.3, 솔로 3.8 |

바꾸지 않는 것:

- 선제공격률 대체값 45%: 팀 평균 43.1%와 거의 같아 이미 중립값이다. 교전 기록이 아예 없는 경기는 팀의 0.6%다.
- 딜량 순위 점수의 구간 경계: 순위 백분율이 저장되지 않아 효과를 검증할 수 없다. 별도 저장 후 다시 검토한다.
- 솔로 배점: 7절 조건이 찰 때까지 유지한다.
- 13단계 티어 기준선, 매치 임팩트 산식.

## 4. 예상 영향(근사 시뮬레이션)

저장된 원본 지표로 대체값 차이만 반영했다. 지원사격률은 `global_benchmarks`에 없어 시뮬레이션에서 빠졌고, 반영하면 기회 없는 경기의 하락 폭이 최대 1.8점 더 커진다.

| 순위 | 기회 없음(현재 → 계산 4) | 실패 | 일부 성공 |
| --- | --- | --- | --- |
| 1~3위 | 67.0 → 57.6 | 59.1 → 58.8 | 66.6 → 66.3 |
| 4~10위 | 45.8 → 38.6 | 42.4 → 42.3 | 52.7 → 52.6 |
| 11위 이하 | 33.9 → 30.2 | 30.2 → 30.1 | 41.8 → 41.8 |

- 팀 평균 49.0 → 47.9점, 경기당 평균 변화 1.2점. 바뀌는 경기는 사실상 기회 없음 경기(팀의 약 13%)다.
- 팀 S 이상 비율 2.3% → 1.3%. 솔로는 66.0 → 65.5점으로 거의 바뀌지 않는다.

## 5. 버전 공존 계약

계산 3 도입(`docs/operations/2026-10-10-calculation-coexistence-*.md`)과 같이 기존 결과를 보존하고 새로 분석하는 경기만 계산 4로 저장한다. 전체 재계산·재라벨·삭제는 하지 않는다.

계산 3과 다른 점: 계산 2·3은 기본 점수 산식이 같아 자유롭게 합쳤지만, 계산 4는 기본 점수가 다르다. 읽는 곳마다 합칠지 정한다.

| 읽는 곳 | 계산 4 방침 | 이유 |
| --- | --- | --- |
| 비교 표본 `benchmark_stats_by_tier_v2` | 2·3·4를 합친다 | 집계 대상은 원본 지표이고 점수는 티어 칸 배정에만 쓰인다. 바뀌는 경기는 약 13%이고 대부분 한 칸 이내다. 분리하면 수 주간 비교 표본이 빈다. |
| 랭킹(주간·지난주) | 2·3·4를 합친다(2026-10-17 결정) | 전환 주에는 기존 점수가 약간 유리하지만 표본을 유지한다. 다음 주부터는 새 분석이 모두 계산 4라 차이가 사라진다. |
| 전적 비교(`battle`) | 2·3·4를 합친다 | 최근 경기 단위 비교이고 8절의 모드 분리와 함께 바뀐다. |
| 개인 전적·과거 점수 표시 | 저장된 값 그대로 | 재계산하지 않는다. |
| 단일 경기 AI 캐시 | 경기의 실제 계산 버전 | 계산 3과 동일 |
| 최근 요약·스쿼드 캐시 | 선택 경기의 실제 버전을 해시에 포함 | 계산 3과 동일 |
| 자동 성과 계산 작업 | 기존 2·3 결과가 있으면 4로 재계산하지 않는다 | 계산 3과 동일, 대량 재계산 방지 |

## 6. 구현 범위

- `lib/pubg-analysis/benchmarkScore.ts`: 대체값 상수와 분기 정리(계산 4 전용 상수를 이름 붙여 정의).
- `lib/pubg-analysis/constants.ts`: `ANALYSIS_CALCULATION_VERSION = 4`, `SUPPORTED_ANALYSIS_CALCULATION_VERSIONS = [2, 3, 4]`. AI 캐시 버전 문자열에 계산 버전이 들어가는 곳 확인.
- DB 함수 migration(새 파일로 추가, 기존 migration은 수정하지 않음):
  - `upgrade_analysis_calculation` 등 `calculationVersion NOT IN ('2','3')` 검사 2곳(`20261010000000_analysis_calculation_v3.sql`).
  - 저장 함수의 `calculation_version` CASE 식(같은 파일 113~114행 계열).
  - 랭킹 함수의 `p_calculation=3 and calculation_version=2` 포함 조건(`20261010001000`, `20261014190000`): 5절 결정에 따라 수정.
  - `scripts/verify_migrations_local.sh`의 `MIGRATIONS` 배열과 prerequisites·시나리오 SQL 갱신.
- 버전 목록을 직접 쓰는 TS reader(`benchmarkLookup.ts`, `performanceCache.ts`, `retainedPerformance.ts`, `cacheIdentity.ts`, `squadAnalysis.ts` 등) 확인.
- 문서: `docs-private/tier_score_rules.md`(개발용), `docs/tactical_score_guide.md`(사용자용) 대체값 설명.
- 테스트: 대체값 회귀(기회 없음 ≤ 실패 + 소폭), 버전 공존(2·3 조회, 4 저장, 미지원 버전 거부), migration 시나리오.

## 7. 솔로 기준

- 같은 플레이어(솔로 2경기·팀 5경기 이상, 30명)의 솔로 평균은 61.0점, 팀은 44.1점으로 16.9점 높다. 경쟁전 솔로도 S 이상이 50.8%라 봇 영향이 아니다.
- 원인은 세 영역 모두에 걸쳐 있다(만점 대비 전투 65% vs 48%, 생존 69% vs 53%). 솔로 선제율 평균(68%)이 만점 기준(60%)을 넘어 변별력이 없다.
- 표본이 작아(월 약 160경기) 지금 가중치를 바꾸지 않는다. 같은 플레이어 비교 100명 또는 솔로 1,000경기가 쌓이면, 같은 플레이어의 솔로 점수 분포를 팀 분포에 맞추는 백분위 연결로 보정한다.

## 8. 먼저 할 일: 모드 분리(계산 버전 변경 없음, 이 문서와 같은 PR에서 구현)

- 전적 비교(`app/api/pubg/battle/route.ts`): 최근 경기를 모든 모드에서 섞어 평균 티어를 낸다. 솔로/팀을 나눠 각자 경기 수가 많은 쪽으로 티어를 계산하고, 두 사람의 기준이 다르면 티어 비교를 보류한다.
- 최근 요약 잠재 티어(`app/api/pubg/ai-summary/route.ts`): 점수 상위 경기를 모드 구분 없이 평균한다. 솔로/팀 중 경기가 많은 쪽만 평균하고, 솔로면 "솔로 기준"을 표시한다. 칭호 접두어도 이 티어를 따른다.
- 범위 판정은 점수 산식과 같은 기준(`gameMode`에 `solo` 포함)을 쓰고 동률이면 팀을 쓴다(`lib/pubg-analysis/tierAveraging.ts`의 `tierScopeOfMode`, `dominantTierScope`).

## 9. 운영 적용 절차

1. migration을 파일 하나씩 적용하고 함수 정의·권한·기존 계산 2·3 점수 불변을 확인한다(`docs/operations/2026-10-10-remaining-review-fixes.md` 절차).
2. 서비스 코드 배포 후, 분석 기록이 없던 경기 1건을 조회해 계산 4 저장을 확인한다.
3. 1주일 뒤 같은 순위대 비교(2.2절)를 다시 조회해 기회 없음이 실패 수준으로 내려왔는지 확인한다.

## 10. 결정

1. 랭킹은 전환 주에도 계산 2·3·4를 합친다(2026-10-17).
2. 모드 분리(8절)는 계산 4보다 먼저 별도 PR로 낸다(2026-10-17).
3. 반격 속도 대체값을 모드별 평균으로 바꾸는 것을 계산 4에 포함할지 검토 중.
