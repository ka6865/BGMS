기존 관리자 가드·동일 출처 검사·비공개 응답 계약을 유지한다. 원격 DB와 실제 Riot API 호출, 기존 개발 서버 재시작, 커밋과 staging은 수행하지 않는다.

## 호출 수

아래는 Riot API 호출만 계산한다. Data Dragon 정적 데이터와 내부 DB 조회는 제외하며, 신규 상세 수를 `U`(0~5)로 표시한다.

| 동작 | account | summoner | league | 경기 ID | 상세 | 합계 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 첫 검색, 저장된 원문 없음 | 1 | 1 | 1 | 1 (`count=20`) | 최대 5 | 최대 9 |
| 첫 검색, 상세 원문 모두 저장됨 | 1 | 1 | 1 | 1 | 0 | 4 |

검색 DTO는 `search:v7`을 사용한다. 더 보기 전용 응답 캐시는 만들지 않고 경기 원문 저장소와 기존 경기 캐시를 사용한다. PUUID는 서버에서만 해석하며 응답에는 넣지 않는다.

## Development Key 처리량

기준은 20회/초·100회/2분이며 BGMS 중앙 가드는 동시 lease 2개, 최소 1.5초 간격, Riot 429 쿨다운을 적용한다. 일일 예산은 없다.

최소 간격 기준 최대 처리율은 약 `60 / 1.5 = 40회/분`, `120 / 1.5 = 80회/2분`이다.
신규 상세 5경기는 약 `5 × 1.5 = 7.5초`의 요청 슬롯을 사용하고 첫 검색 최대 9회는 약 13.5초를 사용한다.
이는 외부 응답 시간·다른 계정 요청·대기열·정적 데이터 조회를 제외한 슬롯 기준 근사치이다.

첫 검색 상세 수는 최대 5개로 유지하여 ID 목록 확대가 동기 상세 요청 수를 늘리지 않는다. 원문이 있으면 해당 경기의 Riot 상세 호출은 없다.

## 결정 사항

- URL 정책: 관리자 단계는 Riot ID URL, 공개 단계(챕터6)에서 공개 UUID 설계와 재검토.
- 관리자 전적 주소는 `/admin/lol/kr/이름-태그`이며 이름·태그 세그먼트를 인코딩하고 마지막 `-`로 구분한다. `/admin/lol`은 검색 입력 화면으로 유지한다.
- 검색·참가자·함께 플레이 이름 선택은 URL `push`, 큐 선택은 `?queue=all|solo|flex|aram`의 `replace`를 사용한다. 큐만 바꿀 때 검색 API를 다시 호출하지 않는다.
- URL 페이지 진입·새로고침·뒤로/앞으로 이동 시 기존 검색 API로 대상을 복원한다. 페이지·레이아웃·메타데이터에 관리자 가드와 noindex를 유지한다.
- 1차 구현은 전체 경기 ID 목록을 확보하고 큐 필터는 클라이언트에서 적용한다. 따라서 선택한 큐의 표본은 로드된 전체 경기 중 해당 큐의 경기 수다.
- 다음 페이지는 20개 단위로 ID를 조회하고 상세는 한 번에 최대 5개 처리한다. 정확히 20개가 반환되면 추가 페이지 존재 가능성을 `hasMore`로 알린다.
- 화면은 확보한 ID에서 다음 최대 5개를 서버에 전달한다. 해당 목록을 모두 소비했을 때만 오프셋으로 다음 ID 페이지를 요청하므로, 확보한 ID를 다시 조회하지 않는다.
- 경기별 실패는 성공 경기와 별도로 전달한다. 실패 경기 재시도는 새 목록 진행 오프셋을 이동시키지 않는다.
- 갱신은 DTO와 account·summoner·league·ID 요청 캐시를 무시하고 상세 원문은 재사용한다. 쿨다운은 서버가 강제하며 남은 시간을 정상 상태 응답으로 알린다.
- 서버 쿨다운은 기존 `lol_accounts.account_fetched_at`을 사용한다. 새 migration은 추가하지 않았으며 운영 DB 적용은 없다.
- 갱신 lease를 얻은 뒤 계정 시각을 다시 읽어, 대기 중 다른 갱신이 완료된 경우에도 120초 제한을 적용한다.
- 요약은 승률·합산 KDA·평균 K/D/A·관여율·챔피언·포지션·동료를 동일한 순수 함수로 계산한다. 무효 경기 제외와 미제공 값 처리는 기존 규칙을 유지한다.
- 동료 집계용 경기 데이터는 Riot ID와 승패만 전달하고 원문 계정 식별자는 노출하지 않는다.
- 실제 Riot 429·공유 쿨다운과 BGMS 자체 동시 수집·간격 제한을 구분해 안내한다.
- 갱신 시 기존에 로드한 경기와 실패 상태를 보존하고, 새로 로드한 경기만 앞에 추가한다. 요약은 병합한 전체 경기로 재계산한다.
- 갱신 후 다음 오프셋은 새·기존 ID 목록에서 이미 처리한 연속 구간으로 계산한다. 추가 페이지 가능성은 갱신으로 늘어난 ID 개수의 20 배수 여부와 별도로 유지한다.
- 갱신 대기 중 기존 카드는 유지하고 진행 문구는 프로필 헤더에만 표시한다. 저장소 오류 뒤에는 같은 동작을 다시 요청하는 버튼을 제공한다.
- 계정 조회와 공통 RPC의 DB 대기 제한은 공통 10초로 통일한다. 기존에는 양쪽 모두 4초였으므로, 계정 조회만 다른 타임아웃을 사용한 상태는 아니었다.
- 저장소 실패 로그는 작업명·단계·`timeout` 또는 `db_error` 사유 코드만 기록한다. 입력값·PUUID·키·원본 오류 본문은 기록하지 않는다.

## Production Key 전환 시 조정 지점

키 등급을 올려도 즉시 표시 상세 수와 중앙 가드 값은 자동 변경하지 않는다.
실제 승인 한도·응답 시간·저장 원문 적중률을 확인한 뒤 동기 상세 최대 5개, 더 보기 배치 최대 5개, 중앙 permit의 1.5초 간격과 동시 lease 수를 함께 조정한다.
요청·응답 크기 제한과 부분 실패 재시도 테스트도 같은 계약에 맞춰 갱신한다.

## 검증과 미확인 사항

검증은 실제 Riot API와 원격 DB에 접속하지 않고 mock과 기존 fixture 하네스로 수행했다.

- `npm run verify:core`: 종료 코드 0, ESLint·TypeScript 오류 없음, 경고 47개.
- `npm run verify:lol`: 153개 통과. URL 파싱·동적 페이지 권한·메타데이터, ID 요청 크기, 원문 재사용, 갱신 쿨다운·부분 실패와 공개 응답 계약을 포함한다.
- 공용 요약 단위 테스트: 3개 통과. 누적 표본·합산 KDA·큐 분리·결측·무사망·동료 중복 제거를 확인했다.
- mock 브라우저: 최종 21개 통과. 기존 목록·갱신·실패 시나리오와 URL 변경·새로고침·뒤로/앞으로·큐 replace·참가자/동료 이동·같은 URL 재시도를 검증했다.
- URL의 큐만 바꿀 때 API 호출이 늘지 않고, 개발 모드의 중복 Effect 실행에서도 진입당 검색 요청이 하나인 것을 확인했다.
- fixture 하네스는 React hydration 완료 후 입력·클릭을 시작한다. 라우터 훅은 History API로 대체하며, 실제 동적 페이지의 서버 렌더링·권한·메타데이터는 별도 검사한다.
- 뷰포트: 375×667, 390×844, 430×932, 1024×900, 1440×900에서 기존 검색·카드·상세·요약 넘침 검사가 통과했다.
- 제품 경로의 `requestUrl`과 변경 파일의 300자 초과 줄은 검출되지 않았다.
- migration 추가가 없어 migration·실제 DB 검증은 실행하지 않았다. 기존 개발 서버의 프로세스를 유지했고 커밋·staging은 수행하지 않았다.
- 이 작업 폴더에는 `.agents/rules/project_rules.md`가 없으므로 제공된 `AGENTS.md`, 실제 구현과 포함된 문서·테스트를 기준으로 작업했다.

실제 Riot Development/Production Key의 응답 지연·429 동작과 운영 DB 적용, 실제 모바일 기기는 mock·뷰포트 검증 범위에 포함하지 않는다.
첫 컴파일 직후 관찰된 실제 503이 DB timeout이었는지는 기존 로그로 확정할 수 없으며, 추가한 사유 로그로 후속 실사용 확인이 필요하다.
