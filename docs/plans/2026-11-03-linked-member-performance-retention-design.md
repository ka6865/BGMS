# 연동 회원의 장기 성과 보존 전환 설계

일일 성과 보충 대상을 마이페이지에서 PUBG 닉네임과 플랫폼을 등록한 회원으로 좁힌다. 연동 명단을 먼저 구하고 사용자별 분석 원본을 직접 조회해, 전역 정리 커서를 따라 전적 전체를 읽는 병목을 제거한다. 아래 준비 집계와 실제 구현·운영 검증 결과의 시점을 구분한다.

## 조회 결과

2026-11-03 22:05 KST 운영 DB 읽기 전용 조회 기준이다. 닉네임과 계정 ID는 문서에 기록하지 않는다.

후보는 기존 SQL의 계정 형식·이름·계산 버전·결과 버전과 저장 요약 부재 조건으로 집계했다. 저장 전 `buildRetainedPerformanceRow` 검증 결과에 따라 줄어들 수 있다. 운영 데이터는 집계 중에도 변한다. 앞서 21:49~21:51 KST에 집계한 전체 14일 경과 후보 9,719건과 비교하면 300건은 약 3.1%다. 두 집계는 동일 시점의 스냅샷은 아니다.

연동 대상별 원본은 최대 318건이고, 100건을 초과한 대상은 10개다. 최대 원본 보유 대상에 대해 플랫폼·닉네임을 먼저 제한한 조회 초안을 `EXPLAIN ANALYZE`로 실행했다. 계획 22.053ms, 실행 1,296.385ms, 후보 3건이었다. 이는 식별자만 반환한 단일 대상 측정이며 전체 명단, 원본 JSON 전송, 콜드 캐시의 8초 내 완료를 보장하지 않는다.

## 대상 정책

- 현재 `profiles.pubg_nickname`과 `pubg_platform`이 유효한 회원을 대상으로 한다. 최근 활동 기간은 제한하지 않는다.
- 앞뒤 공백과 대소문자를 정규화하고 `steam`·`kakao`를 구분한다. 같은 플랫폼·닉네임을 등록한 여러 프로필은 한 번만 처리한다.
- 일일 보충의 경기 나이는 기존 14일 경과 기준을 유지한다. 기간 내 경기 요약은 기존 일반 분석과 성과 worker가 저장한다.
- Discord 단독 연동은 이번 명단에 포함하지 않는다. 현재 마이페이지의 연동 정보가 기준이며 계정 소유권 인증을 추가하는 작업은 아니다.
- 연동 해제 대상과 닉네임 변경 전 별칭은 일일 명단에서 빠진다. 과거 계정을 닉네임만으로 추정해 연결하지 않는다. 이미 저장한 성과는 유지한다.
- 일반 경기 분석의 요약 저장, 핵심 백업, 미연동 기록을 포함한 R2 삭제 전 보존 검증은 기존 경로를 유지한다. 일일 명단 축소가 원본 삭제 허용 조건을 바꾸지 않는다.

## 접근 방법

| 방법 | 영향 | 판단 |
| --- | --- | --- |
| 기존 전역 RPC에 회원 필터만 추가 | 커서와 넓은 전적 조회가 남을 수 있다 | 병목 해소 근거가 부족하다 |
| 연동 명단을 먼저 읽고 플랫폼·닉네임별로 조회 | 기존 인덱스를 사용하고 사용자별 요청을 작게 제한할 수 있다 | 추천 |
| 모든 요약 저장·원본 정리까지 연동 회원 전용으로 변경 | 미연동 기록의 보존과 삭제 계약까지 바뀐다 | 이번 변경 범위를 넘는다 |

사용자가 선택한 방향은 일일 보충의 연동 회원 전환이다. 사용자별 조회와 아래 실행 상한은 그 방향을 구현하기 위한 제안이다.

## 변경 범위

1. `scripts/preserve_match_performance.ts`: 기본 일일 실행에서 연동 명단을 조회하고 사용자별 후보를 순차 처리한다. 실행당 기존 `--limit 1000` 상한 안에서 사용자별 조회를 최대 100건으로 제한한다. 신규 행 저장과 누락 요약 보완은 기존 `preservePerformanceRows`를 사용한다.
2. 신규 migration: 플랫폼·닉네임으로 원본을 먼저 제한하는 연동 대상 조회 RPC를 추가한다. RPC 내부에서도 현재 프로필 연동과 14일 경과 기본 전적을 확인한다. 접근 권한은 `service_role`에만 부여하고 기존 전역 RPC와 정리 커서는 바꾸지 않는다.
3. `.github/workflows/daily-tasks.yml`: 일일 단계의 이름·설명을 연동 회원 보충으로 맞춘다. DB health와 핵심 백업·복원 검증 gate를 유지한다.
4. 기존 `--nickname` 수동 점검은 기존 운영 도구의 별도 경로로 유지한다. 기본 일일 실행이 이 경로를 사용해 명단을 넓히지 않도록 테스트한다.
5. 기존 점수·티어·benchmark·랭킹 자격을 덮어쓰지 않고, 동시 갱신 보호와 저장 후 읽기 검증을 유지한다. 결과 로그에는 대상 수와 저장·제외 건수만 남긴다.

새 큐·커서 테이블·의존성·회원 UI는 추가하지 않는다. 이번 변경은 일일 보충 범위와 조회 경로에 한정한다.

## 검증과 적용 순서

- `tests/preserve-match-performance.test.ts`: 연동 명단 중복 제거, 플랫폼 분리, 비연동 대상 제외, 실행 상한, dry-run의 쓰기 0건, 저장 실패 중단과 기존 점수 보호를 검증한다.
- 격리 migration fixture: 미접속 연동 회원 포함, 14일 경계, 닉네임 정규화, 이미 보존한 버전 제외, 비연동 RPC 호출 제외, 계정 불일치와 `service_role` 전용 권한, 정리 커서 불변을 확인한다. 신규 migration을 `scripts/verify_migrations_local.sh`의 명시 목록에 연결한다.
- `tests/daily-tasks-workflow.test.ts`에서 백업 gate와 기본 일일 경로를 확인한다.
- 코드 검증은 `npm run verify:core`, `npm run verify:analysis`, 집중 테스트, `npm run verify:migrations`, 통합 전 `npm run test:unit`을 실행한다.
- `docs/operations/2026-10-06-match-detail-retention.md`와 로컬 `docs-private/.project_context.md`를 실제 구현에 맞춰 갱신한다.
- 운영 적용 전에는 연동 대상별 실제 원본 반환을 포함한 읽기 전용 dry-run으로 후보·제외 사유·요청 시간을 다시 확인한다. 이후 운영 migration 적용과 실제 저장은 각 실행 경로의 적용 범위를 확인해 진행한다. 삭제 작업은 이 변경에 포함하지 않는다.

기존 스크립트의 요약 검증에서 탈락하는 자료는 보존 완료로 계산하지 않는다. 탈락 자료가 사용자별 첫 100건을 계속 차지하면 이후 후보가 밀릴 수 있으므로, 전체 dry-run에서 이 상황을 먼저 확인하고 필요할 때만 페이지 이동을 보완한다.

## 구현과 실제 검증 결과

- `--linked-only`를 명시한 실행을 추가해 기존 수동 CLI와 전역 RPC를 유지했다. 신규 migration `20261103135922`는 운영에 적용했고 익명·로그인 사용자 실행 권한 없음과 `service_role` 실행 권한을 확인했다.
- 실제 dry-run: 대상85, 조회305, 변환304, 제외1, 저장0. 전체24.02초, 최대조회3130ms, 사용자별·전체 상한 도달0이었다.
- 실제 적용: 대상85, 조회307, 변환306, 저장 후 읽기 검증306, 제외1. 전체31.56초, 최대조회950ms였다. 두 실행 사이에 14일 경계를 넘은 경기로 후보 수가 변할 수 있다.
- 실제 적용 후 재 dry-run: 조회1·변환0·저장0·제외1, 11.68초. 저장 가능한 연동 후보가 남지 않았음을 확인했다.
- 제외1건은 `tutorialatoz` 경기의 순위0으로 기존 요약 검증이 거부한 자료다. 기존 점수 추정이나 원본 변경 없이 제외했다.
- 로컬 집중 테스트126개, analysis 1,145개, 전체 단위 테스트6,329개와 격리 migration 검증이 통과했다. 전체 단위 수는 workflow 테스트 추가 전 실행 기준이며 이후 통합 검증은 PR CI로 확인한다.
- `verify:core`는 기존 로컬 전용 `docs-private/coaching-role-evidence-2026-10-29/pending-extra-replay.ts`의 깨진 import2건으로 실패했다. 해당 로컬 폴더를 제외한 타입 검사와 변경 파일 lint는 통과했다.
