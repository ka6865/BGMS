## 점검 범위와 확인된 결함

경기 API의 참가자/roster/asset 연결 → 원본 수신 → 이벤트·필드 필터 → 비공개 분석 캐시 → 엔진의 위치/교전/투척/자기장 계산 → 스쿼드 집계·장면 → 공개 리플레이·AI 캐시를 추적했다. 모든 지표의 의미와 정확도가 검증됐다는 뜻은 아니다. 수정한 산술/식별 오류와 별도 정의 검증이 필요한 지표를 아래에서 구분한다.

| 결함 | 영향 | 수정 |
|---|---|---|
| 팀 roster ID로 개별 accountId를 선택 | 여러 팀원이 같은 사람의 위치를 참조 | 관측된 이름/accountId를 개인별 연결, 두 위치 별칭 동기화 |
| 오래된 accountId 위치와 이름 위치 혼용, false 상태의 OR fallback | 거리 과장, 사망한 팀원 포함 | 최신 위치 사용, nullish 상태 조회, 적 별칭 중복·사망/기절 제외 |
| 요청자만 팀으로 지정한 최초 lite 필터 | 실제 다른 팀원 위치 최대 68% 소실(확인한 두 경기) | 분석용 필터는 모든 선택 이벤트/위치를 보존 |
| 분석 캐시에 lite를 저장하고 재조회 시 다시 lite 적용 | 적 위치 100→10→1, 같은 경기의 점수 변화 | analyzeFormat=2/projection=full 계약, 구형 캐시 miss, 재투영 동일성 보장 |
| 공개 리플레이 생성 경로의 샘플 순서 차이 | 전멸·리콜 경계에서 서로 다른 위치 선택 | 두 API 모두 full 투영→엔진 생명주기 처리→적 위치 1/10 표시 샘플 |
| 측정된 대응 속도 0ms만 0점 | 1ms보다 낮은 점수 | 동일한 연속 점수식 적용 |
| 봇 식별에서 공식 stats.playerId 누락 | 봇 수에 따라 인간 딜량 백분위 변동 | stats.playerId 우선, 기존 accountId fallback |
| 개인 연막 기절 키가 timestamp만 사용 | 동시에 기절한 다른 팀원의 소생에 성공 귀속 | victim+기절 시각별 사건, 모든 소생/사망에서 사건 종료 |
| 스쿼드 연막을 소생 후/다음 생명주기에 연결 | 잘못된 구출 수·성공 장면 | 같은 기절 사건, 연막→소생 순서, 죽음/재기절에서 종료 |
| 지도 8192 좌표를 항상 미터로 계산 | 작은 맵의 연막 거리 오판 | mapSizeCm/8192/100 변환; 거리 미측정은 성공 수 null |
| 이름에서 하이픈 제거 | 서로 다른 선수 결합 | 공통 normalizeName 적용 |
| 공개 telemetry 경로의 첫 asset 선택과 원본 match 미검증 | 잘못 연결된 원본 처리 가능 | 관계로 asset 선택, CDN/응답 URL/유일한 MatchDefinition의 match·platform 및 필터 후 요청 선수 account 근거 검증 |
| 체력 0을 truthy fallback으로 100 처리 | 리플레이 체력 표시 오류 | 0 보존 |

공식 원본 계약은 [telemetry events](https://documentation.pubg.com/en/telemetry-events.html), [telemetry objects](https://documentation.pubg.com/en/telemetry-objects.html)를 대조했다. 원본 위치는 cm, 엔진 거리 지표는 m, 지연은 ms, 지도/timeline 위치는 맵 크기를 8192로 환산한 좌표다. 피해는 HP 단위다. 투척 식별의 기존 fallback에서 쓰는 attack_id/projectileId도 필드 필터에 남긴다. 이 별칭을 공식 필수 필드로 간주하지 않는다.

구버전 최초 고립도 두 경기 평균은 **5.604 ≈ 5.6**이다. 앞서 운영 AI가 사용한 고립 수치를 재현했다. 수정 후 평균은 약 0.661이며, 백업 속도 5.596초는 유지됐다. 따라서 이 사례에서 기존 전체 경기 고립도만으로 대열 이탈을 단정한 코칭은 근거 재검토가 필요하다. 교전 중 고립은 별도 지표이며, 낮아진 전체 평균이 모든 교전에서 좋은 위치였음을 증명하지 않는다.

두 경기의 팀원 4명(MiaeQ_Q, KangHeeSung_, Suk-Cun, ckadmfdls__) 모두에 대해 원본/필드 투영/분석 캐시 JSON 왕복 재생을 수행했다. **8개 선수·경기 조합에서 점수·위치·교전·투척·무기·자기장·타임라인·리플레이 산출값 차이 0개**, 원본 팀 소생 건수와 파생 타임라인 소생 건수는 각각 1/2건으로 일치했다. 소생 후 연막·동시 기절·사망 후 재기절·다른 이름·좌표 누락·사녹 거리·체력 0 등은 별도 합성 회귀 사례로 검증했다.

## 다음 작업으로 연결한 오프라인 검증 도구

`scripts/audit_telemetry_calculations.ts`는 네트워크·DB·캐시 쓰기·AI 호출 없이 기존 파일만 재생한다. 실패 시 종료코드 1로 원본/필터/캐시 차이 또는 팀 소생 건수 차이를 알린다. 원본 이벤트 개수, JSON/gzip 크기, 주요 지표, 실행 시간, 집중사격 3/5/8초 관측을 JSON 보고서에 남긴다. 원본과 보고서는 개인정보가 포함될 수 있으므로 git에 넣지 않는다.

```sh
npx tsx scripts/audit_telemetry_calculations.ts \
  --match /path/to/match.json \
  --telemetry /path/to/telemetry.json \
  --nickname MiaeQ_Q --platform steam --all-team \
  --output /path/to/audit.json
```

두 경기의 5초 집중사격 관측은 6/40=15%로 유지됐다. 3초 5/42, 8초 7/37이다. **두 경기로 시간창·실력 기준을 검증할 수 없으므로 calibration=pending, 엄호 점수와 스쿼드 종합 등급 보류를 유지한다.** 다음 표본은 듀오/스쿼드, 큰/작은 맵, 리콜, 봇 혼합, 여러 명 동시 기절, 장거리 교전, 투척 다중 피해를 포함해야 한다.

## 비용과 성능

- 같은 원본 수신에서 분석과 표시를 만든다. 분석 정확도를 위해 비공개 분석 캐시에는 모든 위치를 유지하고, 공개 lite 리플레이의 적 위치는 한 번만 1/10로 줄인다. 추가 Gemini 호출·DB 조회를 넣지 않았다.
- 두 원본 JSON은 각각 약 23.9/23.7MB, 필요한 필드만 보존한 분석 JSON은 약 10.8/12.0MB였다. gzip은 원본 약 1.65/1.73MB, 분석 약 0.87/0.98MB다. R2 서비스는 JSON을 gzip으로 저장하지만, 이 수치는 로컬 직렬화 크기이며 실제 청구 비용 측정은 아니다.
- MiaeQ_Q 공개 lite 리플레이 이벤트 부분의 gzip은 약 0.17/0.22MB로 full 약 0.30/0.38MB보다 작다. 분석 캐시는 과거의 잘못 샘플링한 캐시보다 커지고 엔진의 위치 처리량도 늘어난다. 정확도 비용을 숨기지 않으며, 배포 표본에서 함수 메모리·p95 시간·R2 읽기량을 측정한다.
- 일괄 원본 재수집·AI 재생성은 실행하지 않는다. 기존 원본이 있는 요청 경기부터 제한된 동시성으로 재계산한다.

## 배포 전 필수: 계산 버전 이행

현재 develop 새 결과는 `calculationVersion=1`, 비공개 캐시는 analyzeFormat=2다. 단일 경기 AI는 새 결과에 `.calc1` 프롬프트 캐시 키를 사용한다. 이는 새 계산 결과의 구형 AI 캐시 재사용을 막지만 **과거 데이터 전체를 고치지 않는다.**

1. 기존 processed_match_telemetry 결과와 공개 v61 map 캐시는 여전히 hit다. 따라서 이번 수정만 배포하면 기존 결과가 그대로 보이거나 다른 버전이 섞일 수 있다.
2. benchmark 원본/집계/조회에도 계산 버전 격리가 필요하다. 새 계산 결과를 구형 고립도 표본과 비교하지 않도록 저장·조회 계약과 선택적 재집계 계획을 먼저 반영한다. 구형 지표를 0으로 바꾸지 않는다.
3. 공개 map 캐시는 새 포맷 버전으로 키/registry/소비자/정리 작업을 함께 전환한다. 단순 파일 교체로 동시 워커의 구버전 쓰기를 해결했다고 간주하지 않는다.
4. RESULT_VERSION을 무작정 올리지 않는다. 현재 v72→v73 복구 RPC와 identity 검증이 버전에 결합돼 있으므로 결과 버전 또는 별도 계산 버전 전환을 해당 복구 계약/DB migration과 함께 검증한다.
5. 보관 원본이 있는 최근 요청 경기만 소규모 재분석한다. 원본이 없는 과거 기록은 비교/코칭의 해당 지표를 보류한다. 재분석 시 AI는 요청에 따라 새 입력으로 생성하며 일괄 재생성하지 않는다.
6. 신·구 계산 결과가 섞인 최근 경기 요약/팀 집계가 잘못된 평균을 만들지 않는지 검증 후 main PR을 진행한다. 이 이행 전 자동 main merge/배포 대상으로 취급하지 않는다.
