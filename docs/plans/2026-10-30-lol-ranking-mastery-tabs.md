# LoL 랭킹·장인 탭 설계 (2026-10-30, D안 반영 2026-10-31)

범위: 랭킹(명단 순위)과 장인(챔피언별 시즌 판수 명단)의 데이터, 정책, 저장, 수집, 보관, 화면 기준. 운영 절차는 [운영 절차](../operations/2026-10-30-lol-ranking-masters.md)에 둔다.

표기: **확정**(코드, 운영 DB, 공식 문서, 실측 확인), **추정**(간접 근거 또는 계산 가정), **미확인**(구현 전 또는 운영 중 확인).

## 1. 결론

1. **랭킹을 먼저 낸다.** 공식 명단 순서를 그대로 보여 준다. 자체 점수나 보정은 없다.
2. **장인은 D안이다.** 이번 시즌 솔로 랭크에서 챔피언을 15판 이상 했고 승률이 50% 이상인 명단 대상자만 올린다. 정렬은 판수 내림차순이다. 숙련도 포인트 기준은 쓰지 않는다.
3. **판수는 시즌 누적으로 쌓는다.** 대상 계정의 챔피언별 판수와 승수만 저장한다. 경기 원문과 다른 참가자 정보는 저장하지 않는다.
4. **게시본에는 키가 없다.** 공개 게시본은 Riot ID, 티어, LP, 챔피언, 판수, 승수만 가진다. PUUID 원문과 HMAC 모두 넣지 않는다.
5. **수집은 짧은 주기로 이어받는다.** 3시간마다 실행하고, 한 번에 호출 상한만큼만 처리한 뒤 커서를 저장하고 끝난다. 개발 키는 24시간마다 만료되므로 운영 수집에 쓸 수 없다.
6. **수집된 판수는 시즌 전체 판수가 아닐 수 있다.** 실측에서 일부 계정의 경기 목록이 시즌 승패 합보다 짧았다(§4). 화면과 방침에 "수집된 판수"로 적는다.

## 2. 정책 근거

| 항목 | 판정 | 근거 |
| --- | --- | --- |
| 공식 순위표 표시 | 허용 범주(추정, 강함) | [LoL 문서](https://developer.riotgames.com/docs/lol) 승인 사용 사례 "Official Ladder Leaderboards."(개인 키 예시 목록에 있음. 프로덕션 범위로 확인된 것은 아님) |
| 자체 실력 순위·MMR·ELO | 금지(확정) | [일반 정책](https://developer.riotgames.com/policies/general): "Products cannot create alternatives for official skill ranking systems such as the ranked ladder.", "Prohibited alternatives include MMR or ELO calculators." |
| 숨겨진 플레이어 | 금지(확정) | "Products cannot identify or analyze players who are deliberately hidden by the game.", "Products cannot de-anonymize players who cannot reasonably be identified from visible information." |
| 장인 D안(판수 15 이상, 승률 50% 이상, 판수 정렬) | **회색 지대(미확인)** | Riot 문서에 판수 기반 챔피언 순위나 승률 기준 조항이 없다. 금지도 허용도 확인되지 않았다. 승률 조건이 "실력 대체 순위"로 읽힐 가능성을 배제할 수 없다. 정렬 키는 판수이고 승률은 자격 조건으로만 쓴다. |
| 다른 사이트가 같은 기능을 쓴다는 사실 | **허용 근거로 쓰지 않는다** | 다른 서비스의 운영 여부는 Riot 허용을 보여 주지 않는다. |
| 증강·아레나 승률 | 금지(신청 문구 기준) | 신청 문구에 명시된 범위를 지킨다. |

정책 답변 전에 공개할 때의 위험: 장인 목록이 "실력 순위"로 해석되면 금지 조항에 걸릴 수 있다. 완화책은 다음과 같다. 정렬 키를 판수로 두고, 승률은 자격 조건으로만 쓰며, 화면에 "자체 계산 값이 아닙니다"와 수집 범위를 고정 표시한다. Riot 답변에 따라 탭을 끌 수 있도록 `LOL_MASTERS_PUBLIC` 플래그를 둔다.

신청서는 수정 전 원문을 그대로 두고, 공개 전에 §11-2 문구로 맞춘다.

## 3. 탭 정의

### 랭킹 (`/lol/kr/ladder`)

- 메뉴 이름은 "랭킹"이다. 첫 화면은 솔로 랭크 순위표이고, 아래에 기존 컷 그래프를 둔다.
- 대상은 솔로 챌린저·그랜드마스터 명단이다. 자유 랭크와 마스터는 2차다.
- 표시: 순위, Riot ID, 티어(엠블럼), LP, 승패. 행을 누르면 전적으로 이동한다.
- 순서는 공식 명단의 티어, LP 내림차순이다. 같은 LP는 Riot ID 순서다.
- 게시본이 없으면 "아직 집계되지 않았습니다"만 보이고, 컷 기록은 그대로 나온다.

### 장인 (`/lol/kr/masters`, D안, `LOL_MASTERS_PUBLIC=true`일 때만 공개)

- 챔피언을 고르면 그 챔피언의 명단을 보여 준다.
- **자격**: 이번 시즌 솔로 랭크에서 그 챔피언 판수 15 이상, 승률 50% 이상.
- **정렬**: 판수 내림차순. 같으면 공식 티어(챌린저 우선), LP 내림차순. 그다음 Riot ID 순서.
- **표시 열**: 순위, 티어 엠블럼, Riot ID, LP, 판수, 승률 막대(승수와 패수 포함).
- **고정 표시**: 조건 "이번 시즌 솔로 랭크 15판 이상, 승률 50% 이상, 판수 많은 순, 챌린저·그랜드마스터 대상", 수집 범위(명단 N명 중 확인 비율 %), 기준 시각(KST), "수집된 경기 기준이며 시즌 전체 판수가 아닐 수 있습니다", 제외와 삭제 안내.
- 수집 진행률이 100% 미만이면 "수집 중, 판수가 실제보다 적을 수 있습니다"를 기준 시각과 함께 보인다.
- 자격자가 없으면 "조건을 만족한 플레이어가 아직 없습니다"로 안내한다. 표본 부족이라는 말은 쓰지 않는다.
- 금지 표현: "점수", "실력", "1등", "숙련도". 자체 점수, 평점, 가중치 합산, 승률 정렬을 만들지 않는다.
- 챔피언당 최대 50명까지 게시한다.

기각안:
- **숙련도 포인트 순(D안 이전 기준)**: 누적 플레이량이라 실력과 다르다. 판수 자격이 없어 신규 계정이 섞이는 문제가 있다. 숙련도 수집 호출도 없앴다. 실측 응답에는 판수가 없다.
- **승률 정렬 또는 평점 정렬**: 실력 순위로 읽힐 위험이 크다. 정렬 키로 쓰지 않는다.
- **최근 경기 집중도**: 인당 많은 경기 상세가 필요하다. 원문을 다루는 제약과 충돌한다.
- **BGMS 자체 장인 점수**: 금지 조항과 충돌한다.

## 4. 데이터와 호출량

### 확정(실측 2026-10-30, 유효한 키)

| 항목 | 값 |
| --- | --- |
| 챌린저·그랜드마스터 명단 | `/lol/league/v4/{tier}leagues/by-queue/RANKED_SOLO_5x5`. 최상위에 `queue`, `tier`, `entries`. entries 키는 `freshBlood, hotStreak, inactive, leaguePoints, losses, puuid, rank, veteran, wins`. `summonerId`, `summonerName`은 없다 |
| 인원 | 챌린저 300명, 그랜드마스터 700명. 마스터 10,000명은 상한과 같아 잘렸을 수 있다(미확인). 대상은 챌린저·그랜드마스터 1,000명 |
| 비활성 계정 | 챌린저 `inactive` 0명. 같은 LP가 70건 있어 동순위 정렬이 필요하다 |
| Riot ID | `/riot/account/v1/accounts/by-puuid/{puuid}`(asia): `gameName, puuid, tagLine` |
| 개발 키 한도 | 100회/2분, 20회/1초. 개발 키는 24시간마다 만료된다 |
| 경기 목록 | `/lol/match/v5/matches/by-puuid/{puuid}/ids`(asia). 판 목록은 최신순이다 |
| 경기 목록 누락 | 실측 5계정 중 2계정은 시즌 승패 합(594, 505)보다 목록이 짧았다(452, 213). 목록 끝은 2026-01-26과 2026-06-13이었다. 원인은 **미확인**이다. 판수는 "수집된 판수"로 표현한다 |

### 비활성 계정 처리 규칙

공식 명단에 있는 계정은 `inactive`와 무관하게 순서를 바꾸지 않는다. 표시도 하지 않는다. 명단이 공식 순서의 근거이므로 BGMS가 임의로 빼지 않는다. 장인 자격은 판수와 승률로만 정하며 `inactive`를 보지 않는다.

### 시즌 시작과 종료

- 운영 기본값 후보: `LOL_SEASON_START=2026-01-08T00:00:00+09:00`(**추정**). 근거는 Riot 패치 일정의 26.01 시작일(2026-01-08, 태평양 시간)과 실측이다. 명단 승패 합으로 거슬러 올라간 3계정의 경계가 모두 이 날짜를 포함했다. 1계정의 구간은 2025-12-29부터 2026-01-20까지였다. 4월과 8월 초기화와는 맞지 않았다. 공식 문구로 확정된 값은 아니다.
- 코드에 하드코딩하지 않는다. 설정값으로만 받는다.
- `LOL_SEASON_END`는 쓰기 실행에 필수다. 종료 후 30일에 작업 데이터를 지우기 때문이다.

### 호출량 (1,000명 기준, 추정 포함)

가정:
- 명단 2회(챌린저, 그랜드마스터).
- Riot ID는 7일 동안 캐시한다. 신규와 이름 변경 계정은 매번 다시 부른다(추정 10%).
- 계정 확인 주기는 12시간(`LOL_RANKING_CHECK_HOURS`). 확인 때마다 경기 목록 1회를 받는다.
- 계정당 하루 새 경기는 3판으로 가정한다(**추정**, 실측 없음).
- 경기 상세는 대상 계정이 공유해도 한 실행에서 한 번만 받는다. 샘플 비율 9%(1,000/11,000)에서 공유는 작다(추정).
- 시즌 처음 백필: 계정당 시즌 판수 평균 500판으로 가정한다. 실측 승패 합 594와 505에서 추정(**추정**). 전체 백필 약 500,000 상세 호출(추정).

| 구간 | 호출 | 근거 |
| --- | --- | --- |
| 명단 | 2회/실행 | 실측 |
| Riot ID | 1,000회 최초, 이후 약 150회/주 | 7일 캐시 |
| 경기 목록 | 약 2,000회/일 | 12시간 주기, 1,000명 (추정) |
| 경기 상세(일상) | 약 3,000회/일 | 계정당 3판 (추정) |
| 일상 합계 | 약 5,000회/일 | (추정) |
| 시즌 백필 | 약 500,000회 | 계정당 500판 (추정) |

- 프로덕션 background 한도는 30,000회/10분의 50%(15,000회/10분)다. 일상 합계는 여유가 크다. 백필은 약 5.6시간의 최대 background 예산에 해당한다(추정).
- **현재 구현은 순차 호출이다.** 호출 한 번이 약 0.3초(추정)라면 40분 워크플로에서 실행당 약 7,000회다. 백필은 실행 수십 회, 약 9일이 걸린다(추정). 병렬화는 후속 과제다(미구현).
- 개발 키(100회/2분)는 한 실행의 상한을 줄여도 일상 수집을 맡을 수 없다. 개발 키 실측은 가능할 때 한 번만 한다.

## 5. 저장 계약 (migration `20261031030000_lol_ranking_publication.sql`)

공개 게시본과 작업 데이터는 분리한다. 모든 표는 RLS를 켜고 anon, authenticated 권한을 회수하며 service_role 전용이다. 함수는 security invoker, `search_path=''`다.

| 표 | 역할 | 키 |
| --- | --- | --- |
| `lol_ranking_publication` | 명단 게시본(Riot ID, 티어, LP, 승패) | `board` |
| `lol_master_publication` | 장인 게시본(챔피언별 자격자 상위 50명, 수집 범위, 시즌) | `champion_id` |
| `lol_ranking_exclusions` | 삭제 요청 Riot ID의 HMAC | `riot_id_hmac` |
| `lol_ranking_season_accounts` | 시즌 작업 계정(PUUID의 HMAC, Riot ID HMAC, Riot ID, 티어, LP, 커서, 확인 시각, 시즌 종료 시각) | `(season_key, account_hmac)` |
| `lol_ranking_season_champions` | 계정별 챔피언 판수와 승수 | `(season_key, account_hmac, champion_id)` |

- 계정 키는 `HMAC(서버 비밀, "puuid:" + PUUID)`이다. PUUID 원문은 저장하지 않는다.
- 커서는 마지막으로 처리한 경기 시각과 같은 시각의 경기 ID 목록이다.
- 시즌 키는 `LOL_SEASON_START`를 KST 날짜로 바꾼 값이다. 시즌이 바뀌면 다른 행이 되므로 섞이지 않는다.
- 수집 결과 반영 함수는 읽은 커서와 현재 커서가 같을 때만 판수를 더한다. 다르면 40001로 거절해 이중 집계를 막는다.

RPC 요약: 명단 게시, 장인 게시, 게시본 읽기, 제외 등록(제외 키, 시즌 계정 행 삭제, 명단과 장인 게시본에서 제거와 순위 재정렬), 계정 상태 읽기, 계정 등록, 커서와 판수 반영, 장인용 판수 읽기, 종료 후 30일 정리.

## 6. 수집기

- `scripts/lol_ranking_snapshot.ts`. 기본은 dry-run이다. `--apply`는 `LOL_RANKING_ENABLED=true`, `LOL_SEASON_START`, `LOL_SEASON_END`, 32자 이상 `LOL_RANKING_HMAC_KEY`가 있을 때만 쓴다.
- 한 실행의 순서: 명단 2회 → Riot ID 해석(캐시 우선) → 확인 주기가 지난 계정의 경기 목록 → 경기 상세(같은 실행에서 한 번만) → 계정별 커서 반영 → 명단과 장인 게시.
- **호출 상한**: `LOL_RANKING_MAX_CALLS`(기본 600). 상한에 닿으면 저장된 커서로 멈추고 정상 종료한다. 다음 실행이 빠진 경기부터 이어받는다.
- **중간 실패**: 계정 단위로 커서를 저장하므로 실패해도 처리된 범위는 유지된다. 커서가 바뀌었으면 그 계정은 건너뛴다.
- **429와 congested**: 기존 재시도 방식을 쓴다(1, 2, 4초 뒤 재시도). 그래도 실패하면 해석 실패나 누락으로 센다.
- **401과 403**: 키 오류로 판단하고 실행을 멈춘다. 명단을 게시하지 않는다. 저장된 커서는 그대로 두고, 운영자가 키를 바꾼 뒤 다시 실행하면 이어받는다(운영 문서 참고).
- **명단 게시 조건**: Riot ID 해석률(제외된 계정 포함)이 95% 이상일 때만 명단을 바꾼다. 못 넘으면 이전 명단을 유지하고 경고를 남긴다.
- **장인 게시**: 매 실행 현재 누적으로 다시 만든다. 명단에서 빠진 계정은 게시에서 뺀다. 수집 범위(확인 비율)를 함께 저장한다.
- 제외 목록은 게시 직전과 Riot ID 해석 시점에 대조한다.

## 7. 조회와 캐시

- 공개 페이지는 `unstable_cache` 1시간으로 게시본을 읽는다. 수집기는 Next 밖에서 돌아 태그를 비울 수 없으므로 시간 기준이다.
- 게시본 크기는 UTF-8 2MB 미만이다. 장인은 챔피언마다 최대 50행이다.
- 수집 실패 때는 마지막 게시본과 기준 시각(KST)을 보여 준다.

## 11. 개인정보처리방침과 신청서 문구 초안

### 11-1. 방침 초안(공개 전 반영, 실제 `/privacy` 파일은 고치지 않음)

처리 항목 표에 추가할 행:

| 항목 | 보유 기간 |
| --- | --- |
| LoL 랭킹·장인 공개 목록(Riot ID, 티어, LP, 승패, 챔피언별 판수와 승수) | 다음 집계 때 교체. 명단에서 빠지면 다음 집계에서 제외. 삭제 요청 시 즉시 제외 |
| LoL 장인 집계 작업 데이터(PUUID에서 서버 비밀 키로 만든 해시값, 챔피언별 판수·승수) | 해당 시즌 종료 후 30일에 삭제. 삭제 요청 시 함께 삭제 |
| LoL 삭제 요청 제외 목록(Riot ID에서 서버 비밀 키로 만든 해시값) | 서비스 운영 기간 보관(다시 수집되지 않게 하기 위함) |

처리 목적과 절차에 추가할 문장:

> LoL 랭킹과 장인 화면은 Riot 공식 챌린저·그랜드마스터 명단에 있는 소환사의 Riot ID, 티어, LP, 승패를 보여 줍니다. 장인은 이번 시즌 솔로 랭크에서 챔피언을 15판 이상 하고 승률이 50% 이상인 소환사를 판수 순으로 보여 줍니다. 판수는 수집된 경기 기준이며 시즌 전체 판수가 아닐 수 있습니다. 판수를 세기 위해 경기 결과에서 대상 소환사의 챔피언과 승패만 사용하며, 경기 내용과 다른 참가자의 정보는 저장하지 않습니다. PUUID 원문은 저장하지 않고, 서버 비밀 키로 만든 해시값만 저장합니다. Riot ID 삭제를 요청하면 즉시 공개 목록에서 제외하고 작업 데이터를 지우며, 제외 목록의 해시값을 보관해 다시 수집하지 않습니다. Riot ID를 변경한 경우 새 Riot ID로 다시 요청해 주세요.

### 11-2. 신청서 제품 설명 초안(수정 전 원문 파일은 고치지 않음)

> We also display an ordering of Challenger and Grandmaster solo queue players from the official ladder (Riot ID, tier and LP). For each champion we show players with at least 15 solo ranked games in the current season and a win rate of at least 50%, ordered by number of games. We do not compute a score, rating or weighting, and we do not order by win rate. To count games we read only the player's own participant entry (champion and win/loss) from ranked solo matches and keep per-champion game and win counts; we do not store match contents or other participants. We store a keyed hash of the PUUID, not the PUUID itself. Players can request removal of their Riot ID, which removes them from these boards and deletes their working data.

확인할 것: 이 설명은 Riot의 프로덕션 범위 확인을 받은 문구가 아니다. 신청 전 Riot 문구를 다시 확인한다. 승률 조건의 허용 여부는 확인되지 않았다.
