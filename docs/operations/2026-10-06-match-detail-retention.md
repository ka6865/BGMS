# 경기 상세 자료 14일 보관과 장기 성과 보존

## 사용자 동작

- 경기 시작 시각(`played_at`/검증된 공식 `createdAt`)에서 정확히 14일이 지나면 개인 경기 상세, 이동 경로, 사건별 분석과 새 개인 AI 분석을 제공하지 않는다. 객체 업로드 시각으로 기간을 연장하지 않는다.
- 만료된 상세 요청은 `410 PUBG_MATCH_DETAIL_EXPIRED`, `retryable: false`, `Cache-Control: no-store`를 반환한다. 화면에는 보관 기간 안내를 보여주며 자동 재시도하지 않는다.
- 기간 내 자료 부재는 `404 PUBG_MATCH_DETAIL_UNAVAILABLE`, DB 장애는 503으로 구분한다. 비공개 계정의 기존 접근 제한은 만료 확인보다 먼저 적용한다.
- 기본 전적, 저장된 성과와 점수·배지·무기 집계는 계속 조회한다. 스쿼드 집계는 유지하되 만료된 경기의 원인 장면은 제외한다.
- 새 AI 종합 요약은 기간 내 경기만 선택하고 캐시 식별에도 해당 경기만 포함한다. 전부 만료된 요청과 만료 경기를 포함한 새 스쿼드 AI 코칭 요청은 만료 응답을 반환한다.
- 과거 계산 버전의 성과는 당시 기록임을 표시하고 현재 랭킹에 섞지 않는다. 계산하지 못한 값은 임의의 0이나 새 점수로 대체하지 않는다.

## 보존하는 DB 자료

`pubg_player_matches`에는 계정·플랫폼·경기 ID, 실제 경기 시각, 맵·유형, 킬·피해량·순위를 유지한다. 기존 계정 결합이 없는 legacy 행은 공식 확인 없이 다른 계정에 일괄 결합하지 않는다.

`pubg_match_performance`는 계정·경기·계산 버전별 성과 요약을 최대 32 KiB로 저장한다. 점수는 측정되었을 때만 저장하고, 배지와 개인 무기·지원·교전 집계를 보존한다. 원본 이벤트, 이동 경로, 타 계정의 사건별 목록은 넣지 않는다. `played_at`, `summary_version`, 정렬된 원본 결과의 SHA-256 `source_checksum`을 함께 저장한다.

일괄 보존 작업은 신규 행만 추가하고 기존 행에서는 누락된 요약·경기 시각·체크섬만 조건부로 채운다. 기존 점수·티어·benchmark·랭킹 자격과 동시 계산으로 완성된 요약은 덮어쓰지 않는다. 조회에서도 측정된 DB benchmark를 우선해, 원본 요약에 점수가 빠졌다고 기존 점수가 화면에서 사라지지 않게 한다.

일반 상세 계산과 백그라운드 성과 worker가 이 요약을 저장한다. 랭킹 대상이 아닌 유효한 경기의 측정 성과도 보존한다. 일일 작업은 기존 `processed_match_telemetry`에서 아직 보존하지 않은 결과를 서버에서 골라 최대 1,000건씩 옮기고 저장 후 다시 확인한다. 전체 보존 조회는 정리 cursor 다음 100개 기본 행에 해당하는 경기·플랫폼을 먼저 골라 그 분석 원본만 읽는다. 무거운 JSON을 전체 저장소에서 펼치는 조회를 피하고, cursor 이동은 정리 적용 단계에서만 수행한다. 닉네임을 지정한 검증은 기존 범위를 유지한다. 기본 전적과 성과는 기존 90일 작업에서 삭제하지 않으며 핵심 DB 백업 대상에 포함한다.

## R2 정리의 조건

일반 저장소 삭제 도구의 공통 원본·백업·이미지 보호 규칙은 유지한다. 기간 정리는 별도 실행 경로에서 해당 경기와 정확히 일치하는 원본·개인 지도·개인 분석 객체만 다룬다.

삭제 전에 모든 알려진 계정 참조의 기본 전적과 작은 성과 요약을 확인한다. 원본 결과가 남아 있으면 요약의 체크섬도 대조한다. 경기 날짜·계정 결합이 불명확하거나 성과가 아직 보존되지 않았거나 수집/계산/지도 작업이 진행 중이면 원본을 보호한다. 이런 예외는 상세 제공 기간을 늘리지는 않지만 물리적 삭제를 늦출 수 있다.

자동 작업은 매시간 8·23·38·53분에 예약한다. 실행당 기본 전적 행을 최대 1,000개 읽어 120초까지 검사하고 검증된 객체를 최대 50개·합계 32MiB까지 정리한다. 예약 지연에 따라 실제 처리량은 달라진다. 한 경기의 객체가 수량·용량 상한에 걸리면 cursor를 그 경기 앞에 유지하고 다음 실행에서 남은 자료를 처리한다. `pubg_archive_cleanup_cursor`에 마지막 경기와 세대를 기록해 보호 중인 오래된 경기나 이미 정리된 경기 때문에 다음 대상이 영구히 막히지 않도록 한다. 한 바퀴를 마치면 다시 시작해 그동안 보존이 완료된 자료를 재검토한다. 이 진행 상태는 service role만 읽고 갱신할 수 있으며 조사만 수행할 때는 이동하지 않는다.

실행 순서는 대상 조사·성과 보존 확인 → 암호화 백업 → 백업 업로드 확인 → DB/객체 재검증 → 소량 삭제 → 부재 확인이다. 백업은 원본 R2에 다시 복제하지 않고 임시 GitHub Actions artifact로 보관해 순절감량을 확인한다. 적용 중 객체 내용이나 참조가 달라지면 중단한다. 상세 자료를 삭제해도 기본 전적과 성과 행을 삭제하지 않는다.

`match_master_telemetry`는 `platform` 열 없이 경기 ID를 키로 쓰는 기존 공통 테이블이다. 포인터 조회는 경기 ID로 수행하고, 정리·복구는 검증한 정확한 R2 경로 또는 null 상태에 대한 조건부 갱신만 수행한다. Actions는 명시적 `bash` 셸의 `pipefail`로 조사·삭제 오류가 `tee` 뒤에서 성공으로 표시되지 않게 한다.

현재 R2 경로에서 조건부 DELETE는 검증되지 않았다. 만료 자료의 일반 쓰기를 차단하고 작업 lease와 바로 앞 GET의 ETag·크기·SHA-256을 재검증하지만 GET과 DELETE 사이의 매우 짧은 변경 가능성을 완전한 원자성으로 설명하지 않는다. 복구는 조건부 PUT과 읽기 확인을 사용해 동시 변경을 덮어쓰지 않는다.

## 자동 성과 보완과 보호

구형 분석 목록은 경기별 root prefix에서 최대 100개만 읽으며 조회가 잘리면 사유를 기록한다. 목록에 삭제 가능한 구형 분석이 있으면 같은 경기의 남은 사본을 이어서 처리한다. 보호 대상만 앞에 보이는 잘린 목록은 다음 경기로 이동하고 다음 순회에서 다시 확인한다. 목록 밖 자료가 모두 정리되었다고 집계하지 않는다.

준비 단계의 `--preserve-performance`는 검사한 경기의 유효한 기존 DB 분석을 보존한다. 전역 RPC의 100행 범위 밖에 있는 경기에도 이 보존 단계를 적용한다. 구형 기본 전적의 계정이 비어 있어도 기존 분석의 명시된 플랫폼·경기 ID·닉네임과 공식 `stats.playerId`, 경기 날짜·모드·맵·킬·피해량·순위가 모두 일치하면 기존 계정 대조 계약으로 연결할 수 있다. 닉네임만 같은 결과, 누락되거나 충돌하는 계정·날짜·관측값은 이 근거로 사용하지 않는다. 같은 경기의 서로 다른 닉네임을 하나의 계정에 연결하지 않는다.

`bind_retention_legacy_accounts`는 service role만 실행하는 `SECURITY INVOKER` RPC다. 최대 40행씩 기본 전적과 분석의 전체 스냅샷을 잠그고 재검증해 NULL 계정만 일괄 연결한다. 동시 입력에 의한 계정 충돌도 짧은 테이블 잠금으로 제외하며, 잠금 대기는 2초를 넘기지 않는다. 하나라도 달라지면 해당 묶음 전체를 취소한다. 기본 경기 종류가 `unknown`/`unavailable`이면 같은 분석의 명시적인 유효 `matchType`으로만 보완한다. 보조 `matchInfo.matchType`이 있으면 동일한 문자열이어야 하며, 누락·충돌 시 보호한다. 이미 유효한 경기 종류와 킬·피해량·순위·날짜·맵·모드는 바꾸지 않는다. 반환한 기본 전적에서 계정과 검증한 누락 경기 종류 이외의 값이 바뀌지 않았는지 확인한 뒤 기존 성과를 보존하고, 삭제 준비는 DB 전체 참조를 다시 읽어 판단한다. 기본 전적의 관측값과 기존 분석은 삭제하거나 덮어쓰지 않는다.

기존 DB 증거만으로 연결·성과 복사가 되는 경기는 새 공통 원본을 요구하지 않는다. 이 근거가 없거나 분석 결과가 없는 경우에는 검증된 공통 `telemetry-source`를 읽는다. 공식 participant의 계정·당시 닉네임, 경기 날짜·모드·맵·킬·피해량·순위, 실제 account 이벤트 증거가 일치해야 계정을 조건부로 연결한다.

공통 원본의 checksum과 플랫폼·경기 ID를 검증하고 시작·종료 이벤트가 각각 하나이며 시작이 공식 경기 시각의 60초 이내, 종료가 시작 뒤이고 공식 duration+300초 이내인 경우에만 누락 성과를 복구한다. 기존 projection은 `LogMatchDefinition`을 보관하지 않으므로 공식 metadata와 이벤트 시각을 함께 대조한다. 개인 지도만 있거나 다른 DB 증거 없이 이벤트만 있는 구형 분석 파일은 이 복구 증거를 대신하지 못한다. 기존 fullResult가 불완전하거나 다른 측정값을 가진 경우에는 덮어쓰지 않고 보호한다.

복구 계산은 실행당 최대 5개 성과로 제한하고, 비교 표본이 없는 점수와 현재 랭킹 자격은 만들지 않는다. 보존 함수는 기존 측정 점수·티어·benchmark·완성된 요약을 유지하며 실제 DB를 다시 읽어 계정·경기·날짜·요약·checksum을 확인한다. 저장·조회 실패는 삭제 준비를 중단한다. 복구 가능한 원본이 없는 자료는 보호 사유를 남기고 다음 경기를 검사한다. `--preserve-performance`는 백업 준비 단계에서만 사용할 수 있으며 dry-run과 삭제 직전 재검증에서는 쓰지 않는다.

전역 정리는 `list_retention_archive_candidates`로 R2 지도 등록부 또는 기존 분석이 있는 만료 기본 전적을 우선 읽는다. JSON 분석 본문을 후보 목록 전체에서 읽지 않고, 선택한 경기만 후속 검증한다. 동일한 날짜·플랫폼·경기 ID cursor와 최대 1000행·120초 검사 상한을 유지한다. 등록부와 분석 모두 없는 자료는 이 우선 처리 범위 밖에 있으며 R2 전체 재고조사를 대체하지 않는다. Actions 결과의 `preservation`에는 실제 계정 연결·저장 확인된 요약·공통 원본 재계산 수를 각각 기록한다. 조사 모드는 계정·성과·cursor를 갱신하지 않는다.

## 운영 검증

`20261006193137_retention_legacy_account_binding`는 구형 계정 연결과 자료가 있는 경기 우선 조회 RPC를 추가한다. 기존 테이블·기본 전적·성과·분석은 삭제하지 않고, 공개 역할의 실행 권한을 주지 않는다. 격리 PostgreSQL 검증 뒤 운영에 적용했으며, 운영 DB 버전 17.6에서 사용하는 입력 검증 함수의 제공 여부도 확인했다. 운영 계정 연결·성과 보존·R2 정리의 실제 결과는 각 실행 기록으로 별도 남긴다.

운영 DB에는 `20261005193048_pubg_long_term_match_performance`와 `20261006115638_pubg_archive_cleanup_cursor`가 적용되어 있다. 저장소 파일과 검증 스크립트도 실제 적용 버전에 맞춰, 후속 배포에서 같은 SQL을 다시 적용하지 않게 한다. 두 migration은 격리 검증 후 적용했으며 기본 전적이나 분석 데이터를 삭제하지 않았다. 전역 성과 보존 조회의 8초 제한 오류를 확인해 `20261006130700_bounded_unretained_match_performance`로 기존 함수의 읽기 범위만 줄였다. 실제 서비스 키로 40건의 보존 후보를 586ms에 읽고 요약했으며 이 검사는 쓰기 없이 수행했다.

2026-10-06 KST 검증에서 최근 공식 경기 목록 43건씩을 두 테스트 계정의 기본 전적과 대조했다. 누락된 기본 경기 4건과 11건을 범위 제한 수집으로 보완해 전체 전적은 각각 206→210건, 196→207건이 되었다. 기존 개인 분석에서 유효한 성과 요약 114건과 59건을 먼저 저장하고 다시 확인했으며 기본 전적은 보존했다. 검증되지 않은 원본 1건은 삭제 근거에서 제외했다.

## 보호 대상의 읽기 전용 원본 조사

수동 Actions의 `inspect-recovery` 모드는 명시한 플랫폼·경기 ID를 최대 30경기만 대조한다. 해당 경기의 DB 참조와 공통 원본·개인 지도·구형 분석 객체를 읽고, 객체별 크기·ETag·SHA-256과 실제 본문을 암호화 artifact에 7일 보관한다. 경기당 최대 8개 객체, 원본 합계 64MiB의 상한과 목록 잘림·누락·읽기 실패를 기록한다. 이 모드는 DB 계정·성과·cursor를 갱신하거나 R2 자료를 삭제하지 않는다. 평문 원본과 개인 식별자는 Actions 로그에 출력하지 않으며, 조사 자료의 존재만으로 삭제나 복구 성공을 판정하지 않는다.

읽기 전용 원본 조사는 기본 전적의 계정 결합이 없어도 등록부의 명시적 유효 계정과 정확한 경기·플랫폼·모드·버전 경로를 검증하면 그 객체를 읽을 수 있다. 이 조사 권한은 DB 계정 결합이나 삭제 근거를 대신하지 않는다. 용량·시간·행 수 상한 실패는 개인 정보가 없는 고정 사유 코드로 기록하고 더 작은 묶음으로 재시도한다.

## 같은 팀의 공식 기록으로 누락 성과 복구

공통 원본이 없는 만료 경기라도, A의 기존 개인 분석에 B의 공식 팀 기록이 남아 있으면 제한적으로 복구할 수 있다. 같은 경기·플랫폼의 정확한 구형 키와 객체 SHA-256, A의 전체 DB 스냅샷·계정·공식 관측값, B의 공식 닉네임·계정·킬·피해량·순위·생존시간, 이벤트의 경기 시작·종료와 실제 같은 팀 계정들을 대조한다. 경기 종료 참가자 목록과 생성 이벤트의 계정·닉네임·팀 구성을 대조한 전체 인원·팀 수가 공식 값과 일치하지 않거나 공식 개인 기록·해시가 없으면 보호한다. 기본 전적과 루트의 실제 맵을 기준으로 검증하며, 구형 화면용 `erangel` 기본값을 다른 맵의 공식 증거로 사용하지 않는다.

이 경로는 기존 개인 분석과 성과를 덮어쓰지 않는다. 계정이 비어 있고 관측한 값이 일치하는 기본 행만 연결한다. NULL 계정의 0킬·0피해·99위 임시 기록은 공식 개인 값으로 보완할 수 있으며, 날짜·맵·모드까지 보완하는 경우에는 맵·모드가 모두 `unknown`인 전체 임시 기록이어야 하며, 이미 알려진 경기 종류는 공식 유형과 일치하고 그대로 유지해야 한다. 알려진 관측값이 충돌하면 복구하지 않는다.

`recover_retention_legacy_team`은 service role 전용 `SECURITY INVOKER` RPC다. 잠금을 기다리지 않는 `NOWAIT`와 잠금 후 1초 작업 예산, 전체 스냅샷 비교로 기본 행 보완과 작은 성과 요약 추가를 한 트랜잭션으로 처리한다. 기존 분석, 이미 있는 개인 성과, 계정 충돌, 활성 lease가 있으면 취소한다. 생성한 개인 분석 전체는 DB에 새로 적재하지 않고 요약과 작은 복구 근거만 남긴다. 저장 후 기본 행과 성과의 실제 본문을 다시 읽어 확인하며, 실패하면 삭제 준비를 멈춘다.

공식 개인 기록의 실제 0은 유지한다. 부분 이벤트에서 측정 근거 없는 기본값 0과 false는 누락값으로 보존하고, 전체 피해량 순위·비교 점수·현재 랭킹 자격·배지는 생성하지 않는다. 요약에는 `performanceHistorical: true`와 `partial-legacy-team-events`를 기록한다. 대상 구형 파일은 경기당 최대 3개·각 8MiB, 실행 전체의 해제 본문은 최대 32MiB, 재계산 시도는 기존 복구와 합쳐 최대 5회로 제한한다. 목록·파일·계산 상한 밖의 자료는 해당 실행에서 복구하거나 삭제하지 않는다. dry-run은 이 쓰기 경로를 실행하지 않는다.

`20261006223434_legacy_team_retention_recovery`는 격리 PostgreSQL의 권한·전체 스냅샷 변경·기간 내 경기·기존 개인 분석·계정 충돌·다른 참조 계정의 lease/재시도 작업 거부와 실제 운영형 22개 입력의 저장·재조회를 검증한 뒤 운영에 적용했다. 첫 1건을 적용해 실제 기본 전적·성과 요약 200 및 만료 상세 410을 확인했고, 기존 개인 분석 추가와 랭킹 자격 생성은 없었다. 후속 소량 적용과 원본 정리 결과는 실제 실행 기록으로 별도 남긴다.

## 개인 분석 없이 지도만 남은 경기의 부분 성과 보존

구형 `full` 지도에 계정의 공개 해시와 당시 닉네임이 양방향으로 하나씩 대응하고, 경기 시각·맵·킬 수·피해량이 기존 기본 전적과 일치하면 `--preserve-performance` 준비 단계에서 NULL 계정을 연결할 수 있다. 같은 경기의 준비된 지도 등록부가 하나이고 정확한 계정·플랫폼·버전 경로와 실제 본문이 일치해야 한다. 원본은 재확보하지 않으며 읽은 파일의 ETag·SHA-256·크기를 보존 근거에 기록한다.

기본 전적의 순위·경기 유형·킬·피해량·시각·맵·모드는 바꾸지 않는다. 기존 기절·생존 시간이 있으면 요약에 그대로 보존하며, 없으면 공식 기록으로 채우지 않는다. 지도에 남은 기절·격발·소생 사건 수는 `replayObservedMetrics`에 따로 남긴다. 이 요약은 계산/결과 버전 0과 `performanceHistorical: true`, `partial-legacy-map-events`를 사용하고 점수·티어·benchmark·현재 랭킹 자격·배지는 생성하지 않는다.

`recover_retention_legacy_map`은 service role 전용 `SECURITY INVOKER` RPC다. 기본 행과 지도 등록부의 전체 스냅샷을 비교하고 활성 작업·lease·다른 계정 연결·기존 개인 분석·성과가 없음을 확인한 뒤 계정 연결과 작은 성과 저장을 원자 실행한다. 잠금은 `NOWAIT`로 거절하고 잠금 후 작업 예산은 1초다. 실제 DB 재조회가 맞아야 삭제 준비를 진행한다. 일반적인 미확인 경기 유형 허용으로 확대하지 않고 이 전용 보존 근거에만 예외를 적용한다.

이 부분 요약으로 삭제할 수 있는 것은 보존 근거의 경로·ETag·SHA-256·크기가 모두 같은 개인 지도 하나뿐이다. 다른 지도 사본·개인 분석·공통 원본에는 적용하지 않는다. 기존 암호화 백업 업로드·다운로드 대조, 현재 DB/객체 재검증과 삭제 후 부재 확인을 유지한다. `dry-run`은 쓰지 않으며 파일·본문·시도 예산은 앞선 복구와 공유한다. DB 기본 전적 자체가 없는 R2 객체는 별도 원본 재고 대조 대상이며 이 계약의 성공으로 복구됐다고 집계하지 않는다.

`20261007053338_legacy_map_retention_recovery`는 격리 DB의 권한·CAS·관측값 유지·누락 통계·활성 작업 거부 및 실제 운영형 입력의 원자 저장·재조회를 확인한 뒤 운영에 적용했다. 기본 전적 자체와 성과의 삭제는 포함하지 않는다. 이 검증에서 지도 등록부의 운영 `created_at` 필드가 일회용 DB fixture에 빠져 있던 점도 보완했다. 실제 R2 정리 수치는 해당 실행 결과에서 별도로 확인한다.

## 구형 사본 차이와 `matchInfo` 없는 분석의 보존

같은 경기의 구형 분석 사본이 여러 개면 각각 계정·공식 기본 통계·전체 팀과 참가자·경기 시작과 종료를 검증한다. 어느 사본이든 검증 실패하거나 계산 예산 안에서 전부 검사할 수 없으면 쓰지 않는다. 검증된 사본들의 개인 식별자·공식 통계·실제 경기 메타데이터가 같을 때만 개인 집계를 보존하며, 사본별로 다른 집계는 각 값만 `null`로 남긴다. 일치하는 값은 유지하고 검사한 사본의 키·SHA-256과 `common-observations-only` 정책을 작은 요약에 기록한다. 성과 요약은 합친 뒤에도 32KiB 상한을 지킨다.

현재 분석 형식처럼 `matchInfo` 필드 자체가 없으면 루트의 경기 시각·지도·모드·유형과 기본 전적을 대조하고, 유일한 `LogMatchStart`/`LogMatchEnd` 시각으로 관측 구간을 검증한다. 구간은 1초 이상 2시간 이하, 공식 경기 시각과 시작 차이는 최대 60초이며, 모든 공식 팀원의 생존 시간은 구간보다 최대 60초까지만 길 수 있다. 시작 이벤트에 지도 정보가 있으면 지도도 일치해야 한다. 관측 구간을 공식 경기 길이로 표시하지 않고 `verified-legacy-event-interval` 근거로 저장한다. 이미 존재하는 `matchInfo`가 불완전하거나 충돌하면 이 경로로 우회하지 않는다.

RPC도 이 구분과 시각·생존 시간 근거를 다시 검증하며 전체 스냅샷·활성 작업·계정 충돌·권한 조건을 유지한다. 기존 기본 전적과 개인 분석·성과를 덮어쓰거나 삭제하지 않는다. `20261007062957_legacy_team_retention_event_metadata`는 실제 운영형 입력 2건의 격리 DB 저장·재조회와 거부 조건을 검증한 뒤 운영에 적용했다. 실제 삭제 수치는 실행 기록으로 확인한다.

지도 등록부는 준비와 삭제 직전 재검증 모두 전체 필드를 읽는다. 준비에서만 `created_at`을 포함하면 동일한 자료도 증거 변경으로 오판할 수 있으므로, 삭제 실패 시 복원에 사용하는 스냅샷과도 읽기 범위를 일치시킨다. 실제 날짜·lease·상태·경로의 변경 거부는 유지한다.
