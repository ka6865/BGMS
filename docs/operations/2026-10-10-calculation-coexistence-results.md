# 기존 계산 보존과 신규 계산 적용 결과

사용자가 과거 계산 결과를 유지하고 앞으로 새로 분석하는 경기만 새 계산으로 추가하는 방향을 승인했다. 과거 경기 전체 재계산이나 버전 재라벨은 실행하지 않는다.

## 유저와 관리자에게 보이는 동작

- 기존 계산 2 전적·점수·랭킹은 계속 조회한다. 조회 때문에 기존 결과를 다시 계산하거나 덮어쓰지 않는다.
- 새 분석은 계산 3으로 저장하며, 미측정 고립을 캐리 승리 기여 가산 근거로 사용하지 않는다. 기본 점수·티어와 비교 지표 산식은 계산 2·3에서 동일하다.
- 서로 다른 버전의 캐리 점수는 각 경기의 저장 결과 그대로 표시한다. 기본 점수·티어·관측 지표는 기존 비교 표본과 신규 표본을 합쳐 사용할 수 있다.
- 랭킹은 DB에서 비공개 대상과 중복 경기를 제외하고 최신 지원 버전의 경기 점수를 선택한다. 같은 닉네임의 플랫폼과 안정 계정 identity를 유지한다.
- 단일 AI는 해당 경기의 실제 계산 버전으로 코칭 캐시를 조회한다. 최근 요약·스쿼드는 선택한 경기의 실제 버전을 해시에 포함한다. 단일 버전 요약은 기존 `calculationVersion` 형식을 유지하고 혼합 버전에만 `calculationVersions`를 사용한다. 실제 Gemini 호출 검증과는 구분한다.
- 자동 점수 작업은 이미 v2 성과·완료 작업·개인 분석·비교 표본이 있거나 v2 작업이 실행 중이면 v3 재계산을 만들지 않는다. 기존 완료 점수 없이 앞으로 처리하는 대상은 v3 작업으로 생성한다.
- 상세 제공 14일, 계정/플랫폼/경기 identity, 결과 73, 모집단 근거, 관리자 승인 및 저장 하향 보호는 유지한다.

## 검증

계산 공존 회귀 검사에서 기존 결과 불변, v2 조회와 v3 writer 구분, 미지원 버전 거부, 혼합 비교 표본의 관측 수 가중 평균, 실제 버전별 AI 캐시, 닉네임 변경 후 보존 성과 조회를 확인했다. API 검사에서 v2·v3 캐시 조회가 PUBG 호출이나 분석/저장으로 이어지지 않음을 확인했다.

- `verify:core`: 오류 0, 기존 경고 45.
- `test:unit`: 329개 파일, 3,982개 통과, 96개 제외.
- `verify:analysis`: 21개 파일, 663개 통과.
- `verify:admin`: 20개 파일, 420개 통과.
- `verify:migrations`: 격리 PostgreSQL에서 46개 migration과 RPC 시나리오 통과. 티어 비공개 별칭 제외와 피해량·킬의 미계산 경기 보존도 확인했다.
- `npm run build`: 자리표시자 인증 환경에서 통과. 실제 OAuth/DB/Gemini 검증을 뜻하지 않는다.

관리자 브라우저 5개와 고객센터·랭킹 접근성 브라우저 5개는 모바일 375×667·390×844·430×932 및 데스크톱에서 통과했다. 접근성 첫 실행은 앞선 테스트 서버의 dev lock 때문에 시작하지 못했으며, 소유 테스트 서버가 종료된 뒤 재실행해 통과했다.

Luna가 DB 경로와 API/AI 경로를 읽기 전용으로 검토했고 배포를 막는 문제는 발견하지 않았다. 실제 운영 API에서 발견한 티어 조회 시간 초과의 후속 SQL 변경은 별도로 리뷰한다.

## 운영 적용 경로

기존 main에서 적용된 migration 3개의 timestamp가 저장소 파일명과 달랐다. 운영 이력을 repair하거나 과거 SQL을 재실행하지 않는다. 격리한 임시 CLI 폴더에서 해당 파일명만 운영 이력과 맞췄고 dry-run 대상이 아래 신규 3개뿐임을 확인했다. 저장소와 운영의 기존 이력은 유지한다.

- `20261009182823_restore_player_cache_compaction_contract`
- `20261009213020_analysis_calculation_coexistence`
- `20261010000000_analysis_calculation_v3`

세 migration은 함수/권한을 변경하며 기존 업무 데이터에 일괄 UPDATE나 DELETE를 하지 않는다. 계산 v3의 재계산 RPC가 존재하더라도 이번 전환에서는 전체 재계산을 호출하지 않는다.

위 3개는 운영 적용을 완료했고 migration 이력을 재조회했다. 저장된 계산 2 점수 3건의 benchmark 해시와 버전은 적용 전후 동일했다. 함수 5개의 `SECURITY INVOKER`와 service role 전용 실행 권한도 확인했다. 메인 반영은 실제 티어 API 시간 초과 해결까지 보류했다.

전적 브라우저 검사의 기존 13개 실패는 앞선 동일 main 비교 결과와 별개로 유지한다. 실기기·실제 OAuth·실제 AI 호출은 미검증이다.

## 기존 운영 랭킹 시간 초과 점검

변경 전 운영 API에서 tier는 9.27초 후 HTTP 503, damage/kill은 각각 6.96/5.12초에 30행 HTTP 200이었다. 기존 GET 페이지의 HTTP 200과 API의 정상 응답을 구분한다.

읽기 전용 EXPLAIN에서 기존 SQL이 약 76,803개 후보마다 benchmark/보존 성과를 반복 조회하고 프라이버시를 검사하는 계획을 확인했다. 동일한 기간·모드·프라이버시 조건의 후보를 한 번 읽고 점수 소스를 집합으로 JOIN하도록 수정했다. 프라이버시 내부 계정 키의 platform은 이미 일치 조건이 있는 내부 테이블 값을 사용해 반복 외부 참조를 제거한다. 조회 조건과 권한은 유지하고 인덱스/업무 데이터를 변경하지 않는다.

운영 데이터에 대한 새 SQL의 읽기 전용 EXPLAIN ANALYZE는 30행을 5,439.75ms에 반환했다. 후보 CTE를 inline하는 대안은 6,994.827ms여서 채택하지 않았다. 이 측정은 빈 제외 배열의 단일 조회이며 실제 RPC/API·9개 비공개 설정·동시 부하 통과를 대신하지 않는다. 운영 함수 적용 후 실제 API를 추가 확인한다.

함수 적용 후 실제 API는 tier 503/8.85초, damage 200/30행/5.30초, kills 200/30행/3.23초였다. 실제 9개 비공개 설정의 12개 제외 키로 쿼리를 확인하니 주간 후보 123,380행을 읽는 데 약 6.19초가 들었고, 점수가 있는 경기는 1,310개였다. 비공개 조건을 변경하는 대안은 채택하지 않았다.

후속 `20261010001000_bound_tier_ranking_candidates`는 티어에 한해 점수 소스에서 경기 키를 먼저 찾는다. 피해량·킬은 점수가 없는 경기도 원래대로 포함하고, 날짜·모드·비공개·계정 identity·최신 버전 선택·중복 제거·TOP 30 조건을 유지한다. 동일한 실제 비공개 키와 계산 3 입력의 읽기 전용 EXPLAIN ANALYZE는 3,433.276ms에 30행을 반환했다. 이미 적용한 migration을 수정하지 않고 새 함수 정의 migration으로 추가하며 실제 API 확인은 적용 후 수행한다.
