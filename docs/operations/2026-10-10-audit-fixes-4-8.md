브랜치: `codex/fix-audit-4-8`. 기준 커밋은 앞선 1~3번 및 후속 수정이 들어 있는 `d34348f6`이다. 원래 작업 폴더의 미커밋 변경을 보존하고 별도 worktree에서 수정했다. Luna 서브에이전트 2명은 읽기 전용 조사와 코드 리뷰를 담당했고 부모가 코드·문서 수정과 검증을 수행했다.

코드 작성과 격리 검증을 완료한 결과다. 운영 migration 적용·서비스 배포·운영 데이터 재계산·삭제·실제 Gemini 호출은 수행하지 않았다.

이후 최신 main을 통합해 [1~8번 최종 배포 검토](2026-10-10-audit-final-release-review.md)를 수행했다. 운영의 계산 3 모집단이 비어 있어 전체 배포를 보류했다. 아래 구현 완료와 당시 검증 결과를 운영 배포 준비 완료로 해석하지 않는다.

4번은 Auth를 1,000명씩 최대 20페이지, profiles와 기간 내 analytics를 최대 10,000행 요청하는 기존 상한을 유지한다. profiles·analytics는 `count: "exact"`의 전체 건수와 실제 반환 행 수를 비교하므로 서버가 요청보다 적은 행을 반환해도 부분 집계를 감지한다. 총 건수를 받지 못한 경우도 부분 집계다. 부분 프로필에서 역할을 확인하지 못한 로그인 기록·회원 이벤트는 관리자 활동이 섞이지 않도록 제외한다. 이때 누락 프로필·고아 계정으로 단정하는 안내도 하지 않는다. 해당 정책은 `lib/admin-agent/user-metrics.ts`와 도구의 추천 문구에 반영했다.

5번은 기존 이벤트 허용 목록·배치 25개 제한·사용자 인증·관리자 이벤트 제외·수집 쿼터·저장 계약을 유지한다. 정상적인 빈 집계와 조회 실패는 구분하며, 정상 크기의 이벤트 수집 동작은 유지한다.

7번의 새 랭킹·PC 게시글 링크는 `prefetch={false}`로 설정했다. 게시글 상세의 서버 렌더링에서 조회수 RPC가 호출되므로, 목록에서 새 PC 링크가 보이는 것만으로 상세를 미리 조회하는 동작을 추가하지 않는다.

## 계산 버전 3과 운영 적용 조건

점수는 `lib/pubg-analysis/benchmarkScore.ts`, 저장 계약은 `ANALYSIS_CALCULATION_VERSION = 3`을 사용한다. 행동 근거 1개만 있는 우승 경기에서 무사망 근거가 없을 때, 미측정 고립을 잘못 근거로 더해 발생하던 +4 임팩트 가산을 재현하고 수정했다. 이 값이 모든 우승 경기의 점수를 일괄 4점 낮춘다는 뜻은 아니다.

- 단일 경기 AI 캐시는 계산 버전 3을 결합하고 스쿼드 캐시도 현재 계산 버전으로 구성한다.
- 최근 요약의 `precomputedVisuals.calculationVersion`을 상수로 바꿨다. 이 값은 기존 캐시 hash에 포함되어 이전 계산 입력의 요약과 구분된다.
- 기존 benchmark view는 계산 버전별로 집계한다. 조회와 랭킹도 현재 버전을 전달하므로 버전 2·3 전술 표본이 섞이지 않는다.
- 재계산 CLI의 고정 버전 2를 현재 상수로 연결했다. 이전 버전으로 저장한 inventory·plan·checkpoint는 새 계산 작업에 재사용하지 않는다.
- 새 migration은 `supabase/migrations/20261010000000_analysis_calculation_v3.sql`이다. 두 업그레이드 RPC와 recovery finalizer만 갱신하며 테이블·인덱스·RLS·권한·하향 방지 트리거는 유지한다. 기존 행을 버전 3으로 일괄 재라벨하지 않는다.
- 새 RPC는 기존 버전 2 입력을 계속 지원하고, 공식 원본에서 재계산한 legacy→3·2→3 입력도 허용한다. 기존 snapshot·계정·플랫폼·모집단 검증과 두 테이블의 원자적 갱신을 유지한다. 반복·동일·미래·하향 버전 요청은 성공으로 처리하지 않는다.

배포 준비는 다음 순서다.

1. 새 migration과 앞선 캐시 보존 보정 migration의 운영 적용 여부를 확인한다. 현재 점검은 운영 이력을 새로 조회하지 않았다.
2. 버전 2 바이너리와 호환되는 새 migration을 먼저 적용한다. 코드 배포만 하고 DB 함수를 예전 상태로 두면 버전 3 재계산이 거부된다.
3. 운영 재계산 대상과 원본 확보 가능 여부를 읽기 전용으로 확인하고, 새 output-dir에 별도 inventory를 만든다. 예: `npx tsx scripts/run_calculation_upgrade_rollout.ts --output-dir tmp/calculation-upgrade-v3`와 `--canonical-only --output-dir tmp/calculation-upgrade-canonical-v3`. 이 명령은 DB 조회와 로컬 파일 생성을 하며 운영 쓰기는 하지 않는다.
4. 별도로 승인된 운영 범위에서 작은 재계산 배치의 저장 후 재조회를 확인하고 적용 범위를 늘린다. `--apply`·원본 다운로드·운영 쓰기는 이번 코드 수정 허가에 포함해 실행하지 않았다. 기존 절차는 [계산 갱신 계획](../plans/2026-09-08-calculation-upgrade-rollout.md)을 참고하되 과거의 v2 경로와 운영 수치를 현재 값으로 복사하지 않는다.
5. 코드 배포 후 기본 전적·새 분석·랭킹·AI 캐시를 확인한다. 계산 버전 3 표본이 모이기 전에는 전술 비교가 보류될 수 있다.

기존 버전 2 분석은 현재 계산으로 인정되지 않으므로, 원본 재계산 전에는 기본 킬·피해량 기록을 유지하면서 기존 전술 분석·점수 랭킹·AI 생성이 보류될 수 있다. 원본을 확보할 수 없는 과거 경기에는 이 보류가 남을 수 있다. 전 경기 자동 재계산이나 Gemini 결과 일괄 재생성은 추가하지 않았다.

코드만 버전 2로 되돌리면 새 버전 3 행을 이전 코드가 사용하지 못할 수 있다. DB의 버전 하향 보호를 끄거나 저장된 결과를 버전 필드만 낮추지 않는다. 복구는 데이터 보호를 유지하는 전진 수정 또는 검증된 호환 코드로 처리한다.

브라우저는 실제 Next 화면을 사용하되 인증·DB·API를 로컬 fixture로 격리했다. 게시글 조회수 RPC도 응답만 반환하고 저장하지 않는다. Tab·Enter로 실제 URL이 바뀌는 것을 확인했고 FAQ·문의 작성·상세·조회 실패·문의 없음의 main 개수와 가로 넘침, 관리자 마우스 휠 스크롤과 답변 영역 접근을 확인했다. 미로그인 관리자 접근은 공통 로그인 페이지로 이동한다. 로딩 상태는 실제 컴포넌트 단위 검사로 확인했다. 스크린샷은 Git 제외 `tmp/audit-accessibility-qa/`에 보관한다.

Luna 리뷰에서 발견한 부분 프로필의 관리자 활동 혼입과 관리자 고객센터 스크롤 문제를 수정하고 재검토했다. 추가 미로그인 브라우저 검사는 페이지 내부 안내를 기대했지만 실제 공통 middleware의 로그인 이동이 먼저 적용되어 시간 초과가 발생했다. 기존 권한 동작을 확인하고 그 이동을 검사하도록 기대값을 수정했다. 최종 변경 범위에서 추가 필수 결함은 발견되지 않았다. 테스트와 SQL 실행은 부모가 수행했다.

사용자 점수 가이드와 디렉터리·문서 안내를 갱신했다. worktree에 없는 로컬 `docs-private/`는 원래 작업 폴더에서 필요한 문서를 읽고 계산 계약 부분만 갱신했다. 이 로컬 문서는 Git 제외 대상이며, 공유 계약은 이 보고서와 사용자 점수 가이드에 남긴다.

## 남은 확인

운영 적용과 실제 DB에서 exact count의 처리 시간, 과거 경기의 원본 확보·재계산, 배포 후 실제 인증·AI 호출, iOS Safari·Android 앱·실기기는 확인하지 않았다. 이번 격리 migration 검증은 전체 과거 이력 재생이나 baseline 복구 검증을 대체하지 않는다.

앞선 [후속 점검 기록](2026-10-10-audit-followup.md)의 기존 전적 브라우저 10개 실패와 개발 의존성 경고는 이번 범위에서 해결했다고 보고하지 않는다. 기존 전적 화면·원래 폴더의 진행 중 변경을 건드리지 않았고 해당 브라우저 suite는 재실행하지 않았다. 진단 API 중복 조회·대형 executor/registry 구조 개편 등 4~8번 밖의 미완료 항목도 이번 완료 범위에 포함하지 않는다.
