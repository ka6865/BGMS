# 랭킹 자동 계산 및 만난 상대 운영

## 구현 범위

- 킬·피해량 랭킹은 최근 7일 `pubg_player_matches` 기본 기록에서 집계한다. 상세 페이지를 열 필요가 없다. 경기 시각으로 기간을 자르며 Steam/Kakao 및 계정 식별자를 구분한다.
- BGMS 성과는 기존 상세 분석 또는 별도 계산 작업의 현재 버전 결과를 사용한다. 모든 PUBG 플레이어를 수집하는 랭킹이 아니라 BGMS에 확보된 경기 기준이다.
- 자동 계산 대상은 최근 7일 활동한 연결 프로필의 최근 7일 적격 경기다. 단순 검색된 모든 계정이 대상은 아니다.
- 전적 헤더의 ‘만난 상대’에서 나를 기절시킨 상대, 나를 죽인 상대, 개인 관심 목록을 구분한다. 최근 90일 저장 경기, 페이지당 10경기를 사용한다.
- 텔레메트리 계정 ID로 상대를 식별한다. 가려진 신고 알림 닉네임과 추측으로 연결하지 않는다. 관심 등록은 신고 접수나 부정행위 확정을 의미하지 않는다.
- 상대 공식 경쟁전 티어 및 해당 경기 모드의 시즌 평균 피해량을 표시한다. BGMS 성과 등급과 공식 티어는 다른 값이다. 없는 기록은 0으로 추정하지 않는다.
- 랭킹 화면은 제목·탭·필터를 먼저 표시한 뒤 선택한 탭만 `/api/rankings`로 조회한다. 조회 중에는 로딩 표시, 실패하면 재시도 버튼을 보여주며 이전 필터의 늦은 응답은 표시하지 않는다. 탭을 다시 열 때도 새로 조회한다.

아래는 최초 구현 당시의 적용 순서다. 이후 운영 DB·계산 버전 반영 결과는 [2026-10-10 계산 공존 검증 결과](2026-10-10-calculation-coexistence-results.md)를 기준으로 확인한다.

1. 기존 `20260911100000_pubg_match_discovery.sql`, `20260911110000_pubg_ban_watch.sql` 의존성을 적용한다.
2. `20260913090000_pubg_rankings_and_performance.sql`, `20260913100000_pubg_encounter_page.sql`, `20260915090000_pubg_release_hardening.sql`을 적용한다.
3. 새 컬럼을 사용하는 코드를 배포한다. 코드 선배포 시 전적 저장이 실패할 수 있으므로 DB가 먼저다.
4. 기본 조회 및 권한을 확인한 뒤 자동 작업을 선택적으로 활성화한다.

새 테이블은 서비스 역할 전용이다. 기존 전적·벤치마크 테이블을 삭제하지 않는다. `pubg_player_matches`에 nullable 식별·적격성 컬럼을 추가한다. 운영 데이터 전체에 대한 사전 성능 측정이나 실제 마이그레이션 실행은 아직 하지 않았다.

## 부하 제한

`pubg-performance.yml`은 `PUBG_PERFORMANCE_ENABLED` 저장소 변수와 실행 환경 값이 true일 때만 동작한다. 기본 1시간 주기이며 GitHub 일정 지연이 가능하다.

- 전역 동시 계산 1개, 실행당 최대 3경기·4분, 하루 최대 30회 claim.
- 계산 자식 프로세스 V8 힙 상한 512MB, 경기당 110초. 프로세스 전체 RSS 상한을 보장하는 값은 아니다.
- 대기·재시도·실행 큐 합계 300개, 한 번에 최대 50개 추가.
- 실패는 재시도하되 최대 3회, 오래되거나 버전이 달라진 작업은 제외한다.
- AI 코칭 요청을 하지 않는다. 기존 계산 엔진을 재사용한다.
- 실행마다 90일 지난 성과 및 종료 작업을 각 500행까지 정리한다.

랭킹 화면이 보이는 동안 선택한 탭·필터만 60초마다 재조회하며, 조회 중에는 중복 갱신을 시작하지 않는다. 페이지와 API 응답은 `private, no-store`로 유지한다. `get_pubg_rankings_cached`는 기존 `pubg_response_cache`에 정상 집계 결과를 최대 60초 공유하며, 상위 경기의 7일 만료 경계가 더 빠르면 캐시도 먼저 만료시킨다. 탭·정렬된 모드·매치 종류·계산/filter/모집단/result 버전·현재 비공개 키를 캐시 키에 포함한다. 같은 조건의 동시 miss는 advisory transaction lock 뒤 캐시를 다시 확인하므로 서버 인스턴스가 달라도 한 번만 집계한다. 만료된 캐시는 기존 `cleanup_pubg_response_cache` 정리 대상이다.

비공개 목록은 캐시 안에 보관하지 않고 매번 DB의 공통 설정을 읽는다. 관리자 목록·고객문의 처리 중 어느 경로로 변경해도 다음 조회에서 키가 바뀐다. cache hit에서도 상위 행의 현재 경기 계정·legacy discovery·닉네임 cache 연결을 검사한다. 새로 비공개 계정에 연결된 행이 있으면 전체 집계를 다시 수행해 상위 30명을 채운다. 집계 중 비공개 목록이 바뀌거나 설정 검증이 실패하면 이전 공개 결과를 반환하지 않고 오류로 처리한다. 이미 열린 화면의 다음 자동·수동 갱신 전까지 표시된 결과를 원격으로 즉시 지우는 기능은 아니다. 신규 경기·점수와 일반 순위 변동은 최대 60초 뒤 반영될 수 있다.

API는 실제 DB 집계 시각 `generatedAt`을 반환한다. 화면은 응답 수신 시각 대신 이를 조회 기준으로 표시하며, 같은 조건의 자동·수동 갱신 중에는 기존 목록과 갱신 안내를 유지한다. 필터 변경·갱신 실패 시에는 이전 목록을 숨긴다. 서버 RPC 요청은 10초, 화면 요청은 12초 제한 후 재시도할 수 있다. HTTP 요청 중단이 이미 실행 중인 DB 쿼리 취소를 보장하는 것은 아니며 DB의 기존 statement/lock timeout도 유지한다. `X-Ranking-Cache`와 `Server-Timing`의 전체 서버 처리·DB 전체·집계 시간을 이용해 cache hit과 첫 miss를 따로 측정한다. 페이지 진입·필터 변경·자동 갱신은 새 경기 분석을 실행하지 않는다.

`20261010041817_pubg_ranking_safe_cache`의 격리 검증은 hit/miss·필터/버전 구분·비공개 등록/해제·상위 30명 재채움·대소문자 닉네임·cache/discovery/경기 account 연결 변경·TTL·service 권한과 독립 DB 연결의 동시 miss를 포함한다. 집계 중 다른 연결이 비공개 설정을 커밋하면 해당 조회는 오류로 종료하고 캐시를 기록하지 않는다. 재시도에서도 처음 캐시 키만 잠그므로 서로 다른 키 잠금의 교착을 피한다. DB의 마지막 검사 문장이 시작된 뒤 커밋된 변경은 이미 진행 중인 응답에 반영되지 않을 수 있으며, 그 뒤 시작하는 조회는 새 설정으로 검사한다. 로컬 fixture 브라우저는 375×667·390×844·430×932·1440×900에서 갱신·실패·재시도·빈 상태·가로 넘침과 390px의 실제 12초 제한을 확인했다. 단위 테스트 3,995개, analysis 663개, admin 420개와 core 검증이 통과했다(core의 기존 lint 경고 45개). 실제 모바일 기기·대규모 동시 접속·운영 개인정보 설정 변경 검증과는 구분한다.

배포 순서는 기존 호출과 호환되는 위 migration을 먼저 적용하고 새 앱을 배포한다. 앱을 이전 배포로 되돌리면 기존 `get_pubg_rankings`를 캐시 없이 사용하며, 새 RPC와 만료 캐시를 남겨도 이전 앱의 동작을 방해하지 않는다. 경기·점수 데이터 삭제나 재계산은 포함하지 않는다.

`20261010031908_defer_ranking_scores_and_metadata`는 피해량·킬에서 적격 기본 경기의 성과 점수 조회를 건너뛰고, 최종 30명을 고른 뒤 표시할 등급·맵·모드를 조회한다. 적격성이 false/null인 경기는 유효한 점수가 있을 때만 참가하고, 티어는 먼저 점수로 참가 여부를 판단한다. 최근 7일 전체 참가 경기 수, 계정별 최고 경기, 계산 2·3 우선순위, 동점 정렬과 비공개 제외는 유지한다. 전체 경기 수와 최고 경기 선택은 같은 정렬·전체 partition 프레임을 사용한다.

격리 PostgreSQL에서 500건 초과 계정·플랫폼 구분·비공개 별칭·계산 공존과 새 분기를 검증했다. 운영 데이터의 읽기 전용 비교에서도 피해량·킬·티어 각각 30행의 값·경기 수·등급·경기 정보가 이전 함수와 일치했다. 변경 대상은 조회 함수 하나이며 기존 경기·점수의 삭제나 재계산은 포함하지 않는다.

2026-10-10 운영에 위 migration 하나만 dry-run 확인 후 적용했다. `SECURITY INVOKER`·빈 `search_path`·service role 전용 실행 권한과 동일한 migration 버전을 재확인했다. 실제 사이트의 375×667·390×844·430×932·1440×900에서 목록 30명·선택 탭 단일 조회·가로 넘침 없음을 확인했다. 390px 목록 표시 시간은 화면 분리 배포 후 7.985초에서 DB 개선 후 2.385초, 메뉴 이동은 5.042초에서 2.096초, 데스크톱은 4.010초에서 2.245초였다. 첫 375px 조회는 4.300초였으며 단일 순차 측정값으로 동시 부하 성능을 보장하지 않는다. 앱 코드 오류는 없었으나 외부 Google 광고 스크립트 오류는 각 뷰포트에서 1건씩 관측됐다. 실기기 모바일 검증과는 구분한다.

상대 정보는 모드별 시즌 캐시를 6시간 재사용한다. 추가 공식 API 요청은 전역 분당 2회이며 시즌 조회도 이 한도에 포함한다. 다른 기존 기능의 요청량까지 통합 제어하는 한도는 아니다. 요청 제한 시 재시도 시각을 표시한다.

상대 추출은 완료된 빈 결과도 캐시한다. 전역 추출 lease 1개와 사용자 요청 제한을 적용한다. 개인 관심 목록의 증거와 일시적인 상대 캐시는 별개다. `pubg-encounter-cache.yml`은 `PUBG_ENCOUNTER_CACHE_ENABLED=true`일 때만 실행하며 상대 캐시 90일, 프로필 캐시 30일 이후 각 500행까지 정리한다.

## 제재 확인 범위

공식 계정 상태의 임시·영구 제재를 구분하며 마지막 확인 시간을 표시한다. 임시 제재는 해제 전에 조회하지 못하면 놓칠 수 있다. 제재 사유·기간·사용자의 신고와의 인과관계는 공식 상태만으로 확인할 수 없다. 세부 제재 워커 운영은 `pubg-tracking.md`를 참고한다.
