# 성과 등급과 랭킹 갱신 경로 조사

조사일: 2026-09-13. 범위: 현재 로컬 작업 트리의 코드 및 워크플로 정적 조사. 운영 DB의 특정 플레이어 row, 운영 배포 버전, 최근 Actions 성공 여부를 이번 조사에서 조회하지 않았다. 코드·DB·스케줄은 변경하지 않았다.

## 결론

사용자의 '상세를 눌러 성과 등급이 생겨야 랭킹에도 반영되는 것 같다'는 관찰은 현재 일반 사용자 데이터 흐름과 일치한다. 랭킹 갱신은 미분석 경기 수집/계산이 아니라 저장된 분석 결과의 재조회다. 다만 일부 리더보드 선수 자동 분석도 있으므로 상세 클릭만이 유일한 분석 진입점은 아니다.

## 확인한 흐름

```text
플레이어 검색 / 기본 전적 동기화 / 새 매치 ID 보존 worker
  → pubg_player_matches: 경기 시간, 킬, 딜량, 기절, 생존 등
  → 기본 전적 목록 표시 (성과 분석 미실행)

경기 상세 최초 펼침
  → ExpandedMatchDetails → /api/pubg/match
  → 기존 유효 분석 캐시가 없으면 AnalysisEngine 실행
  → processed_match_telemetry에 결과 저장
  → 적격 경기이면 global_benchmarks에 점수·등급·딜량·킬 저장
  → onDetailReady → 전적 카드의 성과 표시

랭킹 진입 / 필터 변경 / 갱신 버튼
  → actions/rankings.ts → global_benchmarks 조회
  → 최근 7일 범위에서 플레이어별 최고 기록 TOP 30
```

### 근거 파일

- `components/stat/MatchCard.tsx`: 처음 펼친 후에만 상세 컴포넌트를 mount. `onDetailReady={setDetailData}`로 분석 응답을 카드에 병합한다.
- `components/stat/matches/ExpandedMatchDetails.tsx`: summary 상태에서 `/api/pubg/match`를 요청한다.
- `components/stat/matches/CompactMatchRow.tsx`: `summary.benchmark`가 있을 때 성과 등급을 계산해 표시한다.
- `app/api/pubg/matches-summary/route.ts`: 분석 캐시 → 기본 전적 → raw stats → 경량 공식 API 순으로 조회. 누락 기본 통계 수집은 최대 5건이며 여기서 분석 엔진은 호출하지 않는다.
- `lib/pubg/playerMatchesIngest.ts`: 기본 경기 필드를 저장하며 성과 점수나 `global_benchmarks`를 생성하지 않는다. 새 discovery worker도 이 경량 수집 경로를 쓴다.
- `app/api/pubg/match/route.ts`, `lib/pubg-analysis/persistMatchAnalysis.ts`: 분석 결과 저장과 적격 benchmark upsert를 담당한다.
- `actions/rankings.ts`: 딜량·킬·BGMS 티어 세 탭 모두 `global_benchmarks`에서 조회한다.

## 표시·반영을 동일시하면 안 되는 경우

- 분석 결과에 등급이 있어도 benchmark 적격성 검사를 통과하지 않으면 랭킹 원장에 저장하지 않는다. 일반 경로에서 분석 엔진은 생존 300초 이상을 유효 benchmark로 표시하며, 저장 시 일반/경쟁 BR 등의 추가 조건도 적용한다.
- 랭킹 딜량·킬에는 현재 filter/population 버전 조건이 있다. BGMS 티어에는 현재 calculation 버전까지 일치해야 한다. 딜량·킬 탭에서 구 계산 버전의 등급은 숨긴다.
- 최근 범위·모드·최고 기록 TOP 30 조건으로도 제외될 수 있다. 분석 완료가 곧 랭킹 입상을 뜻하지 않는다.
- 파생 통계 저장 실패는 상세 응답 자체를 반드시 실패시키지 않는다. 따라서 화면에 계산 결과가 보여도 DB 저장은 실패했을 수 있다.
- 유효 상세 캐시를 반환하는 경로가 있으므로, 랭킹 row 저장 실패가 재클릭만으로 항상 복구된다고 보장할 수 없다.

## 자동 처리와 캐시

- `.github/workflows/daily-tasks.yml`은 매일 UTC 18:00(KST 03:00) 실행 설정이다. `scrape_elite.ts`가 일부 Steam/pc-as 리더보드 선수를 분석한다.
- 설정은 리더보드 모드당 최대 5명, 선수당 최근 최대 3경기다. 5명은 전체 합계가 아니다. 일부 대상 자동 수집이며 사이트에 검색된 모든 사용자의 미분석 경기 처리 작업이 아니다.
- 일반 사용자 `sync_user_matches.ts` 작업은 기본 전적 수집이다. 새 매치 ID 보존 migration을 적용해도 성과 자동 계산까지 연결되지는 않는다.
- `app/rankings/page.tsx`는 초기 데이터에 1,800초 캐시 재검증을 설정했다. 시간이 됐다고 누락 경기 분석을 시작하지 않는다.
- `RankingsClient.tsx` 갱신 버튼/필터 변경은 서버 액션으로 DB를 다시 읽는다. 열린 화면의 주기적 polling은 없다.
- 별도 `/api/rankings`에는 CDN 300초 + stale-while-revalidate 600초 헤더가 있지만 현재 웹 랭킹의 수동 갱신은 이 API를 사용하지 않는다.
- 분석 저장 성공과 `rankings` 태그 무효화를 연결한 호출은 조사한 코드에 없다. 관리자 일반 태그 재검증 API는 별도로 존재한다.
- 화면 `updatedAt`은 페이지 응답을 만들거나 재조회한 시각이다. 마지막 경기 수집·분석 완료 시각을 나타내지 않는다.

## 함께 발견한 집계 정확성 문제

1. `최근 7일` 필터는 경기의 `played_at`이 아닌 benchmark의 `created_at`을 사용한다. 현재 benchmark builder는 경기 일시를 이 필드에 넣지 않는다. DB default/trigger와 실제 row를 추가 확인하기 전 경기 일시 기준 주간 랭킹이라고 보장할 수 없다. 지연 분석·백필 시 결과 범위를 점검해야 한다.
2. 랭킹 쿼리가 platform을 구분하지 않고 `player_id`만으로 중복을 제거한다. 같은 닉네임의 Steam/Kakao가 합쳐질 수 있고 API 응답은 platform을 Steam으로 고정한다.
3. 먼저 상위 500행만 읽은 뒤 30명을 고른다. 특정 플레이어 행이 많이 차지하면 충분한 다른 후보를 조회하지 못할 수 있다. BGMS의 `match_count`도 이 500행 안의 수이므로 전체 분석 경기 수가 아니다.
4. BGMS 티어는 최근 범위의 최고 단일 경기 점수다. 시즌 공식 티어나 최근 경기 평균 실력을 뜻하지 않는다.

## 권장 개선 설계 (미구현)

### 1. 기본 전적 랭킹과 BGMS 점수를 분리

딜량·킬 랭킹은 검증된 `pubg_player_matches` 기본 기록으로 집계하면 상세 클릭과 무관하게 수집 완료 후 반영할 수 있다. 경기 일시·플랫폼·실제 계정·일반/경쟁·사람 참가 등 공통 적격성을 명시한다. 현재 benchmark의 생존/표본 조건과 달라지는 정책은 화면과 문서에 분명히 표시한다.

`global_benchmarks`는 비교 표본 역할도 있으므로 랭킹을 넓히기 위해 부적격 경기나 가짜 점수를 이 테이블에 넣지 않는다. 기본 수집 정보만으로 확인 못 하는 적격성은 별도 상태로 두고 추정하지 않는다. 기존 닉네임 키는 accountId와 안전하게 연결하고 불명확한 과거 identity는 자동 병합하지 않는다.

### 2. BGMS 성과는 별도 백그라운드 작업

기본 전적 저장 후 `(platform, accountId, matchId, calculationVersion)`별 미분석 작업을 멱등 등록한다. 초기 범위는 사이트가 수집 대상으로 관리하는 활성 플레이어의 최근 7일 경기이며, 모든 PUBG 플레이어 자동 수집으로 표현하지 않는다. 단순 검색 남용으로 무제한 분석되지 않도록 활성 대상 선정과 일일 한도를 둔다.

상세와 worker가 같은 분석 서비스를 호출하도록 기존 함수 경계를 정리한다. HTTP 상세 페이지를 통째로 일괄 호출하는 방식은 인증·타임아웃·캐시 분기 때문에 피한다. 유효 분석 캐시는 재사용하고 저장 누락은 결과를 다시 계산하지 않고 안전하게 재저장할 수 있게 한다. 구버전 분석은 별도 재계산 상태로 관리한다.

분석 queue는 `pending/running/done/retry/unavailable/excluded`와 lease·시도 횟수·오류·시각을 가진다. 기본 경기 수집 성공과 분석 성공은 서로 다른 상태다. AI 코칭 문장 생성은 자동 작업에 포함하지 않는다. 성과 계산 자체는 결정적인 분석 엔진 계산이다.

초기 처리 제한안은 1회 동시 1개, 최대 10경기 또는 5분이다. 실행 주기·일일 상한은 실제 CPU/R2/DB 측정 후 설정하고 대기량을 표시한다. 캐시가 없는 경기에는 telemetry 다운로드 및 처리 비용이 추가된다. 보관 기한이 지난 원본 없는 경기는 `분석 불가`로 남긴다.

### 3. 집계·화면 갱신

- SQL에서 `(platform, accountId)`별 최고 기록을 집계한 후 TOP 30을 자른다. 실제 경기 일시를 기간 기준으로 사용한다. 검증 불가한 legacy identity는 명시적으로 제외/격리한다.
- 분석 결과 저장 성공 후 랭킹 캐시를 묶어서 무효화한다. 기존 Next 버전 로컬 문서의 캐시 규칙을 구현 시 다시 확인한다.
- 화면이 보일 때 제한된 간격으로 목록을 재조회하고, `집계 시각 / 분석 완료 경기 수 / 대기 경기 수`를 구분한다. 실패 시 갱신 시각을 성공처럼 바꾸지 않는다.
- 최고 단일 경기 랭킹을 유지한다면 `BGMS 최고 경기 점수`라고 표시하고 공식 경쟁전 티어와 구별한다.

## 검증할 시나리오

- 상세를 한 번도 열지 않은 새 경기: 기본 수집 후 딜량/킬 후보에 반영, 분석 worker 성공 후 성과와 BGMS 후보에 반영.
- 새로고침만으로 분석 요청이 무제한 발생하지 않음. 동일 경기 동시 상세/worker 처리 시 중복 작업 방지.
- 6일 전 경기 지연 저장과 8일 전 경기 백필: 경기 일시 기준 포함/제외.
- Steam/Kakao 동명 계정 분리, 닉네임 변경, 구버전 점수 제외.
- 분석 성공/DB 저장 실패를 구분하고 재시도로 복구. 원본 만료와 일시 장애 구분.
- 500행 넘는 표본에서 TOP 30과 분석 경기 수가 정확함.
- 기존 비교 표본 적격성·분석 점수 계산식은 랭킹 개선 때문에 훼손되지 않음.

이번 산출물은 조사와 개선 설계다. 운영 실행 상태 확인, 마이그레이션, 자동 분석 worker 구현과 배포는 수행하지 않았다.

## 후속 구현

2026-09-14 기본 기록 기반 랭킹, 제한된 서버 성과 계산, 별도 만난 상대 페이지 구현 및 로컬 검증을 진행했다. 적용 순서와 기능 범위는 [랭킹·상대 운영 안내](pubg-ranking-encounters.md)를 참고한다. 운영 DB 반영 및 작업 활성화는 수행하지 않았다.
