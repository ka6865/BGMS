# 서비스 점검 후속 수정과 운영 반영 준비

기준 브랜치는 `codex/fix-audit-approvals-cache-auth`다. [앞선 세 가지 수정](2026-10-10-audit-fixes-1-3.md)에 보안 패치, 관리자 안내 수정, 브라우저 검증, 구조·문서 정리를 추가했다. 이 문서는 브랜치 결과와 운영 적용 준비를 기록한다. 운영 migration 적용·데이터 삭제·배포는 수행하지 않았다.

## 사용자와 관리자에게 달라지는 점

| 동작 | 변경 후 |
| --- | --- |
| 사용자 이미지 보기 | 이미지 처리 라이브러리를 보안 패치한다. 실제 Next 이미지 최적화로 WebP 응답을 확인한다. |
| 관리자 데이터 관리 → 대상 확인 | 삭제 없이 후보만 확인한다. 서버에서 대상 확인이 실패하면 삭제를 시작하지 않는다. |
| 정리 실행 → 확인창 | 전체 후보 수와 요청당 최대 20,000건을 구분한다. 취소하면 삭제 요청이 나가지 않고, 실행 중에는 확인 버튼을 잠근다. |
| 승인 요청의 실패·연결 끊김 | 승인 목록을 다시 읽어 실제 상태를 확인한다. 조회도 실패하면 원래 경고를 유지하고 실행·거절 버튼을 잠근다. `approved`는 “실행 상태 확인”으로 표시해 결과 확인 후 대응하도록 한다. |
| 승인 전 조건 차단·거절 저장 실패 | 실제 상태가 `pending`이면 대기 목록에 계속 표시한다. 실패했다는 이유만으로 처리 완료 목록에 옮기지 않는다. |
| 정리 중 배치 실패 | 확인된 삭제 수와 실패한 배치의 결과가 불확실할 수 있음을 표시한다. 이전 대상 확인 결과를 버리고 다시 확인하게 한다. |
| 게시글 작성·수정 승인 | 비공개 초안 저장과 별도 공개 발행을 설명한다. 수정은 원본의 즉시 덮어쓰기가 아니라 수정 초안 생성이다. 실제 executor는 변경하지 않았다. |
| 플레이어 캐시 정리 | 보정 migration 적용 후 최근 관측 순 150,000건을 보호한다. 조회 횟수가 있거나 시즌 통계가 있는 행도 보존한다. 그 외에는 마지막 조회가 없거나 90일보다 오래된 행이 대상이다. |

최근 관측 시각은 수집 시각이며 최근 사용자 검색 시각과 다르다. 이 캐시는 회원 계정이나 게시글이 아니라 PUBG 플레이어 자동완성·조회 정보다.

## 패키지와 코드 구조

- `sharp` 0.35.4 → 0.35.5와 관련 네이티브 패키지: [공식 보안 공지](https://github.com/lovell/sharp/security/advisories/GHSA-wq5f-xc86-pv6w).
- `source-map-js` 1.2.1 → 1.2.2: [보안 공지](https://github.com/advisories/GHSA-68fv-2mgg-jv7q).
- 테스트 도구 `ts-jest`가 사용하는 `handlebars` 4.7.9 → 4.7.10: [공식 보안 공지](https://github.com/handlebars-lang/handlebars.js/security/advisories/GHSA-8r5x-fm3f-whwj).

메이저 버전이나 Next.js 버전은 변경하지 않았다. lockfile과 별도 worktree의 의존성을 갱신했다. 원래 작업 폴더의 의존성은 공유하지 않는다.

`lib/admin-agent/storage-limits.ts`가 90일·150,000건 보존 기준과 관리자 배치 한도를 정의한다. 관리자 API, 관제, 정리 스크립트가 보존 기준을 공유하고 확인창은 서버와 같은 요청 한도를 사용한다. 관리자 정리는 1,000건씩 최대 20회, 정기 플레이어 캐시 정리는 기존처럼 500건씩 최대 30회(15,000건)다.

`components/admin/dashboard/StoragePanel.tsx`로 데이터 관리 표시를 분리했다. 요청·상태·삭제 확인은 대시보드 페이지가 계속 담당한다. [디렉터리와 문서 안내](../project-map.md)를 추가했다. 문서의 매치 수집 일정은 workflow의 UTC 매시 7·27·47분 실행 기회와 기본 limit 1,000에 맞췄다. 실제 수집에는 `PUBG_API_KEY`가 필요하며 dry-run과 캐시에서의 대상 등록에는 불필요하다. 예약 실행의 실제 시각과 처리량은 GitHub 지연·대기열·API 한도에 따라 달라진다.

## 운영 DB의 읽기 전용 확인

대상은 연결된 BGMS Supabase 프로젝트다. 2026-10-10 04:17 KST의 집계이며 테이블 내용은 변경하지 않았다.

| 항목 | 행 수 |
| --- | ---: |
| 전체 플레이어 캐시 | 343,773 |
| 현재 함수의 삭제 후보 | 341,120 |
| 새 보존 조건의 삭제 후보 | 193,458 |
| 보정으로 추가 보호되는 기존 삭제 후보 | 147,662 |
| 최근 관측 순 보호 범위 | 150,000 |

운영 함수 정의와 migration 이력을 조회해 `20261009182823_restore_player_cache_compaction_contract`가 미적용임을 확인했다. 현재 함수는 `p_keep_recent`를 삭제 조건에 사용하지 않고 실제 삭제 응답의 잔여 건수를 0으로 반환한다.

새 함수와 같은 보존 조건의 SELECT를 `BEGIN READ ONLY`와 8초 제한 안에서 실행했다. 경계값을 한 번 계산하는 조회 계획의 `EXPLAIN ANALYZE` 실행 시간은 3,130.278ms였다. 초기 조인 형태의 검증용 조회는 8초 제한으로 중단됐고, 경계값을 고정하는 형태로 바꿔 확인했다. 이는 SELECT 측정이며 실제 RPC·삭제 배치·요청 전체 시간은 아니다. 현재 인덱스에서 최근 경계 정렬은 임시 디스크를 사용하므로 실행 환경과 부하에 영향을 받는다.

## 운영 반영 순서

1. 정리 작업이 실행 중인지 확인하고 적용 시간 동안 관리자 정리와 자동 정리가 겹치지 않도록 조율한다. 자동 경로는 `.github/workflows/daily-tasks.yml`의 `Run Storage Cleanup`이다. workflow 전체를 중지하면 다른 정기 유지보수도 멈추므로 범위와 시간을 함께 확인한다. 이번 작업에서는 중지 설정을 변경하지 않았다.
2. 운영·로컬 migration 이력을 다시 대조하고 보정 파일 `supabase/migrations/20261009182823_restore_player_cache_compaction_contract.sql`만 적용 대상으로 검토한다. 다른 미적용 migration까지 일괄 적용하지 않는다. 이 파일은 함수를 교체하며 데이터를 삭제하지 않는다.
3. 함수 정의와 실행 권한을 다시 확인한다. `service_role`만 실행할 수 있어야 한다. `compact_pubg_player_cache(90, false, 500, 150000)`으로 삭제 없이 대상·전체 수를 다시 읽고, 위 스냅샷과 달라진 이유를 확인한다.
4. 검증한 브랜치 코드와 lockfile을 배포한다. 기존 인자를 받는 함수이므로 DB 보정 → 코드 배포 순서로 진행할 수 있다. `ADMIN_REVALIDATE_TOKEN` 설정 여부를 값 노출 없이 확인한다. 없으면 재검증 API가 401을 반환하는 것이 정상이다.
5. 승인·거절·대상 확인·취소를 운영 화면에서 확인한다. 실제 삭제는 확인된 영향과 해당 운영 절차에 따라 별도로 실행한다. 첫 삭제 결과의 보존 범위·실제 삭제량·잔여량·시간을 확인한 뒤 정기 정리를 재개한다. 큰 정리를 반복하기 전에 요청 전체 시간과 실패 여부를 확인한다.

문제가 생기면 정리를 먼저 멈추고 실제 결과를 확인한다. 코드 rollback만으로 삭제된 행은 복구되지 않는다. 이전 RPC로 되돌리면 최근 150,000건 보호 누락도 돌아오므로 SQL의 단순 rollback 대신 보존 조건을 유지한 보정 migration을 검토한다. 실행 후 기록 실패로 남은 `approved`를 임의로 `pending`으로 바꿔 재실행하지 않는다.

## 검증과 리뷰

관리자 fixture 브라우저는 로컬 Supabase 호환 인증 서버와 관리자 API 응답을 사용한다. 인증 서버는 쓰기 요청을 거부하고 관리자 API는 브라우저에서 가로챈다. 운영 자격 증명·운영 회원 데이터·실제 삭제는 사용하지 않는다.

- 모바일 `375x667`, `390x844`, `430x932`와 PC `1440x900`에서 대상 확인 → 취소 → 삭제 확인, 정리 일부 실패, 승인, 사유 입력 거절, 승인 전 차단, 실행 후 기록 오류와 재조회 실패, 연결 끊김을 검사한다.
- Next 이미지 최적화 endpoint의 실제 WebP 응답을 검사한다.
- 전적 화면은 기존 `tests/stats-browser-smoke.test.ts` fixture 하네스로 검사한다.
- 기본 명령은 `npm run verify:core`, `npm run verify:admin`, `npm run test:unit`, `npm test -- --runInBand`, `npm run verify:migrations`다. 브라우저는 `RUN_ADMIN_BROWSER_SMOKE=true npx vitest run tests/admin-dashboard-browser-smoke.test.ts`와 `RUN_STATS_BROWSER_SMOKE=true npx vitest run tests/stats-browser-smoke.test.ts`로 별도 실행한다.

| `verify:core` | 오류 0건. 기존 lint 경고 44건 |
| `verify:admin` | 20개 파일·406개 검사 통과 |

최종 검사 병행 실행 중 자원 부족으로 일부 단위·브라우저 검사에 시간 초과가 있었고 생성 타입 파일 충돌도 있었다. 검사 순서를 분리해 재실행한 단위·관리자 브라우저·타입 검사는 통과했다. 실패 시나리오 추가 검사는 수정 전 문제를 재현한 뒤 수정 후 통과한 결과다.

패치 후 `npm audit --omit=dev --package-lock-only`의 취약점은 0건이다. 개발 의존성을 포함하면 High 5건·Moderate 20건이 남고 Critical은 0건이다. 남은 경고는 lint·Jest 의존성 경로이며 audit의 제안에는 Next ESLint와 Jest의 메이저 다운그레이드가 포함돼 이번 호환 패치에 넣지 않았다. 전체 서비스 보안이 무결하다는 뜻은 아니다.

전적 브라우저는 47개 중 37개 통과·10개 실패했다. 후속 수정 전 커밋 `378a6666`의 별도 임시 worktree와 기존 버전 의존성에서도 동일한 10개가 실패했다. 기존 검사와 현재 화면 계약·배치가 맞지 않는 항목을 포함하며 이번 관리자·패키지 변경 때문에 생긴 실패는 아니다. 테스트가 과거의 저장 키 `v2`를 기대하고 실제 구현은 `v3`를 저장하는 차이는 코드로 확인했다.

남은 전적 항목은 최근 검색 표시 2개, 요약 재시도 2개, 즐겨찾기·최근 검색 저장 2개, 모드·리플레이 컨트롤 2개, PC 배치·광고 영역 2개다. 1920px 검사에서는 광고 영역이 화면 오른쪽으로 180px 벗어났다. 나머지 항목도 검사 기대값 수정만으로 정상이라고 단정하지 않고 실제 동작 확인이 필요하다. 현재 브랜치는 전적 화면·기존 fixture를 변경하지 않았으며 원래 작업 폴더의 관련 미완료 변경도 보존했다.

Luna 두 명은 읽기 전용으로 재리뷰했고 부모가 수정했다. 주요 지적은 실패 경고 유실, 실제 대기 건의 잘못된 목록 이동, 일부 삭제 후 재확인 누락, 초안의 즉시 공개·원본 수정처럼 보이는 안내, 운영 API 키 요구 조건의 문서 오류였다. 마지막 재리뷰에서 이번 변경 범위의 남은 지적이 없음을 확인했다. 서브에이전트는 파일 변경·서버 실행·운영 DB 호출 없이 검토했고 실제 검사는 부모가 실행했다.

브라우저 뷰포트 검증은 iOS Safari·Android 앱·실기기 검증을 대체하지 않는다. 운영 migration 적용·실제 삭제 시간·배포 후 동작은 남은 확인이다.
