# 감사 수정 1~8 최종 배포 검토

최종 판단은 **현재 상태의 전체 main 배포 보류**다. 코드·격리 검증 통과와 운영 배포 준비를 구분한다. 계산 버전 3으로 전환할 기존 데이터가 준비되지 않아, 즉시 배포하면 점수 랭킹과 기존 전술 분석·AI 사용 범위가 줄어든다. 사용자의 “충분하면 배포” 조건을 충족하지 못했으므로 main 병합·운영 배포·운영 migration·재계산·삭제를 실행하지 않았다.


후속 사용자 결정: 기존 계산 2를 보존하고 신규 분석만 계산 3으로 저장하는 공존 방식을 적용한다. 아래 내용은 공존 수정 전 배포 차단 근거이며, 최신 구현·검증·배포 결과는 [계산 공존 결과](2026-10-10-calculation-coexistence-results.md)를 따른다.

## 검토 범위

- 브랜치: `codex/fix-audit-4-8`.
- 현재 main 기준: `ea164430f4f31523a7c9e6ca1d3e8763546f84cd`.
- 검토 코드: `68639614fe4cad0d5993c0240fe6f2aedcd1f110`. 최신 main을 합친 뒤 1~8번과 후속 수정 전체 61개 파일을 비교했다.
- 패키지·lockfile·migration 검증 파일·AI fixture 충돌은 양쪽 계약을 보존해 해결했다. 현재 main의 패키지 버전과 lockfile을 유지하며 감사 브랜치의 인증 검사와 계산 3 시나리오를 포함했다.
- Luna 3명이 보안/관리자, 계산/DB, 화면/문서를 읽기 전용으로 검토했다. 부모가 병합과 실제 검증을 실행했다. 원래 작업 폴더의 별도 미커밋 변경은 포함하지 않았다.

## 배포 전에 해결할 사항

### P1: 계산 3을 요구하면 기존 점수·분석이 빠지는 전환 공백

관리자 관점에서는 서버 오류 없이 랭킹이 비어 보일 수 있다. 사용자 관점에서는 기존 경기의 기본 킬·피해량은 남더라도 전술 분석과 AI가 재계산 대기 상태가 된다. 저장된 기록을 삭제하는 문제는 아니지만 주요 기능을 이용할 수 있는 범위가 줄어든다.

2026-10-10 점검 시점에 운영 BGMS DB를 읽기 전용으로 확인했다.

| 항목 | 확인 결과 |
| --- | ---: |
| 필터 8·모집단 1의 계산 2 비교 표본 | 11,568행 |
| 같은 조건의 계산 버전 미확인 표본 | 159행 |
| 최근 갱신 개인 분석 100행 | 모두 계산 2 |
| 계산 3의 비교 집계 | 0행 |
| 계산 3·결과 73의 적격 보존 점수 | 0행 |
| 기존 rollout CLI의 dry-run 전환 재고 | 11,727행·실제 경기 10,123개 |

`lib/pubg-analysis/constants.ts`의 `ANALYSIS_CALCULATION_VERSION = 3`은 비교 reader, 랭킹, 현재 개인 분석 및 AI의 공통 조건이다. `benchmarkLookup.ts`는 계산 3 표본만 조회하고, 기존 개인 분석 reader는 계산 2를 기본 전적 또는 갱신 필요 응답으로 제한한다. 새 migration은 RPC를 교체할 뿐 기존 자료를 재계산하지 않는다. 이 수치에서 코드만 배포하면 전환 공백이 발생한다.

이번 점수 수정은 매치 임팩트에 영향을 주며 기본 점수·티어 산식은 바꾸지 않는다. 따라서 변경 범위에 맞춘 호환 읽기 또는 실제 원본 재계산을 통한 전환을 설계·검증해야 한다. 버전 숫자만 3으로 바꾸는 일괄 UPDATE는 실제 계산을 했다는 잘못된 근거를 만들므로 사용하지 않는다. 보존 요약만으로 정확히 같은 임팩트를 복원할 수 있다는 계약도 확인되지 않았다.

재고 파일은 Git 제외 `tmp/release-calculation-v3-readiness/`에 저장했다. dry-run은 DB 조회와 로컬 파일 생성만 수행하며 원본 다운로드·DB 재계산 쓰기·Gemini 호출은 하지 않았다. DB 행 생성일 기준으로 8,582행이 14일보다 오래됐지만, 생성일은 경기 시각이나 원본 확보 성공을 대신하지 않는다. 원본 확보 가능 여부는 별도 검증이 필요하다. 이 재고는 비교 표본 대상이며 전체 개인 분석 재고를 뜻하지 않는다.

### 운영 DB 반영과 이력 확인

`20261009182823_restore_player_cache_compaction_contract`와 `20261010000000_analysis_calculation_v3`는 운영 migration 목록에 없다. 기존 RPC의 실행 권한은 service role에만 있고 `SECURITY INVOKER` 및 빈 search path를 확인했다. 새 함수 정의와 권한은 격리 DB에서 검증했다.

연결된 CLI의 `db push --dry-run`은 이전 운영 migration 3개의 시간 식별자가 로컬 파일과 달라 중단됐다. 운영에는 `20260922223350`, `20260922225317`, `20261002091734`가 기록돼 있고 로컬 대응 파일은 다른 시간 식별자를 쓴다. 이력이 빠졌다는 이유로 실제 적용된 항목을 reverted 처리하거나 기존 migration 전체를 재실행하지 않았다. 최종 적용 시에는 이력·정의 대조 후 이번 두 함수 보정만 적용하는 경로를 확인해야 한다.

순서는 전환 전략 검증 → 대상 함수 보정 → 작은 실제 재계산 및 저장 후 재조회 → 필요한 비교 모집단·개인 분석 준비 확인 → main 배포 → 배포된 서비스 확인이다. 전환을 준비하며 기존 버전 2 서비스와 데이터 하향 보호를 유지해야 한다.

## 코드 리뷰 결과

승인·거절 경쟁의 조건부 상태 선점, 실행 후 기록 실패의 재실행 방지, 미설정 관리자 토큰 차단, 실제 바이트 수 제한, 부분 통계 안내, 정리 한도·보존 조건, 키보드 링크와 고객센터 스크롤에서 추가 확정 P0/P1 코드 결함은 발견하지 못했다. 승인 부분 실패의 `success: true` 응답 우려는 실제 대시보드가 실패 건수와 확인 안내를 표시하는 것을 추적해 필수 수정으로 확정하지 않았다. 최종 배포 차단은 위 계산 전환 조건이다.

관리자·고객센터 브라우저는 실제 Next 화면과 로컬 인증/API fixture를 사용해 `375×667`, `390×844`, `430×932`, `1440×900`을 확인했다. 실제 운영 승인·게시·삭제는 수행하지 않았다. 빌드는 DB 자리표시자 때문에 상자 데이터 조회 오류가 기록됐지만 빌드 자체는 통과했다. 실제 인증·운영 데이터·실제 AI까지 검증됐다는 뜻은 아니다.

전적 브라우저는 현재 main `ea164430`의 별도 임시 worktree와 동일 패키지로 비교했다. 두 실행 모두 49개 중 36개 통과·13개 실패이며 실패한 시나리오 이름도 모두 일치한다. 최근 검색 표시 2개, 요약 재시도 2개, 저장 2개, 컨트롤 선택자 2개, 계정 전환·시즌 재시도의 player 요청 횟수 3개, PC 배치·광고 2개다. 저장 검사의 v2 쓰기 기대는 실제 v3 쓰기 계약과 다르며, 모든 실패를 실제 서비스 결함 13개라고 단정하지 않는다. 다만 1920×1080에서 광고 레일이 오른쪽으로 180px 벗어나는 현상과 요청 기록 2회/기대 1회는 양쪽에서 재현돼 후속 점검이 필요하다. 이 감사 변경의 추가 회귀로 보고하지 않으며 전적 화면 검증 전체 통과도 주장하지 않는다.

baseline의 첫 실행은 node_modules를 외부 경로로 심볼릭 링크해 Turbopack이 시작을 거부했다. 격리 폴더에 동일 패키지의 별도 디렉터리를 준비한 후 위 49개를 실제 실행했다. 원래 사용자 서버와 작업 폴더는 변경하지 않았다. 원래 폴더의 Git 상태와 tracked diff 해시도 시작 시점과 일치함을 확인했다.

현재 배포된 `https://bgms.kr`의 홈(지도 이동), 전적 검색, 랭킹, 고객센터는 GET 검사에서 HTTP 200이었다. Vercel의 최근 1시간 집계에도 runtime error가 없었다. 이는 기존 main 서비스 상태이며 이번 변경의 배포 후 검사로 보고하지 않는다. 랭킹 RPC 전체 개수 비교는 8초 읽기 제한에 걸려 완료하지 못했으며 그 호출의 성능 통과도 주장하지 않는다.

실기기·실제 OAuth·Gemini·운영 재계산·운영 migration 적용·전체 과거 DB baseline 복구는 실행하지 않았다. 메인 배포와 배포 후 최종 검증은 배포 차단 조건이 해소된 뒤에 진행해야 한다.
