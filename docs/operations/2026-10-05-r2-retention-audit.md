# R2 보존 가치와 정리 후보 대조 — 2026-10-05

R2에는 과거 경기의 지도와 재분석 재료를 보존할 가치가 있다. 경기별 필요한 자료 한 벌을 장기 보관하고, 동일 사본과 교체된 파생 캐시를 정리하는 방향을 권장한다. 현재 구조의 모든 버전·플레이어별 사본을 계속 누적할 필요는 없다.

전체 참조 대조 기준은 **48,504개 / 15,481,024,260바이트(15.481GB)**다. DB 16개 테이블의 297,454행, 복구용 인벤토리 220개를 대조했다. 참조가 완전히 끊긴 파일은 발견하지 못했다. 조건부 정리 계획은 **6,277개 / 921,920,534바이트(0.922GB)**다. 이번 조사는 운영 DB와 R2를 읽었으며, 실제 삭제·교체·DB 수정은 0건이다.

현재 용량에서 유일 자료를 없애며 비용을 줄일 필요는 작다. Standard 저장소와 계정 무료분 10GB-month가 모두 이 버킷에 사용 가능하고 현재 용량이 한 달 유지된다는 가정에서 저장비는 약 **월 $0.09**다. 요청 비용·다른 버킷·일별 최대 용량·세금은 별도이며 실제 청구액은 조회하지 않았다. 가격은 GB-month 올림 기준이다. [Cloudflare 공식 요금](https://developers.cloudflare.com/r2/pricing/)

첫 전체 대조는 KST 04:38:41–04:44:05에 수행했다. 이후 본문 검증 과정에서 버킷은 05:19:42 기준 48,537개 / 15,497,084,901바이트로 증가했다. 증가한 33개는 v62에 있었다. 조건부 계획에 포함된 오래된 경로는 본문 표본 GET에서 기존 ETag·크기를 유지했다. 이 조회들은 운영 중인 DB와 R2의 순차 관측이며, 시스템 간 원자적 스냅샷은 아니다. 실제 정리 시 참조·점유·ETag를 다시 확인해야 한다.

**정리 가능한 후보와 선행 조건**

| 분류 | 파일 수 | 원래 바이트 | 판단 |
| --- | ---: | ---: | --- |
| 구형 분석 사본 | 1,942 | 570,063,306 | 동일 본문 한 벌과 기존 키·플레이어·버전 연결을 보존한 뒤 정리 후보 |
| 상위 버전으로 교체된 지도 | 4,335 | 351,857,228 | 상위 파일 검증 및 오래된 등록부 참조 해제 후 정리 후보 |
| 합계 | 6,277 | 921,920,534 | 즉시 삭제 승인 목록으로 사용하지 않음 |

루트에서 동일 크기·ETag이고 같은 경기 UUID를 사용하는 1,517개 묶음, 추가 사본 1,970개 / 578,849,677바이트를 찾았다. 본문 20쌍을 실제 다운로드했으며 SHA-256과 이벤트 내용이 모두 같았다. 전체 1,517개 묶음의 SHA-256을 읽어 검증한 것은 아니다. 정리할 때 각 후보와 보존 사본을 다시 읽어 확인한다.

이 중 해당 닉네임의 분석 DB 행이 없는 28개 묶음은 제외했다. 해당 묶음의 추가 사본 28개 / 8,786,371바이트도 보존한다. 남은 1,489개 묶음의 추가 사본 1,942개가 첫 후보군이다. 기본 전적과 상세 분석 DB 행이 있고, 정형 DB의 정확한 R2 경로 참조는 없다. 현재 일반 상세 API는 루트 키를 읽지 않는다. 복구 스크립트는 파일명에서 경기·닉네임을 읽으므로, 사본 정리 전에 기존 모든 키와 보존 파일의 연결을 남기고 복구 소비자가 그 연결을 읽도록 해야 한다. [루트 복구 소비자](https://github.com/ka6865/BGMS/blob/d17e209e3dfb47e1ecb18043398fe2d5c2de8dc6/scripts/backfill_pubg_player_matches_from_r2.ts#L60)

같은 플랫폼·경기·계정 해시·모드에서 더 높은 버전의 객체가 존재하는 것은 4,337개 / 352,518,836바이트였다. 이 중 분석 입력 1개 / 595,840바이트는 지도 캐시 정리에서 제외한다. 새 파일의 이벤트 보존 범위가 같다는 검증이 필요하다. 나머지 지도 4,336개 중 상위 등록부가 `pending`인 1개 / 65,768바이트도 제외한다. 그 파일은 현재 master 참조도 남아 있다. 남은 4,335개는 상위 파일이 `ready`이고, 현재 master가 가리키는 경로가 아니다. 이 경로의 등록부 참조는 남아 있으므로 먼저 정리해야 한다. 읽어 검사한 대체 지도 9쌍의 상위 payload는 모두 지도 데이터 계약을 통과했고, 플랫폼·경기·플레이어·모드 식별자가 경로와 일치했다. 전체 후보의 본문 검증은 실제 정리 단계에서 수행한다.

6,277개를 정리해도 전체 저장량은 대조 기준 약 14.559GB로 남는다. 이 작업만으로 10GB 미만이 되지는 않는다. 복구용 연결 기록의 새 저장량은 아직 발생하지 않았으며 위 수치는 원래 파일 바이트의 합계다.

기존 orphan 정리 스크립트의 조건을 실행 없이 대조한 결과 삭제 후보는 0개였다. v60의 미등록 지도 40개도 경기 DB 기록과 연결돼 있다. 파일 수가 DB 행 수보다 많다는 이유나 생성 버전이 오래됐다는 이유만으로 삭제하지 않는다.

**현행 분석의 중복 저장 구조**

v62 분석 파일 6,922개는 경기 기준 6,062개에 해당한다. 같은 경기의 다른 플레이어용 사본이 860개 더 있다. 본문 10쌍은 모두 `analyzeFormat: 2`, `projection: full`이고 이벤트 SHA-256이 같았다. 전체 파일 바이트는 플레이어별 identity 때문에 다르다.

경기당 이벤트 한 벌을 공유하면 현재 파일 크기 기준 약 997,979,087바이트를 줄일 가능성이 있다. 이는 보존할 파일을 남겨 계산한 구조상 추정치이며, 모든 경기의 이벤트 동일성을 검증한 절감량은 아니다. 현행 로더는 정확한 계정·모드 envelope를 검증하므로, 사본을 먼저 삭제하면 캐시 조회가 실패한다. 공통 이벤트와 요청 계정의 검증 정보를 분리하는 읽기·저장 변경이 선행돼야 한다. [분석 envelope 검증](https://github.com/ka6865/BGMS/blob/d17e209e3dfb47e1ecb18043398fe2d5c2de8dc6/lib/pubg-analysis/telemetryCacheKey.ts#L112)

v61도 추가 사본 175개가 있지만 이벤트 내용이 같은지 확인되지 않았으므로 v62 절감량과 합산해 확정하지 않는다.

기존 파일 10개를 메모리에서 Brotli로 압축해 원문 바이트의 복원을 확인했다. R2 파일은 교체하지 않았다. Node 22 실행의 결과다.

모든 경우 복원한 바이트가 원문과 일치했다. 표본에는 중복 파일이 포함되며 현행 2파일은 같은 경기의 서로 다른 플레이어용 사본이다. 이 비율을 버킷 전체에 적용해 몇 GB 줄거나 무료 범위에 들어간다고 확정할 수 없다. 품질 5가 우선 검토할 선택이다. [Node 22 Brotli API](https://nodejs.org/download/release/latest-jod/docs/api/zlib.html)

현재 R2 서버 로더는 gzip과 비압축 JSON을 읽는다. Brotli 전환은 메타데이터를 이용한 codec 식별, 기존 gzip 호환, 서버·브라우저 조회 검증, 조건부 교체와 복구 보관을 구현한 뒤 해야 한다. 운영파일을 바로 Brotli로 덮어쓰는 작업은 수행하지 않았다. [현행 R2 압축·읽기 코드](https://github.com/ka6865/BGMS/blob/d17e209e3dfb47e1ecb18043398fe2d5c2de8dc6/lib/pubg-analysis/r2Service.ts#L67)

**영구 보존의 가치와 현재 기능의 한계**

PUBG 공식 문서는 경기 데이터 보존을 14일로 설명한다. 보관 자료가 있는 28일·36일 된 경기 6개를 직접 조회했으며 모두 HTTP 404였다. 저장한 자료를 지운 뒤 PUBG에서 다시 받을 수 있다는 전제는 사용할 수 없다. 이미 확보한 CDN URL의 개별 수명까지 확인한 결과는 아니다. [PUBG 공식 보존 기간](https://documentation.pubg.com/en/making-requests.html#data-retention-period)

현재 지도 API는 R2를 읽기 전에 PUBG 매치 API를 호출하고 404에서 반환한다. 따라서 R2에 지도 파일이 남아 있어도 API에서 사라진 경기의 지도 URL을 새로 발급받지 못할 수 있다. 상세 분석은 유효한 현재 DB 결과를 먼저 반환하지만, 구버전·재계산 필요·분석 누락 경기는 PUBG 재조회로 진행해 R2 분석 파일까지 도달하지 못할 수 있다. 저장 자료로 과거 경기를 읽는 경로가 있어야 장기 보관의 서비스 가치를 활용할 수 있다. [지도 조회 순서](https://github.com/ka6865/BGMS/blob/d17e209e3dfb47e1ecb18043398fe2d5c2de8dc6/app/api/pubg/telemetry/route.ts#L101), [DB 분석 우선 반환](https://github.com/ka6865/BGMS/blob/d17e209e3dfb47e1ecb18043398fe2d5c2de8dc6/app/api/pubg/match/route.ts#L1312)

루트 표본은 단순 이벤트 배열이다. 공식 기본 스탯과 matchInfo를 함께 가진 구조가 아니다. 피해·킬·아이템·위치 기록은 남아 있지만, 구형 필터가 생략한 이벤트와 위치까지 복원하는 완전한 vendor 원본으로 간주하지 않는다. 추가 8파일에서는 이벤트 actor에 해당 닉네임의 식별 증거가 모두 있었다. 그러나 기존 backfill 스크립트는 배열에 없는 스탯을 0·99·현재 시각으로 대체할 수 있어 그대로 실행하면 안 된다. 이번에 그 스크립트를 실행하지 않았다.

| 유일한 지도 파일 | 원본으로 재생성 가능한지 확인할 때까지 보존 | 현재는 매치 메타데이터 만료가 재생성을 막을 수 있음 |
| 이미지·백업·인벤토리 | 역할에 맞게 유지 | 현재 용량이 작고 자산·복구에 사용됨 |

새 보관 구조에서는 이벤트 한 벌과 플랫폼·경기 식별자·공식 경기 attributes·참가자/팀/공식 스탯·본문 checksum을 함께 저장해야 한다. 이미 필터돼 있는 과거 자료는 보존 범위를 표시한다. 모든 기본 전적 수집에 무조건 전체 텔레메트리를 적재할 필요는 없다. 상세 분석이나 지도 재생, 벤치마크에 실제 사용하는 경기의 자료를 우선 보관한다.

R2 lifecycle 읽기 결과에는 완료된 객체를 만료시키는 규칙이 없었다. 미완료 multipart upload를 7일 후 중단하는 기본 규칙만 있다. 현재 완료 파일은 자동으로 오래된 순서대로 삭제되는 설정이 아니다. 이 설정을 수정하지 않았다. [Cloudflare 수명 정책](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)

**권장 작업 순서**

1. gzip·비압축 파일을 계속 읽으면서 Brotli 품질 5를 지원하고, 더 다양한 원본·지도 표본과 실제 서버·브라우저 흐름을 검증한다. 새 저장부터 적용하고 기존 파일은 복구 가능한 제한 배치로 전환한다.
2. 경기당 공통 이벤트 한 벌과 경기 메타데이터를 보관하는 읽기·저장 구조를 준비한다. 요청 계정 검증과 개인별 지도 데이터의 경계를 유지한다.
3. 구형 사본의 모든 식별 연결을 보존하고 복구 검증을 통과한 뒤, 준비된 후보별로 다시 참조·점유·본문을 확인해 정리한다. `pending`·유일 자료·미검증 입력은 유지한다.
4. 14일 지난 경기의 저장 자료 조회 경로를 개선해 장기 보관한 지도·분석 자료를 실제 서비스에서 사용한다.

고유 원본이나 지도에 30일·90일 자동 삭제 규칙을 바로 걸지 않는다. 필요한 원본과 메타데이터로 외부 API 없이 재생성할 수 있음을 검증한 파생 캐시부터 보존 기한을 적용한다. 작은 현재 저장비를 줄이기 위해 유일한 과거 자료를 없애는 판단은 권장하지 않는다. Infrequent Access는 무료분이 없고 조회 비용도 붙어 현재 크기에서는 Standard보다 유리하다고 판단할 근거가 없다. [Cloudflare 요금과 무료분](https://developers.cloudflare.com/r2/pricing/)

**검증 자료와 운영 적용 범위**

- [구형 식별·수명 정책·무손실 압축 검증](https://github.com/ka6865/BGMS/actions/runs/37231563655): 10개, 읽기 실패 0.

R2 접근 자격 증명은 기존 GitHub Secret을 사용했다. DB 키는 전체 참조 조회 단계에만 전달하고 후속 본문 검사에서는 제외했다. 외부 저장소 접근은 조회 명령으로 한정했다. 상세 키·닉네임·DB 목록은 실행별 AES-256-GCM으로 암호화하고, 키는 감사 전용 RSA 공개키로 감싸 암호문만 artifact로 7일 보관했다. 복호화한 자료와 조건부 대상 목록은 git 제외·접근 제한된 로컬 폴더에 보관한다.

처음 시도한 전체 조회는 대용량 분석 JSON 필드 조회에서 HTTP 500으로 중단됐다. 해당 필드를 제외한 식별·참조 조회로 전환해 성공했다. 분석 JSON은 별도의 소수 경기 조회로 확인했다. 실패한 실행에서 저장소나 DB를 변경한 작업은 없다.

진단 코드의 집중 테스트 14개, TypeScript, 대상 ESLint 및 actionlint가 통과했다. 초기 전체 `verify:core` 결과는 오류 0·기존 경고 44개다. 로컬 node_modules는 기존 설치물에 연결했고, 실제 진단 Actions에서는 lockfile로 `npm ci --ignore-scripts`를 수행했다. 애플리케이션 동작 변경과 운영 배포는 하지 않았다.

진단은 별도 `codex/r2-retention-audit` 브랜치에서 수동 실행했다. 조사 완료 후 그 브랜치의 임시 maintenance workflow를 main의 원래 정의로 복구했다. main의 Actions 설정·소스·환경 파일은 변경하지 않았으며, 이번 조사를 main으로 자동 병합하지 않는다.
