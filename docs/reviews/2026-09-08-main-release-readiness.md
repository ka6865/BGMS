## 1. 출시 전 해결할 데이터 적용 범위

### P1: 기본 랭킹까지 새 계산 표식으로 제한

`actions/rankings.ts:113` 및 동일 파일의 다른 랭킹 쿼리, `app/api/pubg/battle/route.ts:145`가 `calculation_version = 2`를 필수로 요구한다. 기존 필터/모집단 조건을 충족한 킬·피해량 등 기본 기록도 새 계산 표식이 없으면 제외한다.

운영 DB에서 최근 7일, 공식/경쟁전, solo/duo/squad 및 FPP, filter=8/population=1 조건으로 비교했다.

| 적용 조건 | 플레이어·경기 행 | 구별되는 player_id |
| --- | ---: | ---: |
| 기존 모집단 기준 | 1,927 | 306 |
| 계산 v2 추가 필수 | 4 | 2 |

이는 DB 후보 수이며 최종 화면의 순위 인원 수는 추가 집계 조건에 따라 달라진다. 기본 랭킹까지 이 표식을 일괄 요구하는 영향은 크다. 산식 변경에 영향 없는 원천 킬·피해량 등의 호환성을 확인한 뒤 기본 기록과 재계산이 필요한 전술 지표의 자격 조건을 분리하는 것을 권장한다. 잘못된 이전 전술 수치를 다시 신뢰하도록 되돌리는 것은 권장하지 않는다.

### P1: 기존 상세 분석의 대규모 보류와 자동 해소 경로 부재

`app/api/pubg/match/route.ts:1334`는 현재 RESULT v73이어도 계산 표식이 없으면 즉시 `409 PUBG_CALCULATION_UPGRADE_REQUIRED`를 반환한다. `squadAnalysis.ts:64`에서도 해당 경기를 제외한다. 서버 내 일괄 갱신 큐는 연결되어 있지 않으며, 이번 새 배치 도구는 운영자가 준비한 검증 원본 목록을 소비한다.

점검 시점 운영 저장 현황:

- v73 + 계산 표식 없음: 5,282행
- v73 + 계산 v2: 7행
- v72 + 계산 표식 없음: 9,055행
- 비교 표본(filter=8/population=1): 계산 v2 4행 / 표식 없음 4,763행

저장 행 개수는 사용자 수나 실제 요청 실패율이 아니다. 다만 기존 v73 캐시를 정상 identity로 조회하면 해당 조기 반환 조건에 걸리는 구조다. v72는 별도 경로이므로 9,055행을 같은 409 발생 수로 합산하지 않았다.

이전 배치 사전 점검의 최근 후보 100행은 prepared=0/current=2/benchmark_missing=30/raw_unavailable=68이었다. 68은 허용된 원본 카탈로그에서 확인하지 못했다는 뜻이며 영구 원본 부재를 입증하지 않는다. 이 사전 점검은 이번 운영 집계보다 이른 시점 결과다.

출시 전에는 최근 이용자 우선 재계산 또는 기본 전적을 유지하면서 변경 지표만 보류하는 단계적 적용 경로가 필요하다. 모든 과거 데이터를 복원해야만 출시할 수 있다는 뜻은 아니다. 재분석할 수 없는 경기와 일시 실패는 구별하고 Gemini 재호출로 해결하려 하지 않는다.

## 2. 회원 관리 변경의 적용 조건과 추가 개선

운영 DB에는 `user_lifecycle_events`와 `get_user_lifecycle_daily`가 아직 없다. 이번 추가 migration `20260907140000_user_lifecycle_events.sql`은 미적용 상태다. API는 누락 시 unavailable로 처리하므로 기존 관리 목록은 유지되지만 새 그래프는 확인 불가 상태다. 회원 증감 기능 출시에는 migration 적용 순서가 필요하다.

새 migration은 auth.users 트리거를 추가한다. 격리 PostgreSQL 검증에서 KST 첫날 오전 집계, soft-delete 후 hard-delete 중복 방지, 기존 계산/복구 RPC 시나리오를 통과했다. 운영 Auth와의 통합 점검은 별도다. Supabase 공식 문서도 사용자 트리거 실패가 가입을 막을 수 있음을 설명한다: [사용자 데이터 관리](https://supabase.com/docs/guides/auth/managing-user-data).

P2 코드 개선: `components/admin/GameDataEditor.tsx:408`의 기간별 요청에 취소 또는 최신 요청 식별 검사가 없다. 기간을 빠르게 바꾸고 이전 응답이 늦게 도착하면 `setUserMembership`에서 이전 기간 결과가 덮일 수 있다. 또한 기간 변경 때 전체 회원·활동 데이터를 다시 가져오므로 그래프 조회를 분리하면 부하를 더 줄일 수 있다. 이 요청 경합은 정적 코드로 확인한 조건이며 브라우저에서 지연 응답을 주입해 재현하지는 않았다.

- 이번 점검에서는 제품 코드 변경, 운영 migration, 대량 갱신, 커밋, 푸시, 병합을 하지 않았다.
