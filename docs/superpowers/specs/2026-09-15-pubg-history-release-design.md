# PUBG 전적 보존 단계 배포 설계

## 목표

사용자는 내부 수집 대기열을 보지 않고 BGMS에 저장된 전체 전적을 일반적인 전적 목록처럼 탐색한다. 운영자는 PUBG의 최근 14일 원본 보존 기간 안에 발견한 경기 ID를 백그라운드 워커로 안전하게 저장하고, 매치 보존·성과 계산·처치 상대 및 제재 추적을 순서대로 활성화한다.

## 현재 기준

- 운영 메인은 `origin/main`의 `3105790`이며 현재 작업 브랜치의 기준 커밋 `4e07a8d`보다 앞선 병합 커밋이다.
- 운영 DB에는 신규 마이그레이션 다섯 개가 적용됐지만 원격 메인에는 신규 워크플로가 없다.
- GitHub 저장소에 `PUBG_MATCH_RETENTION_ENABLED`, `PUBG_PERFORMANCE_ENABLED`, `PUBG_BAN_WATCH_ENABLED`, `PUBG_ENCOUNTER_CACHE_ENABLED` 활성화 변수가 없으므로 워커는 실행되지 않는다.
- 2026-09-15 실측에서 Steam `Zucchini__`는 저장 전적 62건, 빠른 캐시 20개, 발견 대기 100건이다. 대기 중 42건은 저장 전적과 겹치며 이 중 12건만 같은 공식 account ID가 저장되어 있다. 신규 미저장 경기는 58건이다.

## 사용자 경험

- `최근 20경기 요약`은 현재 플레이 흐름을 설명하는 고정 표본으로 유지한다.
- 매치 목록은 `저장된 전적 N경기 · P/T페이지`로 표시한다. `현재 20게임`은 사용하지 않는다.
- 전체·일반전·경쟁전·캐주얼·TDM 필터는 현재 페이지가 아니라 저장된 전체 전적에 서버에서 적용한다.
- `과거 기록 수집 중`, 대기 건수, unavailable 건수는 전적 화면에 표시하지 않는다.
- 실제 목록 API가 실패할 때만 재시도 가능한 오류를 표시한다.
- 수집이 끝난 새 경기는 다음 검색·페이지 이동·명시적 재조회에서 자연스럽게 나타난다. 시간 단위 워커를 기다리며 10초 간격으로 사용자 브라우저가 반복 조회하지 않는다.
- 전적 프로필에는 `나를 처치한 상대 보기` 진입점을 유지하고 처치·기절·관심 등록은 별도 페이지에서 제공한다.

## 데이터 경계

- `pubg_player_cache.recent_match_ids`와 `PlayerStatsResponse.recentMatches`는 최근 요약과 즉시 표시를 위한 최대 20개 경계다.
- `pubg_player_match_discovery`는 PUBG가 반환한 전체 매치 ID와 처리 상태를 보존하는 서버 전용 원장이다.
- `pubg_player_matches`는 사용자에게 페이지로 제공하는 저장 전적 원장이다.
- 사용자용 API는 저장 전적의 필터된 `totalCount`와 `totalPages`를 제공한다. discovery 상태는 서버 내부 워커와 운영 점검에서만 사용한다.
- 계정 ID가 동일하게 저장된 기존 경기는 워커가 PUBG 원본을 다시 요청하지 않고 완료 처리할 수 있다. 닉네임만 같은 과거 행은 identity 증거로 사용하지 않고 공식 참가자 ID를 다시 확인한다.

## 단계별 배포

### 1단계: 전적 보존 기반

전체 건수 표시, 서버 전체 필터, 사용자 대기 문구 제거, 불필요한 진행 폴링 제거, 수집 워커 `--limit` 안전장치와 검증된 중복 건너뛰기를 구현한다. 워커가 꺼진 상태로 코드를 배포한 뒤 3건과 20건 canary를 통과하면 매치 워커만 활성화한다.

### 2단계: 성과 및 랭킹

저장된 기본 전적을 성과 작업으로 연결하고 일일 30건 예산 안에서 계산한다. 랭킹은 DB RPC가 플랫폼·비공개·계산 버전을 일관되게 적용하는지 확인한 뒤 성과 워커만 활성화한다.

### 3단계: 처치 상대 및 제재 추적

로그인 사용자에게 별도 상대 페이지를 제공하고 서버에서 검증한 경기 상대만 개인 관심 목록에 등록한다. 매치 워커가 안정화된 뒤 제재 워커와 만료 캐시 정리 워커를 각각 활성화한다.

## 배포와 복구

- 현재 변경은 최신 `origin/main` 위로 재배치하고 기능별 커밋으로 분리한다.
- 기능 브랜치에서 `develop` PR과 Preview QA를 거친 뒤 `develop`에서 `main` PR을 만든다.
- 메인 배포 시 모든 워커 변수는 비활성 상태를 유지한다.
- canary 결과에서 `saved`, `retry`, `unavailable`, `rateLimited`, 실행 시간을 확인한다.
- 반복 429, DB 오류, 대기량 증가가 확인되면 해당 활성화 변수를 제거하거나 `false`로 바꾼다.
- 앱 롤백 시 DB 테이블과 저장 데이터는 삭제하지 않는다. 마이그레이션은 기존 메인 코드와 공존한다.

## 완료 조건

- Zucchini__ 전적 화면이 저장 전적 62건과 4페이지를 일관되게 표시한다.
- 필터 결과와 페이지 수가 전체 저장 전적 기준으로 계산된다.
- 사용자 화면과 접근성 트리에 discovery 대기 수가 노출되지 않는다.
- `--limit 3` 실행이 최대 3개만 claim하고, 동일 account ID로 이미 저장된 경기는 외부 매치 요청 없이 완료된다.
- 핵심 테스트, 타입 검사, ESLint, 프로덕션 빌드, 마이그레이션 검증과 375/390/430px 모바일 QA를 통과한다.
- 메인 배포 후 canary 전까지 워커가 자동 실행되지 않는다.
