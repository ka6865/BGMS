# BGMS OP.GG형 전적 페이지 리디자인 설계

- 작성일: 2026-08-09
- 상태: 대화에서 디자인 승인 완료, 문서 검토 대기
- 대상: `/stats`, `/stats/[platform]/[nickname]`
- 기준 방향: OP.GG형 균형 레이아웃 + BGMS 블랙·골드 정체성 + 고밀도 광고 수익화

## 1. 요약

BGMS 전적 검색 화면을 OP.GG처럼 빠르게 훑을 수 있는 구조로 재편한다. 색상과 브랜드 표현은 BGMS의 블랙·골드 체계를 유지하고, 플레이어 프로필·핵심 통계·최근 매치의 우선순위를 명확하게 만든다.

데스크톱 결과 화면은 중앙 2열 콘텐츠를 사용한다. 왼쪽에는 게임 수·핵심 지표·AI 한줄 요약을 두고, 오른쪽에는 접을 수 있는 최근 매치 목록을 둔다. 광고는 Google AdSense와 Kakao AdFit의 역할을 분리한다. Google은 자동 사이드 레일·앵커·fluid 인피드를 담당하고, AdFit은 고정 규격 인페이지 배너를 담당한다.

기존 PUBG API, AI 분석, 텔레메트리, 리플레이 데이터 계약은 변경하지 않는다. 현재 비대한 `StatSearch`와 `MatchCard`의 책임을 화면 단위 컴포넌트로 분리하되, 이번 리디자인과 무관한 도메인 로직은 재작성하지 않는다.

## 2. 목표와 성공 기준

### 목표

1. 검색 결과 첫 화면에서 플레이어 정체성, 현재 랭크, 핵심 지표, 최근 매치를 순서대로 이해할 수 있게 한다.
2. OP.GG 수준의 높은 정보 밀도를 제공하되 BGMS AI 분석의 차별점을 유지한다.
3. 광고를 많이 배치하면서도 콘텐츠와 명확히 구분하고 오클릭·가림·레이아웃 이동을 방지한다.
4. 데스크톱과 모바일에서 동일한 정보 우선순위를 유지하되 화면 특성에 맞게 재배치한다.
5. 검색·광고·프로필·매치 렌더링의 책임을 분리해 이후 수정과 테스트 비용을 낮춘다.

### 성공 기준

- 1440×900 데스크톱 첫 화면에서 프로필, 상단 광고, 핵심 통계, 최근 매치 시작점이 함께 보인다.
- 1600px 이상에서 Google 좌·우 사이드 레일이 노출되는 경우 중앙 콘텐츠를 가리지 않는다.
- 모바일에서는 고정 하단 내비게이션과 앵커 광고가 겹치지 않는다.
- CSS로 숨겨진 광고 컴포넌트가 네트워크 요청을 발생시키지 않는다.
- 광고 로드 전후에 주요 콘텐츠가 갑자기 밀리지 않는다.
- 기존 검색, 시즌 전환, 갱신, 비교 진입, 무기 분석, 매치 상세, AI 분석, 리플레이 기능이 유지된다.
- 검색 실패나 일부 매치 실패가 전체 결과 화면을 제거하지 않는다.

## 4. 현재 제약

- `components/stat/StatSearch.tsx`는 약 1,400줄이며 검색, API, 인증, 프로필, 탭, 광고, 매치 목록을 함께 소유한다.
- `components/stat/MatchCard.tsx`는 약 2,100줄이며 요약 행과 상세 분석을 함께 소유한다.
- 기존 광고 컴포넌트는 `AdSenseBanner`와 `AdfitBanner`로 나뉘며, 개발 환경 플레이스홀더와 프로덕션 스크립트 초기화를 이미 제공한다.
- 현재 통계 화면은 320×100, 728×90, 160×600, fluid 인피드 슬롯을 보유한다.
- 반응형 광고를 CSS `hidden`으로만 감추기 때문에 보이지 않는 슬롯도 마운트될 수 있다.
- AdSense 전역 자동 광고 스크립트는 모든 경로에서 로드된다.
- 플레이어 API에는 닉네임, 플랫폼, 시즌, 모드별 통계, 최근 매치, 클랜, 제재, 갱신 시각이 있으나 별도 프로필 이미지와 매치 페이지네이션은 없다.

## 5. UX 구조

### 5.1 검색 초기 화면

검색 초기 화면은 콘텐츠가 적으므로 광고 밀도를 제한한다.

1. 페이지 제목과 한 줄 가치 제안
2. 플랫폼 선택, 닉네임 검색, 비교 모드 진입
3. 최근 검색과 즐겨찾기
4. 기능 설명은 세 개 이하의 작은 카드로 축소
5. AdFit 가로 배너 한 개: 모바일 320×100, 768px 이상 728×90
6. Google 앵커 광고

초기 화면에는 매치 인피드와 수동 사이드 광고를 두지 않는다. 검색 초기 셸 전체에 `google-side-rail-overlap="false"`를 적용해 Google 자동 사이드 레일이 해당 섹션과 겹치지 않게 한다.

### 5.2 플레이어 결과 헤더

결과 화면의 첫 블록은 다음 순서를 사용한다.

1. 플랫폼, 닉네임, 클랜 태그
2. 현재 랭크와 RP의 canonical 표시
3. 갱신 상태와 최근 업데이트 시각
4. 즐겨찾기, 비교, 무기 분석
5. 시즌 선택
6. AdFit 가로 배너

제재 상태는 정상 사용자의 시선을 빼앗지 않도록 작은 상태 배지로 유지한다. 문제가 있을 때만 강조한다.

### 5.3 중앙 2열 콘텐츠

1024px 이상 데스크톱 중앙 콘텐츠는 최대 1,200px 안에서 `320px minmax(0, 1fr)` 두 열과 16px 간격을 사용한다.

- 왼쪽 320px: 게임 수, KDA, 평균 딜량, Top 10 비율, 선호 모드, AI 한줄 요약
- 오른쪽 나머지: 최근 매치 필터와 접힌 매치 행

현재 랭크와 RP는 프로필 헤더에서만 표시한다. 요약 레일에서는 반복하지 않는다. 모바일도 프로필 헤더에 압축된 랭크를 한 번만 표시한다.

왼쪽 요약은 화면 상단에서만 보이며 장시간 sticky로 고정하지 않는다. 긴 스크롤에서 콘텐츠보다 광고·요약이 과도하게 따라오는 것을 방지한다.

### 5.4 매치 행

접힌 매치 행은 다음 정보만 표시한다.

- 순위
- 맵과 게임 유형
- 킬, 피해량, DBNO, 생존 시간
- AI 등급 또는 핵심 평가
- 승리·상위권·일반·저성과 상태를 구분하는 절제된 왼쪽 색상선
- 상세 펼치기 버튼

팀 목록, 무기 상세, 티어 근거, 지도, AI 코칭, 리플레이는 펼친 상태에서 기존 기능을 사용한다. 접힌 행에서 모든 상세 데이터를 반복 표시하지 않는다.

### 5.5 모바일

모바일은 단일 열로 재배치한다.

1. 검색창
2. 스크롤 이후 나타나는 닫기 가능한 Google 상단 앵커
3. 압축된 플레이어 프로필
4. AdFit 320×100
5. 2×2 핵심 지표
6. AI 한줄 요약
7. 최근 매치 목록
8. 여섯 번째 매치 이후 Google 인피드 한 개

모바일 하단에는 기존 `BottomNav`가 있으므로 Google 앵커 위치는 사이트 전역에서 `Top only`로 설정한다. 이 설정은 데스크톱에도 동일하게 적용한다. 긴 상세 내용은 모달보다 인라인 펼침 또는 기존 전체화면 흐름을 우선한다.

### 5.6 시각 토큰과 반응형 규칙

전적 경로는 기존 BGMS 토큰을 그대로 사용하고 전역 팔레트를 바꾸지 않는다.

- 기본 배경: `#0d0d0d`
- 카드 표면: `#161616`
- 강조 표면: `#1f1f1f`
- 주 액센트: `#F2A900`
- 기본 테두리: `rgba(255,255,255,0.08)`
- 본문/보조/비활성 텍스트: 흰색 100%/60%/30%
- 양호 상태: `#2dd4bf`와 상태 텍스트
- 저성과·오류 상태: `#ef6b6b`와 상태 텍스트
- AI 강조: 기존 보라 계열을 한 개의 AI 카드와 등급에만 사용
- 페이지 제목: 24px/32px
- 플레이어 닉네임: 모바일 20px/28px, 데스크톱 24px/32px
- 핵심 수치: 20px/24px
- 카드 라벨: 11px/16px
- 매치 주요 정보/보조 정보: 14px/20px, 12px/18px

반응형 규칙은 다음과 같다.

- `<768px`: 단일 열, 핵심 지표 2×2, AdFit 320×100
- `768~1023px`: 단일 열, 핵심 지표 4열, AdFit 728×90
- `>=1024px`: 320px 요약 레일 + 가변 매치 열
- 전체 콘텐츠 최대 폭: 1,200px
- 카드 간격: 모바일 8px, 태블릿·데스크톱 16px
- 주요 터치 대상 최소 크기: 44×44px
- 닉네임: 한 줄 말줄임, 전체 값은 접근 가능한 이름과 `title`로 제공
- AI 한줄 요약: 모바일 2줄, 데스크톱 3줄 후 `더보기`로 확장

새 스타일은 `.stats-page` 아래에 한정하거나 컴포넌트 클래스에 직접 적용한다. `:root` 색상, 공용 헤더, 다른 경로의 카드 스타일은 변경하지 않는다.

## 6. 광고 설계

### 6.1 공급자 역할

| 공급자 | 역할 | 구현 방식 |
| --- | --- | --- |
| Google AdSense | 좌·우 사이드 레일 | Auto ads, Google이 충분한 가로 공간을 판단한 데스크톱 |
| Google AdSense | 닫기 가능한 앵커 | Auto ads `Top only`, 모바일·데스크톱 공통 |
| Google AdSense | 매치 인피드 | fluid 수동 슬롯 |
| Kakao AdFit | 결과 상단 가로 배너 | 728×90 데스크톱·태블릿, 320×100 모바일 |
| Kakao AdFit | 긴 결과 중간 배너 | 열 번째 매치 이후 728×90 |

AdFit 160×600은 통계 결과 화면의 기본 슬롯으로 사용하지 않는다. Google 자동 사이드 레일과 겹칠 가능성이 있고 광고 미충족 여부를 신뢰성 있게 감지해 대체하는 계약이 현재 없기 때문이다. 다른 페이지의 기존 160×600 슬롯은 이번 범위에서 변경하지 않는다.

### 6.2 결과 화면 광고 매트릭스

| 화면 | 상단 AdFit | Google 인피드 | 중간 AdFit | Google 사이드 레일 | Google 앵커 |
| --- | --- | --- | --- | --- | --- |
| `<768px` | 320×100 | 6번째 이후 1개 | 없음 | 없음 | 상단 |
| `768~1279px` | 728×90 | 5·15번째 이후 | 10번째 이후 728×90 | 플랫폼 판단, 수동 슬롯 없음 | 상단 |
| `1280~1599px` | 728×90 | 5·15번째 이후 | 10번째 이후 728×90 | 플랫폼 판단, 겹침 방지 | 상단 |
| `>=1600px` | 728×90 | 5·15번째 이후 | 10번째 이후 728×90 | 좌·우 허용 | 상단 |

Google Auto ads의 실제 노출, 채움, 사이드 레일 노출 시작 폭은 플랫폼 판단에 따르며 모든 위치가 항상 동시에 채워진다고 가정하지 않는다. 1600px은 강제 노출 breakpoint가 아니라 좌·우 레일이 함께 노출돼도 안전해야 하는 QA 기준이다.

Google Auto ads 설정은 사이트 전역에 영향을 준다. 저장소 구현은 전적 셸의 안전 영역과 수동 슬롯을 담당하고, AdSense 콘솔에서는 다음 운영 설정을 별도로 적용한다.

- Side rail position: `Left and right`
- Anchor position: `Top only`
- Auto ads 미리보기에서 검색 초기 화면과 수동 AdFit·AdSense 영역의 중복 배치 제외

콘솔 설정 변경은 저장소 커밋만으로 완료되지 않는다. 구현 완료 후 사용자가 직접 적용하거나, 별도 명시적 승인을 받은 브라우저 작업으로 수행한다.

Auto ads와 수동 광고의 소유권은 다음과 같이 고정한다.

- `app/layout.tsx`는 AdSense main script 한 개만 소유하며 route 전환 때 중복 삽입하지 않는다.
- `ResponsiveAdSlot`은 수동 AdSense 인피드와 AdFit 고정 배너만 관리한다.
- 좌·우 사이드 레일과 상단 앵커는 JSX 컴포넌트로 직접 만들지 않고 AdSense Auto ads가 관리한다.
- 전적 콘텐츠 영역은 Auto ads 인페이지 배너 제외 영역으로 설정해 수동 5·10·15 배치와 중복되지 않게 한다.
- 검색 초기 셸은 `google-side-rail-overlap="false"`로 사이드 레일 겹침을 막는다. 이 속성은 앵커를 끄지 않으며 앵커는 사이트 전역 `Top only` 설정을 따른다.
- 결과 중앙 콘텐츠 셸에도 `google-side-rail-overlap="false"`를 적용해 플랫폼이 띄운 좌·우 레일이 1,200px 콘텐츠 안으로 침범하지 않게 한다.

### 6.3 광고 안전 규칙

- 광고 슬롯은 `광고` 또는 `Advertisement`로 명확히 구분한다.
- 광고 주변에 화살표, 글로우, 추천 문구, 펼치기 버튼을 배치하지 않는다.
- AdFit은 고정 폭·높이를 렌더 전에 예약한다.
- fluid AdSense는 130px 최소 높이를 예약하되 실제 광고를 자르지 않는다.
- 브레이크포인트별 슬롯은 CSS로 숨기는 대신 조건부 마운트한다.
- 동일한 AdFit placement는 한 번만 마운트·초기화한다. 서로 다른 두 개의 실제 AdFit 슬롯은 Kakao가 제공하는 단위별 스크립트 계약을 유지하며, 검증되지 않은 전역 단일 초기화 방식으로 합치지 않는다.
- 광고 실패, 광고 차단, 미충족은 콘텐츠 로딩과 오류 상태에 포함하지 않는다.
- 수동 광고와 Auto ads가 같은 영역을 차지하지 않도록 제외 영역을 선언한다.
- 광고 수와 면적이 게시자 콘텐츠보다 커지지 않도록 렌더 가능한 매치 수에 따라 고밀도 구성을 적용한다.
- 5번째 이후 광고는 렌더 가능한 매치가 6개 이상일 때, 10번째 이후 광고는 11개 이상일 때, 15번째 이후 광고는 16개 이상일 때만 삽입한다. 광고가 목록의 마지막 항목이 되지 않게 한다.

관련 정책:

- [Google AdSense 사이드 레일 위치 설정](https://support.google.com/adsense/answer/16242705?hl=en)
- [Google Publisher Policies: 광고보다 적은 게시자 콘텐츠 금지](https://support.google.com/publisherpolicies/answer/11169917?hl=en)
- [Kakao AdFit 운영정책](https://adfit.kakao.com/web/html/use.html)

## 7. 컴포넌트 경계

### 7.1 화면 셸

`StatsPageShell`

- 검색 대상과 정규 URL 상태를 관리한다.
- 로딩, 준비, 갱신, 오류 상태를 조정한다.
- 프로필, 요약, 매치 피드, 광고 배치를 조립한다.
- 상세 통계 계산이나 광고 스크립트 초기화를 직접 수행하지 않는다.

`useStatsPageController`

- 플레이어 요청, 매치 요약 요청, 갱신, 요청 취소와 최신 응답 우선 규칙을 소유한다.
- 시즌, 상위 탭, 통계 모드, 파티 크기, 매치 필터 상태를 한 곳에서 조정한다.
- 표시 컴포넌트에 계산된 값과 이벤트 콜백만 전달한다.

### 7.2 검색

`StatsSearchBar`

- 플랫폼 선택, 닉네임 입력, 자동완성, 최근 검색, 즐겨찾기를 담당한다.
- 최근 검색과 즐겨찾기는 기존 `string[]` 저장 계약을 유지해 `/stats/battle`과의 호환성을 보존한다.
- 빠른 검색은 화면에서 현재 선택한 플랫폼을 사용한다. 플랫폼까지 영구 보존하는 스키마 개선은 별도 작업이다.
- 검색 성공 시 `/stats/{platform}/{nickname}`으로 이동한다.

### 7.3 프로필과 요약

`PlayerProfileHeader`

- 플레이어 정체성, 랭크, 갱신, 시즌, 액션을 표시한다.
- 데이터 요청을 직접 하지 않고 이벤트 콜백을 받는다.

`StatsOverviewRail`

- 모드별 핵심 지표와 AI 한줄 요약을 표시한다.
- 빈 통계는 `0`으로 오인하지 않고 `기록 없음`으로 표현한다.

`StatsSectionTabs`

- `overview`와 `squad` 상위 탭을 표시하고 선택 이벤트를 컨트롤러에 전달한다.
- 컨트롤러가 URL의 `tab`에서 복원한 초기 탭을 받는다.
- 컨트롤러가 보존한 `groupKey`를 `SquadAnalysisPanel`에 전달한다.

`StatsOverviewControls`

- 경쟁전·일반전과 솔로·듀오·스쿼드 요약 선택을 표시하고 변경 이벤트를 컨트롤러에 전달한다.
- 매치 피드의 전체·일반·경쟁·TDM 필터와는 독립적으로 동작한다. 한쪽 선택이 다른 쪽을 자동 변경하지 않는다.

### 7.4 매치 목록

`MatchFeed`

- 컨트롤러가 소유한 전체·일반·경쟁·TDM 선택을 표시하고 변경 이벤트를 전달한다.
- 필터링된 매치 배열 안의 광고 삽입 지점을 소유한다.
- 누락된 매치를 제외하고 렌더 가능한 목록을 유지한다.

`CompactMatchRow`

- 빠르게 훑는 데 필요한 요약만 표시한다.
- 클릭 또는 키보드 조작으로 상세를 연다.

`ExpandedMatchDetails`

- 기존 `MatchCard`의 상세 분석, 팀 정보, 지도, AI, 리플레이를 감싼다.
- 상세 데이터 요청은 펼친 뒤 시작하거나 기존 캐시를 사용한다.

### 7.5 광고

`ResponsiveAdSlot`

- `placement`, `provider`, `viewportClass`를 입력으로 받는다.
- 현재 화면에 해당하지 않는 슬롯은 자식 광고 컴포넌트를 마운트하지 않는다.
- 서버 렌더와 hydration 전 `viewportClass`는 `unknown`이며 공급자 스크립트를 실행하지 않는다.
- `unknown` 동안 CSS 미디어 쿼리로 슬롯 높이만 예약하고, 클라이언트 미디어 쿼리가 확정된 뒤 해당 규격 하나만 마운트한다.
- 개발·테스트에서는 실제 네트워크 요청 대신 규격 플레이스홀더를 표시한다.

`statsAdPlacements`

- 전적 화면의 공급자, 규격, 위치, 화면 조건을 선언형 데이터로 보관한다.
- UI 컴포넌트 안에 광고 단위 ID와 매치 인덱스를 흩어 놓지 않는다.

기존 `AdSenseBanner`와 `AdfitBanner`는 공급자별 렌더러로 재사용하되 초기화 계약을 섞지 않는다. `AdSenseBanner`는 전역 main script를 공유하고 명시적인 크기 계약을 지원한다. `AdfitBanner`는 Kakao의 단위별 스크립트 방식을 유지하면서 동일 placement의 중복 마운트만 방지한다.

## 8. 상태와 데이터 흐름

### 8.1 기본 흐름

1. 서버 페이지가 경로의 `platform`과 `nickname`을 `StatsPageShell`에 전달한다.
2. 셸이 기존 플레이어 API에서 프로필·시즌·최근 매치 ID를 가져온다.
3. 기본 결과를 먼저 표시한다.
4. 기존 `matches-summary` 배치 요청이 최대 20개의 접힌 매치 행을 채운다.
5. 매치 상세는 사용자가 펼친 시점에 기존 분석·텔레메트리 경로를 사용한다.
6. 시즌, 모드, 개인·스쿼드 탭 변경은 플레이어 정체성을 유지한 채 필요한 영역만 갱신한다.
7. URL의 `tab=squad`와 `groupKey`를 복원해 공유 링크가 같은 스쿼드 화면을 연다.

### 8.2 화면 상태

별도 상태 관리 라이브러리를 추가하지 않고 다음 상태를 명시적으로 구분한다.

- `idle`: 검색 초기 화면
- `loading`: 최초 플레이어 검색
- `ready`: 기본 결과 표시
- `refreshing`: 기존 결과를 유지한 채 갱신
- `partial`: 일부 매치 요약 또는 상세만 실패
- `error`: 표시할 기존 결과가 없는 검색 실패

`partial`은 내부적으로 다음 원인을 구분한다.

- `summary_batch_failed`: 매치 요약 배치 요청 전체 실패
- `summary_missing`: 특정 매치 요약 누락
- `detail_failed`: 펼친 매치 상세 실패
- `analysis_failed`: AI·텔레메트리 분석 실패

### 8.3 URL 상태

- 검색 대상은 경로에 유지한다.
- `tab=squad` 공유 URL은 실제 스쿼드 탭을 연다.
- `groupKey`는 스쿼드 탭 초기화와 공유 링크에서 보존한다.
- 시즌, 통계 모드, 파티 크기, 매치 필터는 URL에 쓰지 않고 현재 페이지의 로컬 UI 상태로 유지한다.
- 잘못된 플랫폼 또는 빈 닉네임은 검색 초기 화면 또는 명확한 오류로 복구한다.

### 8.4 동시 요청 규칙

- 플레이어·시즌이 바뀌면 이전 플레이어 요청과 매치 요약 요청을 `AbortController`로 취소한다.
- 각 검색에는 증가하는 `requestId`를 부여하고 현재 ID와 일치하는 응답만 상태에 반영한다.
- 같은 플레이어·시즌의 중복 요청은 진행 중 가드로 합친다.
- 수동 갱신은 기존 `ready` 결과를 유지한 `refreshing` 상태에서 수행한다.
- 매치 상세, AI, 텔레메트리 실패는 해당 행 내부에만 반영하며 프로필과 다른 매치 상태를 덮어쓰지 않는다.

## 9. 오류 처리

- `not_found`: 플랫폼과 대소문자 확인 안내 및 추천 플레이어 제공
- `rate_limit`: 재시도 가능 시간을 안내하고 반복 요청을 막음
- `server`: 기존 결과가 있으면 유지하고 갱신 실패 알림만 표시
- `partial match`: 배치 요약에서 찾지 못한 매치는 목록에서 제외한다. 접힌 요약이 있는 상태에서 상세 요청만 실패하면 행은 유지하고 상세 영역에 재시도 버튼을 표시한다.
- `summary_batch_failed`: 프로필과 시즌 요약은 유지하고 매치 영역에 전체 재시도 버튼을 표시한다.
- `analysis_failed`: 접힌 매치와 기본 상세는 유지하고 AI·텔레메트리 섹션만 재시도할 수 있게 한다.
- `expired match`: 기존 만료 정책을 유지하고 분석 불가 이유를 명확히 표시
- `ad blocked/no fill`: 사용자 오류로 표시하지 않고 콘텐츠를 정상 유지
- `script error`: 광고 공급자 단위로 격리하고 다른 공급자나 콘텐츠에 전파하지 않음

오류 메시지는 페이지 상단 전체 폭 모달보다 해당 기능 근처의 인라인 상태와 토스트를 우선한다. 검색할 플레이어 자체가 없을 때만 결과 영역 전체 오류를 사용한다.

## 10. 접근성·성능

- 모든 탭과 매치 행은 키보드로 조작할 수 있어야 한다.
- 접힘 상태는 `aria-expanded`로 노출한다.
- 광고 컨테이너는 의미가 분명한 `aria-label`을 사용한다.
- 색상만으로 승리·패배·등급을 구분하지 않고 텍스트를 함께 표시한다.
- 프로필과 매치 목록의 주요 텍스트는 WCAG AA 명암 대비를 목표로 한다.
- 상세 지도와 AI 컴포넌트는 필요할 때 동적 로드한다.
- 브레이크포인트 판정은 중복 `resize` 리스너보다 공유 미디어 쿼리 훅을 사용한다.
- 광고 초기화는 공급자 계약에 맞게 중복을 방지한다. AdSense main script는 공유하고 AdFit은 동일 placement만 멱등 처리한다.

| 테스트, 실제 광고 검수, 안정화 | 2~3일 |
| 합계 | **8.5~13.5 개발일** |

현실적인 캘린더 일정은 리뷰와 실제 광고 채움 확인을 포함해 약 2~3주다. 이 범위는 다음을 전제로 한다.

- 기존 API와 분석 계산을 변경하지 않는다.
- 새로운 일러스트나 랭크 자산을 제작하지 않는다.
- 디자인 수정 라운드는 한 차례다.
- AdSense·AdFit 계정과 현재 광고 단위가 정상 상태다.
- AdSense 콘솔의 사이트 전역 Auto ads 설정 변경과 플랫폼 심사 대기 시간은 개발일에 포함하지 않는다.

신규 통계 API, 매치 페이지네이션, 프로필 이미지 시스템을 추가하면 별도 3~5개발일이 필요하다. 금액 견적이 필요하면 위 개발일에 사용하는 1일 단가를 곱한다.

## 14. 위험과 대응

| 위험 | 대응 |
