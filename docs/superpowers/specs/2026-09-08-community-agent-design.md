# BGMS 커뮤니티 운영 비서 설계

작성일: 2026-09-08
상태: 사용자 검토용. 구현·배포·자동 게시를 실행한 문서가 아니다.

## 1. 합의한 방향과 구현 순서

사용자는 외부 PUBG 커뮤니티의 최근 반응과 정보를 참고해 글을 쓰고, 최종적으로 BGMS 안의 댓글과 답글까지 응대하는 비서를 원한다. 서버에서 기존 Gemini 연동을 활용하고 Codex는 개발, 운영 분석, 지침 개선을 맡는다. Gemini는 현재 사용 중인 무료 티어를 전제로 한다. 오류가 잦아지면 사용자가 유료 전환을 결정한다. 자동 결제나 유료 서비스 추가는 범위에 없다.

초기 운영 제안은 AI 비서 계정으로 하루 최대 1글, 향후 댓글·답글 합계 하루 최대 10개다. 한도를 채우기 위해 글을 만들지는 않는다. 정상적인 글마다 승인을 요구하는 방식 대신 사용자가 설정한 범위에서 실행한다. 신고, 분쟁, 계정 제재는 운영자가 처리한다.

전체를 두 개발 단위로 나눈다.

1. **이번 설계의 구현 대상:** 세 출처의 수집 상태 관리, 근거 저장, 주제 선정, 글 작성, 품질 검사, 제한적 자동 게시, 관리자 기록과 중지 기능.
2. **다음 설계 대상:** BGMS 댓글 감지, 대화 문맥 구성, 댓글·답글 생성과 게시, 중복·자기 대화 방지. 1단계의 근거와 실행 기록을 재사용하되 별도 설계·계획으로 진행한다.

외부 디시·카페·유튜브에는 글이나 댓글을 등록하지 않는다. 기존 Codex 초안 자동화 제안은 서버 자동 게시 기능과 별개다. 서버 운영 전 중복 실행 여부를 확인하고 발행 담당을 하나로 정한다.

## 2. 기존 코드에서 확인한 기반

- `app/api/admin/bot/run/route.ts`: Gemini 함수 호출, 관리자 인증, 실행·단계 기록. 현재 발행은 승인 요청으로 처리한다.
- `lib/admin-agent/tools.ts`: Tavily 검색, 게시글 생성·수정 및 콘텐츠 발행 승인 도구. Tavily 키의 설정 여부나 운영 성공 여부는 이번 조사에서 검증하지 않았다.
- `lib/admin-agent/content.ts`: 내부 DB 데이터를 이용한 고정 형식 초안. 외부 반응을 정기 수집해 글을 생성하는 파이프라인은 아니다.
- `lib/admin-agent/content-performance.ts`: 게시글 조회·좋아요·댓글 집계. 향후 봇 댓글을 성과에서 제외하도록 보완해야 한다.
- `app/api/board/comments/route.ts`, `types/board.ts`: 댓글과 부모 댓글 식별자 기반 답글 구조.
- `.github/workflows/daily-tasks.yml`: 기존 예약 실행과 패치노트 동기화. 커뮤니티 작업의 실패가 기존 유지보수를 막지 않게 실행을 분리한다.

이번 조사는 코드와 공개 문서의 읽기 검토다. 운영 DB, 외부 API 키 유효성, 무료 잔여 한도, 실서비스 게시 성공은 검증하지 않았다.

디시 페이지에는 다른 갤러리의 추천 콘텐츠와 광고도 함께 나온다. 페이지 전체를 그대로 모델에 넣지 않고 `battlegrounds`의 게시글 영역, 게시글 ID, 날짜를 검증해 추출한다. 광고, 타 갤러리, 공지의 반복 수집은 제외한다.

카페 검색 결과의 요약은 본문을 읽은 것과 구분한다. 검색 응답의 생성 시각을 게시글 작성 시각으로 사용하지 않는다. 작성 시각이 검증되지 않은 자료는 최신 24시간/7일 반응 집계에서 제외하고 발견용으로만 사용한다. 다른 카페를 몰래 대체 출처로 사용하지 않는다.

유튜브는 영상 제목·설명과 댓글의 근거 범위를 구분한다. 영상 제목만으로 영상 속 설명이나 수치를 추정하지 않는다. 자막 다운로드 API에는 영상 편집 권한이 필요하므로 타인 영상의 자막을 모두 가져오는 기능은 포함하지 않는다. 댓글 비활성화는 수집 실패와 구분한다. 공식 영상이라는 사실과 댓글 작성자의 의견은 별도로 기록한다.

각 수집기는 운영 전에 접근 조건과 제공자 사용 조건을 확인한다. 로그인·가입·차단 우회는 하지 않고 읽을 수 없는 출처는 상태와 이유를 남긴다. 공식 PUBG 패치노트는 기존 동기화 경로를 활용한 사실 확인 자료이며 이용자 민심 표본에는 넣지 않는다.

## 4. 실행 흐름과 책임

예약 실행 → 출처별 수집 → 정규화·중복 제거 → 주제 후보 → Gemini 초안 → 검증 → 발행 대기 → 제한 정책 재검사 → 게시 → 결과 기록 순으로 처리한다.

| 단위 | 입력과 출력 | 책임 |
| --- | --- | --- |
| 출처 수집기 | 출처 설정·마지막 성공 지점 → 자료 목록·수집 결과 | 출처별 API/HTML 차이를 처리하고 확인 범위를 표시 |
| 근거 저장 | 정규화 자료 → 근거 ID | 재사용, 날짜 검증, 중복 제거, 출처 추적 |
| 편집 단계 | 근거 묶음·최근 BGMS 글 → 주제·초안 | Gemini로 분류·설명·작성. 게시 권한은 갖지 않음 |
| 검증·발행 단계 | 검증된 초안 ID → 게시글 ID 또는 보류 사유 | 일일 한도, 계정, 출처, 중복, HTML 정제, 상태 검사 |
| 관리자 화면 | 실행·근거·초안·결과 → 운영 상태 | 중지·재개, 출처별 상태, 보류 사유, 글 확인, 한도 설정 |

첫 실행기는 GitHub Actions의 별도 커뮤니티 workflow로 제안한다. 기존 유지보수와 독립적으로 실패·재실행할 수 있게 한다. 매일 한국시간 오전 9시를 예약 기준으로 사용하되 실제 시작 시각이 지연될 수 있으므로 정확한 정각 발행을 보장하지 않는다. 예약 시점에 최근 자료를 수집하고 발행까지 이어간다. 1단계에서 별도 큐 서비스나 상시 서버를 추가하지 않는다.

운영 API의 제한된 실행 경로가 인증과 정책을 검사한다. 실행기는 저장된 초안 ID를 전달하며 임의 SQL이나 관리자 작업을 요청할 수 없다. 구현 시 기존 인증·게시글 저장·HTML 정제 방식을 재사용하고 새 에이전트 전용 경로를 검증한다.

## 5. 초기 수집·호출 기본값

다음 값은 운영 측정 후 관리자가 낮추거나 조정할 수 있는 제안 기본값이다. 무료 사용 가능량에 대한 보장이 아니다.

- 디시: 실행당 최신 목록 최대 2페이지, 글 후보 최대 60개, 관련성이 높은 공개 본문 최대 10개.
- 카페: 실행당 검색 최대 3회, 응답당 최대 20개를 요청하고 대상 카페만 남긴다. 결과가 부족해도 페이지를 무제한 순회하지 않는다.
- 유튜브: 최근 7일 영상 최대 3개, 영상당 공개 댓글 최대 30개. 좋아요 상위만 골라 전체 반응처럼 제시하지 않는다.
- Gemini: 작은 근거 묶음으로 주제 분류 1회, 선택 주제 작성 1회, 검증 1회를 기본 상한으로 둔다. 검증 실패 시 재작성은 다음 실행으로 넘긴다. 자동 모델 전환에 따른 반복 호출도 이 상한에 포함한다.
- 네이버·유튜브 접근 정보가 없으면 해당 출처를 `설정 필요`로 표시한다. 키의 값은 모델이나 로그에 전달하지 않는다.
- 추가 과금 가능성이 있는 검색 도구는 기본 자동 실행에서 제외한다. 기존 Tavily나 Gemini 검색 연동을 켜려면 사용 가능 조건을 별도로 확인한다.

## 6. 근거와 주제 선정 기준

자료는 출처 종류, 검증된 원문 URL, 제공자 자료 ID, 제목, 확인된 짧은 근거, 작성 시각 또는 미확인 상태, 수집 시각, 열람 범위, 중복 해시를 저장한다. 원문 전체, 외부 작성자의 IP·프로필·연락처는 저장하지 않는다. 모델에 넣을 본문은 개인정보와 메뉴·광고를 제거하고 길이를 제한한다.

최근 24시간의 새로운 화제와 최근 7일에 반복된 질문을 따로 본다. 동일·유사 글의 재게시를 하나로 묶는다. 플랫폼별 수집 건수와 누락 상태를 함께 기록한다. 수집량이나 추천 수를 전체 PUBG 이용자의 대표 의견으로 표현하지 않는다. 데이터가 적을 때 백분율 민심 점수는 만들지 않는다.

주제는 아래 순서로 고른다.

1. 실제 근거가 있고 현재 패치·플랫폼과 관련이 있는가.
2. 최근 BGMS 게시글과 주제가 중복되지 않는가. 같은 주제는 7일 안에 반복하지 않되 공식 변경이 확인되면 새 변경점을 설명할 수 있다.
3. 이용자가 바로 이해하거나 적용할 질문·설명이 있는가.
4. 여러 독립 자료에서 반복되는가. 한 자료만 있으면 개별 질문·의견으로 명시한다.
5. BGMS에서 해당 문제를 해결할 실제 기능이나 설명으로 연결할 수 있는가.

상황에 맞는 공략, 공식 발표 해설, 반복 질문 답변을 작성한다. 출처가 부족한 날에는 발행을 보류한다. 주제가 정해진 요일 편성에 맞추기 위해 부족한 근거를 꾸미지 않는다.

## 7. 글 작성과 자동 발행 정책

작성자는 `BGMS AI 비서`로 표시한다. 말투는 친근한 존댓말로 하고 배그 용어는 필요한 만큼 사용한다. 직접 플레이한 후기, 실제 이용자인 척하는 경험, 가짜 대화는 만들지 않는다.

글은 구체적인 제목, 약 600~1,200자의 본문, 필요할 때 실전 적용 설명, 답하기 쉬운 질문 한 개, 확인한 출처 링크로 구성한다. 글 길이는 목표이며 의미 없이 늘리지 않는다. 공식 사실·관찰한 의견·미검증 주장·편집자의 제안을 구분한다. 무기 수치나 변경 사항은 확인한 공식 근거가 없으면 단정하지 않는다. 원문을 장문 복제하지 않고 요약·비교·설명을 추가한다.

모델은 자유 URL 대신 제공받은 근거 ID를 반환하고 서버가 실제 원문 링크로 치환한다. 모델의 자체 신뢰도 숫자만으로 발행하지 않는다. 근거 ID 존재, 최신성 주장과 날짜의 일치, 중복, 금지된 개인정보, 허용 HTML을 코드로 검사한다. 근거 내용과 초안의 의미 일치는 별도 검증 호출로 보조하되 완벽한 사실 검증으로 간주하지 않는다.

기존 관리 에이전트의 일반 게시·삭제·권한 변경 승인 정책은 유지한다. 커뮤니티 비서 전용 정책으로 지정 계정·허용 카테고리·검증된 초안·하루 1글만 자동 발행할 수 있게 한다. 카테고리는 구현 시 현재 게시판에서 실제 지원하는 값에 매핑하고 관리자 설정으로 노출한다. 임의 계정 지정, 일반 관리자 도구 실행, 기존 글 삭제는 이 권한에 포함하지 않는다.

발행 직전에 비서 활성 상태, 계정, 초안 상태, 품질 검사, 한국시간 기준 일일 사용량을 다시 확인한다. 재시작이나 응답 유실에도 초안 ID로 기존 게시 결과를 조회한다. 일일 발행 슬롯과 초안 ID의 고유성은 DB에서 보장하여 동시 실행으로 2글이 생기지 않게 한다. 보류된 옛 초안을 다음 날 자동으로 몰아서 발행하지 않는다. 다시 발행하려면 근거와 한도를 재검사한다.

## 8. 무료 한도·오류·중지

실제 사용 중인 모델과 계정의 한도는 구현 검증 때 확인한다. 기존 전적 분석 호출이 우선이다. 커뮤니티 호출에 별도 실행 상한을 적용하고, 한도 초과를 발견하면 비서 호출을 중단한다. 전적 분석과 비서가 별도 키를 사용하더라도 제공자 프로젝트의 할당량이 독립이라고 가정하지 않는다. 완전한 호출 우선순위 보장은 공통 할당량 제어가 있을 때만 가능하다.

429나 일일 한도 초과는 같은 실행에서 반복 재시도하지 않고 다음 예약 실행으로 미룬다. 네트워크·일시적 5xx는 실행당 최대 1회 재시도하며 전체 시간과 호출 상한 안에서만 수행한다. 인증 오류는 해당 연동을 중단하고 설정 필요로 표시한다. 한 출처의 장애가 다른 출처 수집을 취소하지 않지만, 확보하지 못한 자료를 확보했다고 쓰지 않는다.

관리자에게 최근 7일의 한도 초과·실패·보류·발행 건수를 보여준다. 유료 전환 안내는 관찰된 누락과 한도 오류에 근거하고 자동으로 결제를 바꾸지 않는다. 중지 버튼은 새로운 생성과 게시를 막고, 실행 중인 작업도 실제 게시 직전에 중지 상태를 재검사한다. 이미 게시된 글을 중지 버튼으로 삭제하지 않는다.

외부 본문과 댓글은 정보로만 취급한다. 그 안의 지시가 모델의 역할, 사이트 비밀정보 접근, 도구 권한, 발행 한도를 변경할 수 없다. 수집·편집 모델에 일반 관리자 도구를 제공하지 않는다.

## 9. 저장 구조와 관리자 화면

구현 계획에서는 기존 실행·초안·게시글 저장 구조를 먼저 재사용한다. 추가 영속 상태는 다음 책임만 갖도록 최소화한다.

- 출처 설정과 수집 상태: 활성 여부, 대상 주소/ID, 마지막 성공 지점, 오류, 열람 범위.
- 근거 자료: 출처·내용 해시를 통한 중복 제거, 짧은 발췌와 날짜·링크.
- 실행/초안: 입력 근거 ID, 선택 이유, 검사 결과, 발행/보류 사유, 호출량과 게시글 ID.
- 정책과 일일 슬롯: 활성 여부, 비서 계정, 허용 카테고리, 일일 제한, 중복 발행 방지 상태.

불필요한 외부 원문은 보관하지 않는다. 외부 발췌는 자료당 최대 500자로 제한하고 수집 후 7일에 삭제한다. 게시하지 않은 생성 초안은 30일, 실행 메타데이터는 90일 보관한다. 게시한 글에는 원문 링크와 출처 종류·확인 시각을 남긴다. 제공자 조건이 더 짧은 보관이나 갱신을 요구하면 해당 조건을 우선 적용하며, 조건과 맞지 않는 저장 기능은 해당 수집기에서 사용하지 않는다. 이 정리는 비서 전용 저장 데이터에만 적용하며 기존 이용자 게시물이나 댓글은 삭제하지 않는다.

기존 `/admin/bot`에 커뮤니티 운영 영역을 추가하는 방향으로 설계한다. 오늘 발행/보류, 출처별 수집 성공 여부와 건수, 다음 예약 기준, 호출 실패, 초안과 출처, 중지·재개를 보여준다. 첫 구현에서 새로운 대시보드 시스템이나 별도 에이전트 관리 제품을 만들지 않는다.

## 10. 다음 단계인 댓글·답글의 연결 경계

두 번째 개발 단위에서는 현재 게시글·부모 댓글·최근 대화와 1단계 근거 ID를 응대 입력으로 사용한다. 공개적으로 AI 비서임을 표시하고 사이트 질문·관련 질문·비서에게 온 답글에 우선 응답한다. 자기 댓글이나 이미 처리한 댓글에 자동 응답하지 않고 봇 간 대화, 삭제된 대상, 신고·분쟁을 구분한다.

댓글·답글 합계 하루 10개 상한, 동시 처리 잠금, 대상 댓글별 중복 방지, 대화별 응답 횟수, 응답 지연, 운영자 이관 조건은 2단계 설계에서 확정한다. 이 문서가 댓글 자동 등록을 실행하는 승인은 아니다. 댓글·답글 기능이 추가되면 운영 성과에서 비서 작성분을 반드시 제외한다.

## 11. 검증과 운영 시작 기준

구현 후 아래 동작을 확인한다.

1. 실제 실행 환경에서 세 출처 각각 최소 1건 수집 또는 구체적 미지원/설정 필요 상태가 나온다. 읽기 실패를 0건 성공으로 기록하지 않는다.
2. 디시 광고·다른 갤러리 링크 제외, 카페 정확한 대상 주소 필터, 작성 시각 미확인 처리, 유튜브 댓글 비활성 처리를 고정된 예시 데이터로 검증한다.
3. 근거 없는 무기 수치, 미등록 출처 ID, 오래된 자료의 최신 주장, 반복 주제, 외부 본문의 지시를 넣었을 때 발행 검사를 통과하지 않는다.
4. 잘못된 인증·계정·카테고리, 중지 상태, 일일 상한, 동시에 실행한 두 발행 요청, 성공 후 응답 유실 재시도에서 추가 글이 생기지 않는다.
5. 429·5xx·한 출처 장애에서 호출 상한과 보류 사유가 지켜진다.
6. 초기 검증은 게시하지 않는 실행으로 실제 수집 → 근거 → 초안 → 검사 → 관리자 확인을 연결한다. 검증 후 사용자가 정한 자동 운영 정책을 활성화한다.
7. 해당 변경에 필요한 기존 관리자·게시판 검증을 실행한다. 1단계 완료를 댓글·답글까지 완성됐다고 보고하지 않는다.

성과는 AI 게시글 수가 아니라 실제 이용자의 열람, 참여, 질문 해결과 운영자의 수정 필요 빈도로 평가한다. 낮은 표본에서 수익 증가나 전체 민심을 단정하지 않는다.
